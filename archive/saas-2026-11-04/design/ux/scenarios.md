# Пользовательские сценарии

Сценарии — проверяемое описание того, что делает человек в системе. Каждый сценарий
ссылается на функциональные требования [brief.md](../brief.md) и на инварианты
[domain/invariants.md](../domain/invariants.md). Экраны — в [screens.md](screens.md).

Обозначения: **Роль** — кто действует; **Предусловия** — что уже верно;
**Основной поток** — счастливый путь; **Альтернативы и ошибки** — что система
делает иначе; **Приёмка** — наблюдаемый результат.

## US-01 Первичная настройка организации

- **Роль**: администратор организации.
- **Цель**: завести дома, помещения и лицевые счета, чтобы стало возможно начисление.
- **Предусловия**: пользователь аутентифицирован и имеет роль `admin` в организации.
- **Основной поток**:
  1. Администратор создаёт дома (адрес, город, тип).
  2. Добавляет помещения: вид (квартира/дом/машиноместо), номер, площадь.
  3. Для каждого помещения открывает лицевой счёт с номером.
  4. Добавляет плательщиков и связывает их с помещениями (собственник, наниматель, доля).
  5. Заводит услуги и тарифы с датой начала действия.
- **Альтернативы и ошибки**:
  - Номер лицевого счёта уже занят в организации → `CONFLICT`, поле подсвечено.
  - Помещение без площади → `VALIDATION_FAILED`; дом без адреса → `VALIDATION_FAILED`.
  - Тариф с датой начала, раньше действующего, но без перекрытия → принимается;
    перекрытие периодов действия → `BUSINESS_RULE`.
- **Приёмка**: лицевой счёт виден в реестре, помещение связано с плательщиком.
- **Связи**: FR-01, FR-02, FR-03; INV-04.

## US-02 Массовое начисление за период

- **Роль**: бухгалтер.
- **Цель**: начислить суммы по всем лицевым счетам за месяц.
- **Предусловия**: период не закрыт; тарифы на дату начисления заданы.
- **Основной поток**:
  1. Бухгалтер выбирает период `YYYY-MM` и набор услуг.
  2. Запускает расчёт в режиме «черновик» — видит количество и сумму.
  3. Проверяет выборку и нажимает «Провести».
  4. Система создаёт начисления, фиксирует прогон и публикует `AccrualPosted`.
- **Альтернативы и ошибки**:
  - Повторный запуск с тем же ключом идемпотентности → возвращается результат первого.
  - Для части лицевых счетов нет тарифа → прогон завершается частично, отчёт о
    пропущенных с явным списком; ничего не проводится «молча».
  - Период уже проведён → `CONFLICT` (`PERIOD_CLOSED`), предложено сторно.
- **Приёмка**: число начислений совпадает с числом лицевых счетов с тарифом;
  повторный запуск не увеличивает количество.
- **Связи**: FR-04; INV-03, INV-09; QS-01.

## US-03 Выставление счетов

- **Роль**: бухгалтер.
- **Цель**: выставить счета/квитанции за период с единым сроком оплаты.
- **Предусловия**: начисления проведены.
- **Основной поток**:
  1. Бухгалтер выбирает период и срок оплаты.
  2. Система формирует по одному счёту на лицевой счёт, строки — по услугам.
  3. Счета переходят в состояние «Выставлен», публикуется `InvoiceIssued`.
  4. Житель видит счёт в личном кабинете.
- **Альтернативы и ошибки**:
  - Счёт за этот период уже существует → `CONFLICT` (`INVOICE_ALREADY_ISSUED`).
  - Сумма счёта равна нулю → счёт не выставляется, попадает в отчёт «пропущенные».
  - Срок оплаты раньше периода → `VALIDATION_FAILED`.
- **Приёмка**: сумма счёта равна сумме начислений периода; счёт не редактируется
  после выставления.
- **Связи**: FR-05; INV-05, INV-10, INV-12; QS-01.

## US-04 Приём платежа вручную

- **Роль**: кассир.
- **Цель**: зафиксировать поступление денег от плательщика.
- **Предусловия**: лицевой счёт открыт.
- **Основной поток**:
  1. Кассир находит лицевой счёт по номеру/адресу/ФИО.
  2. Вводит сумму, дату поступления, канал (касса/банк), примечание.
  3. Система создаёт платёж, аудит-запись и событие `PaymentRegistered`.
  4. Предлагает автоматическое распределение (US-05).
- **Альтернативы и ошибки**:
  - Сумма ≤ 0 → `VALIDATION_FAILED`.
  - Платёж по закрытому счёту → `BUSINESS_RULE`.
  - Повторное нажатие «Сохранить» → тот же платёж, второй не создаётся (INV-13).
- **Приёмка**: платёж виден в истории счёта; баланс изменился на сумму платежа.
- **Связи**: FR-06, FR-09; INV-13, INV-20; QS-02.

## US-05 Распределение платежа

- **Роль**: кассир / бухгалтер.
- **Цель**: закрыть платёж на счета, чтобы долг уменьшился.
- **Предусловия**: платёж существует и имеет нераспределённый остаток.
- **Основной поток**:
  1. Система предлагает FIFO по сроку оплаты.
  2. Пользователь подтверждает или правит суммы по счетам.
  3. Система создаёт распределения, обновляет состояние счетов и баланс.
  4. Публикуется `PaymentAllocated`, при полном закрытии — `InvoiceSettled`.
- **Альтернативы и ошибки**:
  - Сумма больше остатка счёта → `BUSINESS_RULE` (`ALLOCATION_EXCEEDS_INVOICE`).
  - Сумма больше остатка платежа → `BUSINESS_RULE` (`ALLOCATION_EXCEEDS_PAYMENT`).
  - Конкурентное изменение → `CONFLICT` (`CONCURRENT_MODIFICATION`), повтор с перечитыванием.
  - Остаток платежа остаётся → становится авансом лицевого счёта.
- **Приёмка**: сумма распределений по счёту равна `paid_minor`; по счёту состояние
  «Оплачен» только при полном покрытии.
- **Связи**: FR-08, FR-09; INV-06, INV-07, INV-14, INV-15; QS-04.

## US-06 Импорт банковской выписки

- **Роль**: бухгалтер.
- **Цель**: занести пачку поступлений без ручного ввода.
- **Предусловия**: выписка получена из банка в согласованном формате.
- **Основной поток**:
  1. Пользователь загружает файл выписки.
  2. Система создаёт батч импорта и разбирает строки.
  3. Каждая строка сопоставляется с лицевым счётом по реквизитам.
  4. Создаются платежи; несопоставленные строки попадают в очередь сверки.
  5. Отчёт импорта: создано / пропущено как дубль / требует ручной сверки.
- **Альтернативы и ошибки**:
  - Повторная загрузка того же файла → все строки распознаны как дубли, новых нет.
  - Строка без однозначного лицевого счёта → не создаётся платёж, строка в очереди.
  - Битая строка → батч не падает целиком, ошибка строки фиксируется.
- **Приёмка**: повторный импорт не увеличивает число платежей; отчёт объясняет
  каждую строку.
- **Связи**: FR-07; INV-13, INV-16; QS-03.

## US-07 Исправление ошибочного начисления (сторно)

- **Роль**: бухгалтер.
- **Цель**: отменить неверное начисление и выставить корректное.
- **Предусловия**: начисление проведено.
- **Основной поток**:
  1. Бухгалтер открывает начисление, выбирает «Сторно», указывает причину.
  2. Система создаёт обратную запись со ссылкой на исходную; исходная остаётся.
  3. Если счёт уже выставлен и не оплачен — счёт аннулируется с причиной.
  4. Бухгалтер повторяет начисление корректной суммой.
- **Альтернативы и ошибки**:
  - Повторное сторно того же документа → `CONFLICT` (`REVERSAL_ALREADY_EXISTS`).
  - Счёт с распределениями → аннулирование запрещено (`INVOICE_IMMUTABLE`);
    предлагается сторно распределения и работа с задолженностью.
- **Приёмка**: в истории видны обе записи; баланс отражает только корректную сумму.
- **Связи**: FR-10; INV-09, INV-11, INV-19; QS-06.

## US-08 Просмотр начислений и оплат жителем

- **Роль**: собственник/наниматель.
- **Цель**: понять, сколько и за что начислено, что оплачено, сколько долг.
- **Предусловия**: пользователь связан с помещением.
- **Основной поток**:
  1. Житель входит в личный кабинет.
  2. Видит список помещений и текущий баланс.
  3. Открывает период: начисления по услугам, счёт, платежи и распределения.
  4. Скачивает квитанцию (PDF) и видит срок оплаты.
- **Альтернативы и ошибки**:
  - Нет связи с помещением → пустое состояние с инструкцией обратиться в УК.
  - Данные другого помещения недоступны (изоляция по связи, не по вводу URL).
- **Приёмка**: суммы в кабинете совпадают с суммами документов; чужие данные
  недоступны.
- **Связи**: FR-11, FR-12; QS-05.

## US-09 Отчёт по дебиторской задолженности

- **Роль**: руководитель / бухгалтер.
- **Цель**: увидеть, кто и сколько должен, с разбивкой по срокам.
- **Предусловия**: есть выставленные счета.
- **Основной поток**:
  1. Пользователь выбирает период и дом.
  2. Система строит отчёт: сумма долга, число счетов, корзины просрочки
     (0–30, 31–60, 61–90, 90+).
  3. Пользователь выгружает CSV.
- **Альтернативы и ошибки**:
  - Отчёт строится по read-model; при отставании обновления показывается
    «данные на момент …», а не устаревшее значение без пометки.
- **Приёмка**: сумма отчёта совпадает с суммой остатков счетов на дату.
- **Связи**: FR-14; QS-06.

## US-10 Закрытие лицевого счёта

- **Роль**: администратор.
- **Цель**: закрыть счёт выбывшего помещения.
- **Предусловия**: счёт открыт.
- **Основной поток**: администратор закрывает счёт с указанием даты.
- **Альтернативы и ошибки**: ненулевой баланс → `BUSINESS_RULE`
  (`ACCOUNT_HAS_BALANCE`), сначала нужно погасить/перенести.
- **Приёмка**: закрытый счёт не принимает начисления и платежи.
- **Связи**: FR-01; INV-08.

## US-11 Управление ролями

- **Роль**: администратор.
- **Цель**: выдать бухгалтеру доступ, отозвать у уволенного.
- **Основной поток**: администратор добавляет пользователя в организацию с ролью;
  отзыв — удаление членства.
- **Альтернативы и ошибки**: попытка выдать роль вне своей организации →
  `FORBIDDEN`; последний администратор не может быть удалён → `BUSINESS_RULE`.
- **Приёмка**: после отзыва доступа запросы пользователя отклоняются.
- **Связи**: FR-12; QS-05.

## US-12 Аудит изменения документа

- **Роль**: аудитор.
- **Цель**: понять, кто и почему изменил финансовый документ.
- **Основной поток**: аудитор открывает карточку документа → вкладка «История»:
  кто, когда, действие, причина, связанные документы.
- **Альтернативы и ошибки**: аудит-записи не редактируются и не удаляются.
- **Приёмка**: для каждого изменения есть запись; попытка правки аудита невозможна.
- **Связи**: FR-13; INV-18; QS-06.
