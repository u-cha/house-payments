# Бриф: архитектура приложения house-payments

Статус: **proposed** (черновик для ревью). Владелец решения: продукт + техлид.
Дата: 2026-11-04.

Документ фиксирует границы задачи, требования, критерии приёмки и точки реализации.
Все остальные артефакты (`domain/`, `architecture/`, `ux/`) выводятся из этого брифа
и ссылаются на его идентификаторы.

## 1. Назначение

Система учёта начислений, счетов и платежей за жильё: квартиры, дома, машиноместа.
Продукт — многопользовательский (multi-tenant) SaaS для организаций, которые
**выставляют** счета за жилищно-коммунальные и связанные услуги: управляющих
компаний, ТСЖ/ЖК, расчётных центров. Житель (собственник/наниматель) получает
личный кабинет только на чтение своих начислений и платежей.

### Почему именно так

В предметной области есть необратимый факт: начисление и счёт — это **документ**,
который нельзя править после выставления. Значит, система должна быть системой
учёта (source of truth) для организации-эмитента, а не трекером для жителя.
Трекер для жителя — возможный будущий продукт, но он не требует ни распределения
платежей, ни сторно, ни мультитенантности, и его архитектура была бы другой.

### Допущение, требующее подтверждения

> **A-01.** Целевой пользователь — организация-эмитент счетов (УК/ТСЖ/РЦ), а не
> частное лицо, ведущее личный бюджет. Если продукт задуман как личный трекер,
> границы MVP сужаются (см. §3), а модель остаётся пригодной: объект «организация»
> становится владельцем одного домашнего хозяйства. Решение фиксируется в ADR-0001.

## 2. Заинтересованные стороны

| Сторона | Интерес | Критичность |
|---|---|---|
| Администратор организации (УК/ТСЖ) | Настроить дома, услуги, тарифы, роли | Высокая |
| Бухгалтер/расчётчик | Провести массовое начисление, выставить счета, исправить ошибку сторно | Критическая |
| Кассир/оператор | Принять платёж, распределить его, найти платёж по выписке | Критическая |
| Собственник/наниматель | Увидеть начисления, счета и историю платежей без звонков | Высокая |
| Внутренний аудитор/руководитель | Отчёты: собираемость, дебиторка, расхождения | Средняя |
| Банк/эквайринг | Передать выписку/вебхук о платеже | Высокая (интеграция) |

## 3. Границы

### В scope MVP

- Реестр организаций (тенантов), домов, помещений, лицевых счетов, плательщиков.
- Услуги и версионируемые тарифы, начисления за расчётный период.
- Счета/квитанции с неизменяемым после выставления содержимым.
- Регистрация платежей: вручную, импортом банковской выписки, вебхуком эквайринга.
- Распределение платежа по счетам (автоматически FIFO и вручную), частичная оплата.
- Сторно ошибочных начислений и счетов; аудит всех финансовых изменений.
- Личный кабинет жителя (только чтение), роли и изоляция тенантов.
- Базовые отчёты: начисления, поступления, дебиторская задолженность.

### Вне scope MVP (осознанно отложено)

- ГИС ЖКХ и другие государственные интеграции.
- Автоматизированный сбор показаний приборов учёта с устройств (только ручной ввод/импорт).
- Полноценный бухгалтерский и налоговый учёт (вместо этого — экспорт проводок в 1С).
- Онлайн-оплата картой как платёжная страница (принимаем только вебхук о результате).
- Мобильное приложение, офлайн-режим, биллинг по нормам потребления с коэффициентами.
- Пени и судебная работа (выделено в отдельный поток, не блокирует MVP).

### Ограничения

| ID | Ограничение |
|---|---|
| C-01 | Мультитенантность обязательна с первого дня: одна инсталляция — много организаций. |
| C-02 | Деньги — только целые минорные единицы (копейки), без floating point. |
| C-03 | Расчётный период — `YYYY-MM`, начисления и счета привязаны к периоду. |
| C-04 | Персональные данные: минимизация, срок хранения, разграничение доступа (152-ФЗ/GDPR-совместимо). |
| C-05 | Платёж может прийти дважды из внешнего источника — обработка обязана быть идемпотентной. |
| C-06 | Стек: TypeScript, PostgreSQL, модульный монолит; отдельные сервисы — только по доказанной необходимости. |
| C-07 | Диаграммы — только из текстовых источников (`.mmd`, `.dbml`), рендер детерминирован. |

| ID | Характеристика | Суть | Приоритет |

| QS-07 | Восстановление | RPO ≤ 15 мин, RTO ≤ 4 ч; восстановление проверено репетицией | 2 |

## 6. Критерии приёмки (DoD задачи)

| ID | Критерий |
|---|---|
| AC-01 | Определены границы, стейкхолдеры, ограничения и допущение A-01; перечислены точки реализации. |
| AC-02 | Модель данных (`domain/model.dbml`) покрывает все сущности MVP, ссылки консистентны, деньги и периоды соответствуют C-02/C-03. |
| AC-03 | Инварианты пронумерованы и у каждого указан способ принуждения (БД/домен/тест). |
| AC-04 | Архитектурный стиль, границы модулей и правила зависимостей зафиксированы ADR. |
| AC-05 | Сценарии качества измеримы и имеют проверку (fitness function или план проверки). |
| AC-06 | Пользовательские сценарии и экраны покрывают все FR уровня MVP. |
| AC-07 | Матрица прослеживаемости связывает FR → модуль → сущность → ADR/инвариант. |
| AC-08 | Все диаграммы рендерятся из текстовых источников без ошибок. |
| AC-09 | Набор проверок `pnpm test` зелёный, включая негативные тесты самого валидатора. |
| AC-10 | Остаточные риски и открытые вопросы перечислены с владельцем. |
