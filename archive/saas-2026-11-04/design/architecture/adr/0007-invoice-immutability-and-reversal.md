# ADR-0007: Неизменяемый выставленный счёт, исправление через сторно

## Статус

`proposed`, 2026-11-04. Владелец решения: продукт + техлид. Решение не принято
до ревью.

## Контекст

- Счёт/квитанция — документ, выставленный плательщику (FR-05). После выставления
  его сумма, период и состав обязаны быть воспроизводимы: на них ссылаются
  плательщик, бухгалтер, аудитор и банк.
- FR-10 требует сторно начисления/счёта с сохранением исходного документа.
  Глоссарий прямо запрещает «удалить» в финансовом контуре: есть сторно и
  аннулирование.
- INV-09, INV-11, INV-12, INV-19 задают: проведённые начисления не
  перезаписываются, аннулирование допустимо только при отсутствии распределений,
  выставленный счёт неизменяем, а сторно ссылается на оригинал и возможно ровно
  один раз. Полноту аудита задаёт INV-18.
- QS-06 требует, чтобы 100 % финансовых изменений имели запись аудита, а не
  «последнее состояние». Правка на месте делает историю невосстановимой.
- Отчётность (дебиторка, собираемость) должна объяснять каждую копейку, включая
  исправления; следовательно, ей нужны подписанные суммы, а не только итог.

## Рассмотренные варианты

### 1. Неизменяемые выставленные документы + обратные записи (выбран)

Черновик редактируется; после выставления счёт неизменяем. Исправление —
связанная обратная запись (сторно), исходный документ остаётся.

**Плюсы:** история воспроизводима; аудит объясняет «было/стало» без догадок;
юридически защитимо; нет lost update при конкурентных правках; отчётность
считается по подписанным записям; сторно можно отличить от исходной операции.

**Минусы:** больше строк; UI обязан показывать пары «документ–сторно» и не
скрывать их от жителя; отчёты суммируют знаковые величины; ошибка не исчезает из
истории (это цель, но пользователи ожидают обратного); нужен явный сценарий
исправления для бухгалтера.

### 2. Правка на месте с записью «до/после» в аудите

**Плюсы:** привычный UX «отредактировать счёт»; одна строка на документ.

**Минусы:** исходное состояние существует только в аудите и не участвует в
расчётах; невозможно доказать, что видел плательщик; конкурентные правки теряют
изменения; отчёты за прошлые периоды меняются задним числом; нарушает INV-12 и
QS-06 по существу. Отклонён.

### 3. Мягкое удаление/отмена с изменяемыми итогами

**Плюсы:** «чистый» список для пользователя; просто скрыть ошибочное.

**Минусы:** скрытая история равна отсутствию аудита; «удалить» в финансовом
контуре запрещено глоссарием; восстанавливать дебиторку по скрытым документам
невозможно; регуляторный риск. Отклонён.

### 4. Версионирование документа (несколько версий + указатель на актуальную)

**Плюсы:** формально «документ можно исправить», сохраняя версии; удобно для
электронного документооборота; явная история.

**Минусы:** указатель на актуальную версию — точка гонки; нужно правило, какая
версия участвует в расчётах; удваивает модель; большинство документов никогда не
исправляется; для аудита достаточно исходной записи и сторно. Отклонён до
появления внешнего требования (см. условия пересмотра).

## Решение

1. **Жизненный цикл.** Черновик (`draft`) редактируется. Выставление (`issued`)
   фиксирует период, сумму, строки и срок оплаты; с этого момента документ
   неизменяем. Допустимые переходы: `draft → issued`, `draft → void`,
   `issued → partially_paid → paid`, `issued/partially_paid → overdue`,
   `overdue → paid`, `paid → closed`, `issued → void` только при отсутствии
   распределений.
2. **Запрет изменения на уровне БД.** Для финансовых таблиц (`accrual`,
   `invoice`, `invoice_line`, `allocation`) триггер отклоняет `UPDATE`
   финансовых полей после фиксации, а роли приложения отозваны права `DELETE`.
   Это гарантия, а не соглашение: приложение не может «случайно» переписать
   документ.
3. **Сторно.** Исправление = новая запись со ссылкой `reversal_of_id` на
   исходную, с причиной, автором и временем; исходная запись остаётся. Один
   документ можно сторнировать один раз: повторная попытка возвращает
   `REVERSAL_ALREADY_EXISTS`.
4. **Порядок исправления.** Пока счёт не оплачен и распределений нет — он
   аннулируется, затем формируется корректный документ. Если ошибка в
   начислении — начисление сторнируется и заменяется новым; счёт, не имеющий
   распределений, при необходимости аннулируется и выставляется заново. Если
   распределения уже есть, аннулирование запрещено (INV-11), а отмена
   распределения в MVP не поддерживается (жизненный цикл платежа): исправление
   ограничено сторно начисления и корректировкой в следующем периоде. Это
   известное ограничение MVP, а не молчаливая правка.
5. **Аннулирование (`void`).** Разрешено для черновика, а для выставленного
   счёта — только при отсутствии распределений и `paid_minor = 0` (INV-11);
   причина обязательна.
   Аннулированный счёт не участвует в дебиторке, но остаётся в истории.
6. **Отчётность.** Дебиторка и собираемость считаются по знаковым суммам:
   `начислено − сторнировано`, `оплачено` — по распределениям. Read-model
   отчётности строится на этих правилах, а не на «актуальных» строках.
7. **Аудит.** Каждое сторно и аннулирование пишут `audit_event` в той же
   транзакции: кто, когда, что, основание, ссылка на исходный документ
   (QS-06, INV-18).
8. **Видимость.** Житель видит и исходный документ, и сторно; скрывать
   исправления нельзя — это часть прозрачности учёта.

## Последствия

**Положительные:**

- История финансовых документов воспроизводима на любой момент времени; аудит
  и юридическая защита обеспечены по построению.
- Конкурентные правки невозможны: нет lost update, нет «кто последний, тот и
  прав».
- Отчётность объяснима: каждая копейка дебиторки раскладывается на исходные
  записи и сторно.
- Сторно использует те же сущности и транзакционные границы, что и обычные
  операции (ADR-0005), не создавая отдельного контура.

**Отрицательные:**

- Объём растёт: каждая корректировка — новые строки. При массовых ошибках
  начисления сторно затрагивает столько же строк, сколько исходный прогон.
- UI и сценарии усложняются: нужны экраны «исправить через сторно», показ пар
  документов, объяснение жителю.
- Отчёты обязаны корректно работать со знаковыми суммами; ошибка в агрегате
  даёт неверную дебиторку.
- Привычка «просто поправить» не работает: бухгалтера нужно обучить, иначе он
  будет искать обходной путь.

**Нейтральные:**

- Аннулирование — не удаление: строка остаётся, меняется состояние.
- Сторно начисления и сторно счёта — разные операции с разными последствиями
  для распределений; обе фиксируются ссылкой на исходный документ.

## Условия пересмотра

- Появляется требование электронного юридически значимого документооборота
  (версии, подписи, внешний регламент): рассматривается вариант 4 для контура
  квитанций, не для всего учёта.
- Доля сторно становится значимой (например, массовые ошибки тарифов каждый
  период): пересматривается процесс начисления и предварительная проверка
  черновика, а не принцип неизменяемости.
- Регуляторика требует аннулирования счёта после оплаты: меняется правило
  INV-11 и порядок возврата средств.
- Требуется массовая корректировка сроков оплаты без изменения суммы: решается
  отдельным атрибутом/расширением, а не правкой документа.
