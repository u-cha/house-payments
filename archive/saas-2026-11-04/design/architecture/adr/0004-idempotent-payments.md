# ADR-0004: Идемпотентность платежей по ключу в границах тенанта

## Статус

`proposed`, 2026-11-04. Владелец решения: продукт + техлид. Решение не принято
до ревью.

## Контекст

- C-05: платёж может прийти дважды из внешнего источника — обработка обязана быть
  идемпотентной.
- Повторяют все: эквайринг при таймауте ответа, банк при повторной выгрузке
  выписки, кассир при двойном нажатии, сетевой клиент при retry, оператор при
  повторной загрузке файла.
- Дубликат платежа — не косметическая ошибка: он увеличивает аванс, искажает
  дебиторку, создаёт ложные распределения и требует ручного сторно с аудитом.
- INV-13 требует: ключ уникален в границах тенанта, повтор возвращает
  существующий платёж.
- QS-03 требует импорта 100 000 строк без дублей при повторной загрузке.
- Ключ должен быть дешёвым в проверке на потоке 200 rps (10×, A-04) — проверка
  «прочитать и сравнить» в приложении не годится, нужна уникальность в БД.

## Рассмотренные варианты

### 1. Ключ идемпотентности в границах тенанта + уникальное ограничение (выбран)

Клиент (или адаптер импорта) присылает `idempotency_key`; БД хранит
`UNIQUE (tenant_id, idempotency_key)`; повтор возвращает существующий платёж.

**Плюсы:** точная семантика «ровно один эффект»; работает для всех каналов
(ручной ввод, API, вебхук, импорт); проверка — одна вставка/конфликт индекса, без
гонок; повтор безопасен на уровне сети и приложения; следов дублей не остаётся.

**Минусы:** клиент обязан генерировать и сохранять ключ; ключи нужно хранить и
чистить (13 месяцев, A-05); при повторном использовании ключа с другим телом
запроса нужна явная ошибка, а не «тихий» возврат; ключ бесполезен, если внешняя
система не даёт стабильного идентификатора (тогда ключ выводится из данных
импорта).

### 2. Дедупликация по сумме, дате и лицевому счёту

«Если такой платёж уже есть — не создавать».

**Плюсы:** не требует изменений у клиентов; ноль настройки.

**Минусы:** ложные срабатывания на легальных одинаковых платежах (два платежа по
5 000 ₽ в один день — нормальная ситуация); пропуски, если дата или сумма
отличаются на копейку/день; границы суток и часовые пояса; нет способа отличить
дубль от совпадения. Отклонён: эвристика вместо гарантии.

### 3. Без дедупликации, разбор дублей вручную

**Плюсы:** минимальная сложность; ничего не блокирует приём денег.

**Минусы:** прямо нарушает C-05; дубли неизбежны при сбоях сети; ручной разбор
дороже и опаснее (сторно с аудитом); доверие к учёту падает. Отклонён.

### 4. Только по `external_ref` от внешней системы

**Плюсы:** естественный идентификатор для банка/эквайринга; не нужно
генерировать ключи.

**Минусы:** не у всех каналов есть стабильный `external_ref` (ручной ввод,
часть форматов выписки); разные источники могут переиспользовать номера;
отсутствие ссылки оставляет канал без защиты; повторная выгрузка файла без
ссылок не дедуплицируется. Отклонён как единственный механизм, но сохранён как
дополнительный (см. решение).

## Решение

1. `payments.RegisterPayment` принимает обязательный `idempotencyKey` (UUIDv7 или
   производный от файла/строки для импорта). Уникальность —
   `UNIQUE (tenant_id, idempotency_key)` в PostgreSQL.
2. Область уникальности — **тенант**, а не глобальная: одинаковый ключ у двух
   организаций — разные платежи. Это же правило задаёт INV-13.
3. Поведение повтора:
   - тот же ключ и тот же смысл запроса → возвращается существующий платёж,
     ответ 200, повторное событие `PaymentRegistered` не публикуется; в ответе
     признак повтора;
   - тот же ключ и другой payload → `409 CONFLICT`, `reason:
     DUPLICATE_IDEMPOTENCY_KEY`, существующий платёж не изменяется. Для этого
     рядом с ключом хранится нормализованный отпечаток запроса (лицевой счёт,
     сумма, `paid_at`, канал, назначение), а не только сам ключ.
   - разные ключи при одинаковых сумме/дате — разные платежи; семантические
     дубли разных источников ищет сверка (ADR-0008), а не идемпотентность.
4. Внешняя ссылка — дополнительный барьер: `UNIQUE (tenant_id, source,
   external_ref)` для строк, где `external_ref` задан. Ограничение частичное:
   платежи без ссылки (ручной ввод) не участвуют.
5. Импорт выписки идемпотентен на двух уровнях: `batchKey` (повторная загрузка
   того же файла) и `external_ref` строки (пересечение файлов) — см. ADR-0008.
   `batchKey` вычисляется детерминированно из тенанта, источника и содержимого
   файла.
6. Ключи хранятся 13 месяцев (12 месяцев горизонта повторов + 1 месяц запаса,
   A-05), затем удаляются регламентной задачей. Повтор с ключом старше горизонта
   создаст новый платёж — это осознанная граница, зафиксированная в контракте.
7. Проверка идемпотентности выполняется вставкой в транзакции регистрации
   платежа; никакого предварительного `SELECT` без уникального индекса.

## Последствия

**Положительные:**

- Повторные вебхуки, retry клиента и повторная загрузка файла не создают денег
  из воздуха; QS-03 выполняется без ручной чистки.
- Ошибка сети перестаёт быть финансовым инцидентом: клиент может безопасно
  повторять запрос.
- Дедупликация не зависит от эвристик и объяснима аудитору: «ключ тот же —
  платёж тот же».
- Проверка дешёвая: одна уникальная вставка на платёж, индекс с ведущим
  `tenant_id`.

**Отрицательные:**

- Клиенты обязаны генерировать ключи и не переиспользовать их; это требование
  контракта API, а не рекомендация.
- Нужно хранить отпечаток запроса и ключи 13 месяцев; растёт объём и появляется
  задача очистки.
- Ошибка «тот же ключ, другое тело» требует явной обработки в UI/интеграции:
  пользователь должен увидеть конфликт, а не «платёж уже есть».
- Идемпотентность не спасает от семантических дублей с разными ключами —
  их разбирает сверка.

**Нейтральные:**

- Ключ не является бизнес-идентификатором платежа: идентификатор платежа —
  отдельный UUIDv7.
- Для импорта ключ выводится детерминированно, поэтому повтор файла не требует
  участия оператора.

## Условия пересмотра

- Внешний источник не даёт ни стабильного ключа, ни `external_ref`, и
  детерминированный ключ вывести нельзя: нужен резервный механизм (окно
  дедупликации в staging) с отдельным ADR.
- Объём ключей становится значимым (например, > 100 млн строк на хранении):
  пересматривается горизонт 13 месяцев и способ хранения.
- Появляется требование идемпотентности на уровне API-шлюза или нескольких
  сервисов (после пересмотра ADR-0001): ключ придётся вынести в общее
  хранилище.
- Регуляторика требует иного срока хранения ключей или их аудита.
