# ADR-0001: Модульный монолит вместо микросервисов и serverless

## Статус

`proposed`, 2026-11-04. Владелец решения: продукт + техлид. Решение не принято
до ревью; до этого момента оно описывает предлагаемый стиль, а не факт.

## Контекст

- C-06 фиксирует стек: TypeScript, PostgreSQL, модульный монолит; отдельные
  сервисы — только по доказанной необходимости.
- A-01: целевой пользователь — организация-эмитент счетов, система является
  source of truth финансового учёта. Ошибка в деньгах не «чинится» постфактум:
  она ломает доверие к учёту и требует сторно с аудитом.
- Домен требует транзакционной согласованности нескольких записей: регистрация
  платежа, распределение, остаток лицевого счёта, состояние счёта, аудит и
  outbox-событие должны фиксироваться атомарно (QS-04, QS-06).
- Объёмы базового профиля умеренные (A-02, [scaling.md](../scaling.md)): 200 000
  лицевых счетов, до 200 rps платежей. Узкое место — не горизонтальное
  масштабирование, а корректность и стоимость эксплуатации.
- QS-09 требует выдержать 10× рост **без смены стиля**; QS-10 — онбординг
  инженера менее чем за день. Каждый дополнительный процесс, брокер и контур
  деплоя увеличивает стоимость входа.

Силы, действующие одновременно: транзакционная целостность (тянет к одной БД),
независимость изменений (тянет к сервисам), простота эксплуатации (тянет к
монолиту), возможность точечного масштабирования (тянет к сервисам).

## Рассмотренные варианты

### 1. Модульный монолит с одной PostgreSQL (выбран)

Один деплой API, один процесс воркера, одна база; модули с публичным `api.ts` и
запретом на импорт внутренностей.

**Плюсы:** ACID-транзакция на весь финансовый сценарий без распределённых
протоколов; один поток миграций и один набор бэкапов; низкая задержка вызовов
внутри процесса; простая локальная разработка; легко выполнить QS-10; границы
модулей проверяются тестом, а не сетевым контрактом.

**Минусы:** домен отказа общий — падение процесса влияет на все модули;
деплой связан; масштабируется приложение целиком; дисциплина границ держится
только архитектурными тестами и ревью; одна БД — общий предел по объёму.

### 2. Микросервисы по bounded context

`billing`, `invoicing`, `payments`, `ledger`, `registry` — отдельные сервисы,
свои базы, взаимодействие через брокер.

**Плюсы:** независимый деплой и масштабирование; изоляция отказов; команда
владеет сервисом целиком; можно выбрать технологию под задачу.

**Минусы:** транзакция «платёж + распределение + остаток + аудит» становится
сагой с компенсациями — это прямо повышает риск двойного списания и усложняет
QS-04; нужен брокер, идемпотентность каждого шага, распределённая трассировка,
дежурство на N сервисов; сетевые отказы становятся частью бизнес-логики; для
команды текущего масштаба это стоимость без выгоды; QS-10 деградирует
(локальный запуск пяти сервисов с брокером не укладывается в день).

### 3. Serverless: функции + управляемая БД + очередь

Каждая операция — отдельная функция; состояние — в управляемом PostgreSQL;
события — в управляемой очереди.

**Плюсы:** оплата по факту, нет серверов, автоматическое масштабирование,
быстрый старт для тонких сценариев.

**Минусы:** холодные старты против p99 ≤ 300 мс (QS-02); ограничения времени
выполнения против массового начисления 5 000 счетов за 60 с (QS-01) и импорта
100 000 строк (QS-03); пулы соединений к PostgreSQL из функций — отдельная
проблема; блокировки и транзакции плохо ложатся на модель «функция на запрос»;
отладка распределённого сценария дороже; вендор-лок.

### 4. Классический монолит без модульных границ

Один код, любые импорты, общие таблицы.

**Плюсы:** минимальные стартовые затраты, нет церемоний.

**Минусы:** границы исчезают через несколько месяцев; невозможно понять, кто
владеет данными; выделение сервиса позже требует переписывания; QS-09
(эволюционность) достигается только рефакторингом «всё сразу». Отклонён как
исходный вариант, а не как альтернатива на равных.

## Решение

Принимается **модульный монолит**:

1. Один артефакт деплоя API и один артефакт воркера из одного репозитория и
   одного процесса сборки; они делят код и базу, но запускаются раздельно, чтобы
   фоновая нагрузка (outbox relay, начисления, импорт) не влияла на p99
   HTTP-запросов.
2. Одна PostgreSQL. Модули владеют своими таблицами; прямой доступ к чужим
   таблицам запрещён — только публичный контракт или read-model владельца.
3. Модуль экспортирует только `api.ts` (use case, события, DTO). Зависимости —
   `shared` и публичные контракты; циклы запрещены и проверяются тестом.
4. Межмодульные изменения в одной транзакции допускаются только через явный
   порт владельца данных (ADR-0005); всё остальное — события после коммита.
5. Путь выделения сервиса проектируется заранее: сначала `integrations`, затем
   `notifications`/`reporting` (они уже асинхронные), затем `payments`; `ledger`
   и `invoicing` — в последнюю очередь, потому что их транзакционная связка
   является ядром корректности.

## Последствия

**Положительные:**

- Финансовый сценарий атомарен: нет саг, компенсаций и «двойной записи» между
  базами; QS-04 и QS-06 достигаются локальными средствами PostgreSQL.
- Один поток миграций, один бэкап, один мониторинг, один способ локального
  запуска — QS-10 выполним.
- Задержки внутри процесса минимальны — резерв для QS-02.
- Выделение сервиса позже возможно по одному модулю, без переписывания модели:
  контракт уже существует в виде `api.ts`.

**Отрицательные:**

- Общий домен отказа: ошибка в одном модуле может уронить процесс API. Частично
  компенсируется раздельным процессом воркера и health checks (QS-08).
- Деплой связан: изменение в `registry` требует релиза всего приложения.
- Одна БД — общий предел по объёму и конкурентной записи. Управляется
  триггерами T-01…T-05, T-13 в [scaling.md](../scaling.md).
- Границы модулей не обеспечены средой исполнения: без архитектурных тестов они
  деградируют. Тесты обязательны, а не «желательны».
- Нельзя выбрать другую технологию для отдельного модуля без выделения сервиса.

**Нейтральные / требующие дисциплины:**

- Батч-операции (`RunAccruals`, `ImportStatement`) обязаны идти через воркер, а
  не через HTTP-процесс, иначе QS-01/QS-03 конкурируют с QS-02.
- Любой модуль, которому нужен чужой данные-контракт, обязан получить его через
  `api.ts`, а не через SQL-join по чужой таблице; отчётные исключения — только
  через read-model владельца.

## Условия пересмотра

Решение пересматривается при наступлении любого из условий (пороги — в
[scaling.md](../scaling.md) §7):

- Устойчивая нагрузка регистраций платежей > 500 rps или импорт > 5 000 000
  строк/сутки, и настройка пула/индексов/батчей не возвращает пороги QS-02/QS-03
  (T-06, T-08).
- Одна PostgreSQL > 2 ТБ или время восстановления превышает RTO QS-07, и
  партиционирование с архивом не решает проблему (T-05).
- Появляется требование независимого релизного цикла для модуля, который нельзя
  удовлетворить ветвлением/фича-флагами (например, отдельная команда с
  собственным SLA).
- Модулю требуется принципиально иной рантайм или изоляция по регуляторным
  причинам (выделенный контур данных).
- Число команд, работающих в одном репозитории, делает связанный деплой
  блокирующим (оценивается по частоте конфликтов релизов, а не по ожиданию).

Порядок выделения при пересмотре: `integrations` → `notifications`/`reporting` →
`payments`. `ledger`/`invoicing` выделяются последними и только вместе, если
сохраняется возможность одной транзакции на распределение.
