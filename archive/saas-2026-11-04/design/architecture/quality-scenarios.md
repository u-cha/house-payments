# Сценарии качества: измеримые требования и проверки

Статус: **proposed** (ревью 2026-11-04). Основание: [brief.md](../brief.md) §5
(QS-01…QS-10), ограничения C-01…C-07. Связанные решения:
[core-modules.md](core-modules.md), ADR-0001…ADR-0008, [scaling.md](scaling.md).

## 1. Как читать и что означает «проверка»

Сценарий качества — это не пожелание, а утверждение с порогом и способом
опровержения. У каждого сценария ниже шесть полей:

- **Источник** — кто или что создаёт стимул.
- **Стимул** — конкретное событие с параметрами.
- **Окружение** — при каких условиях стимул должен быть выдержан.
- **Ответ** — что система делает (какой модуль, какая транзакционная граница).
- **Мера** — числовой порог; формулировки «быстро» и «надёжно» запрещены.
- **Проверка** — чем порог опровергается: fitness function (исполняемая
  архитектурная проверка), интеграционный тест, нагрузочный тест или план с
  владельцем и сроком.

Приоритеты взяты из брифа без изменений: QS-01…QS-06 — приоритет 1,
QS-07…QS-09 — приоритет 2, QS-10 — приоритет 3. Обязательный минимум — пороги
брифа; дополнительные уточнения (p50/p95, поведение при всплеске, частота
репетиций) — предложения к принятию вместе с ADR, а не новые требования.
Конфликты между сценариями разбираются в §5.

## 2. Сценарии

### QS-01 — Производительность: массовое начисление

| Поле | Значение |
|---|---|
| Источник | Бухгалтер/расчётчик организации |
| Стимул | Запуск начисления за расчётный период на 5 000 лицевых счетов × 6 услуг (30 000 начислений) в режиме `post` |
| Окружение | Штатная нагрузка (не более 20 rps регистраций платежей), рабочая БД с объёмом за 3 года (допущения A-03, A-05 в [scaling.md](scaling.md)), батчи по 500 счетов |
| Ответ | `billing.RunAccruals`: батч-транзакции по 500 счетов, запись начисления + аудита + outbox в одной транзакции, прогресс в `period_run`; повтор с тем же `idempotencyKey` возвращает результат первого прогона без новых записей |
| Мера | ≤ 60 с на 5 000 счетов (≥ 83 счёта/с); p95 прогона ≤ 45 с; повторный прогон — 0 новых начислений, 0 новых событий outbox; частичный сбой возобновляется с последнего батча, а не с нуля |
| Проверка | Нагрузочный тест на seed 5 000 × 6 в `tests/performance/` + интеграционный тест идемпотентности повтора. Владелец: бэкенд `billing` |

### QS-02 — Задержка: регистрация платежа

| Поле | Значение |
|---|---|
| Источник | Кассир, вебхук эквайринга, API интеграции |
| Стимул | Устойчивый поток 20 rps регистраций платежей, всплеск 100 rps в течение 60 с |
| Окружение | Рабочие часы, прогретый пул соединений, БД с боевым объёмом, без синхронных вызовов внешних систем в транзакции |
| Ответ | `payments.RegisterPayment`: одна транзакция (INSERT платежа + аудит + outbox), проверка идемпотентности по уникальному индексу; внешние уведомления — только через outbox после коммита |
| Мера | p99 ≤ 300 мс, p50 ≤ 80 мс при 20 rps; при 100 rps p99 ≤ 1 000 мс и 0 ошибок 5xx; доля отказов < 0,1 % |
| Проверка | Нагрузочный тест 30 мин по профилю (20 rps + пик) + `EXPLAIN` ключевых запросов: index scan, без seq scan по `payment`. Владелец: бэкенд `payments` |

### QS-03 — Пропускная способность: импорт банковской выписки

| Поле | Значение |
|---|---|
| Источник | Банк (файл выписки), бухгалтер |
| Стимул | Файл на 100 000 строк; повторная загрузка того же файла; параллельно идёт ручная регистрация платежей |
| Окружение | Батчи по 1 000 строк, staging-таблица, тот же экземпляр PostgreSQL |
| Ответ | `payments.ImportStatement`: адаптер → staging → дедупликация (`batchKey` + `externalRef`) → множественное создание платежей; отчёт об импорте; повтор возвращает тот же `batchId` и не создаёт записей |
| Мера | ≤ 5 мин на 100 000 строк (≥ 333 строк/с); 0 дублей при повторе; 100 % строк отражены в отчёте в одной из категорий: `created`, `matched`, `duplicate`, `rejected`; ручная регистрация платежей не деградирует ниже p99 300 мс |
| Проверка | Интеграционный тест 100 000 строк + повтор; property-тест на дедупликацию; отдельный нагрузочный прогон 1 000 000 строк как проверка 10× (QS-09). Владелец: бэкенд `payments` |

### QS-04 — Корректность под конкуренцией: распределение платежей

| Поле | Значение |
|---|---|
| Источник | Несколько кассиров и вебхуков одновременно |
| Стимул | 50 параллельных вызовов `ledger.AllocatePayment` по одному лицевому счёту и одному счёту-получателю |
| Окружение | PostgreSQL `READ COMMITTED`, блокировка лицевого счёта `SELECT … FOR UPDATE`, повторные попытки клиента при `CONCURRENT_MODIFICATION` |
| Ответ | Сериализация распределений в границах лицевого счёта; проверка «сумма распределений ≤ остаток счёта» и «≤ сумма платежа»; конфликт возвращается как retryable-ошибка, а не приводит к переплате |
| Мера | 0 случаев переплаты сверх суммы счёта; сумма распределений после теста равна сумме принятых платежей (расхождение 0 копеек); 100 % конфликтов возвращают `CONCURRENT_MODIFICATION`; тупиковые блокировки < 0,1 % операций |
| Проверка | Конкурентный интеграционный тест (50 виртуальных клиентов на один счёт) с проверкой инвариантов INV-14/INV-15 после прогона; property-based тест распределения. Владелец: бэкенд `ledger` |

### QS-05 — Безопасность и изоляция тенантов

| Поле | Значение |
|---|---|
| Источник | Злоумышленник с валидной учётной записью тенанта A; ошибочный клиент |
| Стимул | Попытки чтения и записи объектов тенанта B через подмену `tenantId`, перебор идентификаторов, прямые SQL-запросы, чужие файлы выписок |
| Окружение | RLS включён, роль приложения без `BYPASSRLS`, `tenant_id` берётся только из контекста аутентификации |
| Ответ | Проверка прав в прикладном слое + RLS как защита в глубину; для чужих объектов возвращается `NOT_FOUND`, а не `FORBIDDEN`; хранилище файлов ключуется тенантом |
| Мера | 0 успешных операций над данными чужого тенанта в матрице «роль × ресурс × способ»; 0 таблиц без `tenant_id`, кроме глобальных справочников; 100 % HTTP-эндпоинтов покрыты тестом изоляции |
| Проверка | Fitness function: архитектурный тест «каждая таблица с данными тенанта имеет `tenant_id`»; security-набор интеграционных тестов; отдельный прогон от имени роли приложения без прав владельца. Владелец: техлид |

### QS-06 — Прослеживаемость финансовых изменений

| Поле | Значение |
|---|---|
| Источник | Внутренний аудитор, руководитель, регулятор |
| Стимул | Запрос: все изменения финансовых документов за период с основанием и автором |
| Окружение | Любая операция финансового контура, включая импорт, вебхуки и сторно |
| Ответ | `audit_event` пишется в той же транзакции, что и изменение; запись содержит актора, время, тип действия, объект, основание, `correlationId`; аудит append-only (нет UPDATE/DELETE) |
| Мера | 100 % финансовых изменений имеют ровно одну запись аудита (расхождение 0 за период); 0 успешных UPDATE/DELETE по `audit_event`; каждая запись позволяет восстановить цепочку «причина → документ → распределение» |
| Проверка | Трансформационный тест «изменение без аудита невозможно» (ограничение БД/триггер); сверка количества записей в e2e-сценариях; fitness function «нет прямого SQL к `audit_event` вне модуля аудита». Владелец: техлид |

### QS-07 — Восстановление после сбоя

| Поле | Значение |
|---|---|
| Источник | Отказ инфраструктуры, ошибка оператора, повреждение данных |
| Стимул | Потеря основного экземпляра PostgreSQL или повреждение данных в рабочее время |
| Окружение | Прод-подобная среда, непрерывный архив WAL, проверенные резервные копии |
| Ответ | Восстановление на момент времени (PITR) по runbook; outbox и аудит восстанавливаются вместе с БД, поэтому события после точки восстановления доставляются повторно (at-least-once), а не теряются |
| Мера | RPO ≤ 15 мин (окно WAL-архива); RTO ≤ 4 ч до возобновления приёма платежей; успешная репетиция восстановления не реже 1 раза в квартал с зафиксированным временем |
| Проверка | План с владельцем: квартальная репетиция на копии боевых данных с протоколом (дата, RPO, RTO, найденные расхождения). Владелец: DevOps |

### QS-08 — Доступность в рабочие часы

| Поле | Значение |
|---|---|
| Источник | Организация-клиент и её операторы |
| Стимул | Отказ одного процесса (API или воркер), плановый деплой, деградация внешней системы |
| Окружение | Будни 08:00–20:00 МСК; расчётная база для бюджета — 21 рабочий день × 12 ч = 252 ч/мес (оценка календаря, не SLA-факт), 99,5 % даёт не более 1 ч 16 мин недоступности в месяц |
| Ответ | Rolling deploy без простоя, health checks, автоматический перезапуск; при перегрузке деградируют нефинансовые функции (отчёты, уведомления), а регистрация платежей и распределение остаются доступными |
| Мера | ≥ 99,5 % успешных синтетических проверок в окне; error budget ≤ 1,26 ч/мес; восстановление финансовых операций после отказа процесса ≤ 15 мин |
| Проверка | Синтетический мониторинг каждые 60 с + месячный отчёт; chaos-тест «остановить API/воркер» с замером времени восстановления. Владелец: DevOps |

### QS-09 — Эволюционность при 10× росте

| Поле | Значение |
|---|---|
| Источник | Рост бизнеса: больше организаций, домов, лицевых счетов, платежей |
| Стимул | 10× объём данных и 10× объём импорта относительно базового профиля (допущения A-02…A-05 в [scaling.md](scaling.md)) |
| Окружение | Та же архитектура: модульный монолит, одна PostgreSQL, без перехода на микросервисы |
| Ответ | Батчинг, партиционирование по периоду, read models для отчётов, индексы с ведущим `tenant_id`; решения о следующем шаге принимаются по именованным триггерам [scaling.md](scaling.md) §7, а не заранее |
| Мера | Пороги QS-01, QS-02, QS-03 удерживаются на 10× данных (5 000 → 50 000 счетов за прогон; 100 000 → 1 000 000 строк импорта); отсутствует обязательный переход на другой архитектурный стиль; стоимость растёт линейно по ресурсам |
| Проверка | Нагрузочный тест на 10× синтетическом объёме (50 000 счетов, 1 000 000 строк импорта, 200 rps платежей); ревью триггеров пересмотра раз в полгода. Владелец: техлид |

### QS-10 — Сопровождаемость и онбординг

| Поле | Значение |
|---|---|
| Источник | Команда разработки и эксплуатации |
| Стимул | Новый инженер на чистом ноутбуке с доступом к репозиторию |
| Окружение | Документация в git, локальный запуск через контейнеры, детерминированные seed-данные |
| Ответ | README с шагами запуска, `pnpm test` как единая точка проверки, ADR как объяснение решений, генерация диаграмм из текста |
| Мера | ≤ 8 ч от клонирования до зелёного `pnpm test` (медиана по трём последним онбордингам); ≤ 30 мин до работающего локального стека; 0 шагов, требующих устной передачи знаний |
| Проверка | Онбординг-протокол с таймером на каждом новом инженере; CI-проверка «`pnpm test` на чистом клоне»; ежеквартальный прогон онбординга одним из действующих инженеров. Владелец: техлид |

| QS-03 | Интеграционный + property-based | `tests/integration/payments`, `tests/contract/` | бэкенд `payments` |
| QS-04 | Конкурентный интеграционный | `tests/integration/ledger` | бэкенд `ledger` |
| QS-05 | Fitness function + security-набор | `tests/architecture/`, `tests/security/` | техлид |
| QS-06 | Трансформационный тест + fitness function | `tests/integration/audit`, `tests/architecture/` | техлид |
| QS-07 | План + квартальная репетиция | runbook восстановления, протокол репетиции | DevOps |
| QS-08 | Мониторинг + chaos-тест | синтетические проверки, `tests/chaos/` | DevOps |
| QS-09 | Нагрузочный на 10× объёме | `tests/performance/` (профиль 10×) | техлид |
| QS-10 | Протокол онбординга + CI | README, CI, журнал онбордингов | техлид |

Типы проверок намеренно разные: там, где свойство архитектурное (нет циклов,
есть `tenant_id`, нет обхода аудита), проверка дешёвая и исполняется на каждом
коммите; там, где свойство нагрузочное, проверка дорогая и исполняется по
расписанию. Ни один сценарий не остаётся без владельца.

## 4. Конфликты характеристик и выбранное разрешение

Характеристики конфликтуют, и это нормально. Ниже — конфликты, которые реально
возникают в этом домене, и правило, по которому они разрешены.

**Правило приоритета.** Сначала — целостность финансовых данных и изоляция
тенантов (QS-04, QS-05, QS-06), затем производительность приоритета 1
(QS-01…QS-03), затем доступность и восстановление (QS-07, QS-08), затем
эволюционность (QS-09). Сценарий более низкого приоритета уступает, но не
отключается: он деградирует управляемо и видимо.

### Доступность против консистентности (QS-08 vs QS-04, QS-06)

Соблазн — отвечать на запись из кэша или принимать платёж «потом», чтобы не
терять доступность. Это создаёт переплату и дыры в аудите, которые дороже
простоя. Решение: финансовые операции — CP-контур. При недоступности PostgreSQL
регистрация платежей возвращает `EXTERNAL_FAILURE` с `retryable: true`, а не
принимает данные в ненадёжный буфер. Деградируют только чтение отчётов и
уведомления. Компенсация — error budget 1,26 ч/мес и RTO ≤ 15 мин на
восстановление процесса (QS-08).

### Скорость начисления против аудита и неизменяемости (QS-01 vs QS-06, ADR-0007)

Аудит и неизменяемость требуют дополнительных записей на каждое начисление,
что замедляет массовый прогон. Решение: аудит пишется в той же транзакции, но
батчем — один INSERT на пачку начислений, без по-строчных round-trip; батч 500
счетов выбран как компромисс между временем блокировки и числом коммитов;
прогресс фиксируется в `period_run`, поэтому сбой не откатывает весь прогон
(QS-01, QS-06). Снижать полноту аудита ради скорости запрещено.

### Пропускная способность импорта против конкурентной корректности (QS-03 vs QS-04)

Импорт 100 000 строк не должен конкурировать за блокировки лицевых счетов с
ручными распределениями. Решение: импорт создаёт только платежи (быстрый
множественный INSERT после дедупликации), а авто-распределение выполняется
после коммита батча, порциями и с сериализацией по лицевому счёту. Пользователь
видит платёж сразу, распределение — в течение секунд; корректность (INV-14,
INV-15) не зависит от порядка.

### Изоляция против эволюционности и стоимости (QS-05 vs QS-09)

RLS и ведущий `tenant_id` в каждом индексе стоят производительности и места.
Решение: оставляем RLS (защита в глубину) и составные индексы с `tenant_id`
первым столбцом; накладные расходы измеряются в нагрузочном тесте и не превышают 10 % p99
(QS-02). Отключать RLS ради скорости запрещено; при превышении бюджета
пересматривается схема индексов, а не политика изоляции. Выделение тенанта в
отдельную БД — триггер из ADR-0006, а не оптимизация «на всякий случай».

### Эволюционность против простоты (QS-09 vs QS-10)

Преждевременное партиционирование и вынос сервисов усложняют онбординг и
эксплуатацию. Решение: базовая схема остаётся простой, а переход к
партиционированию и read models запускается по именованным триггерам
([scaling.md](scaling.md) §7) с замером, а не по ожиданию роста. Это сохраняет
QS-10 и делает QS-09 проверяемым: у каждого триггера есть порог и владелец.
