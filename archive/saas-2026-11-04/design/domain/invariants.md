# Инварианты предметной области

Нумерация `INV-01 … INV-20` — **контракт**. На неё ссылаются
[core-modules.md](../architecture/core-modules.md), [entities.md](./entities.md) и
[model.dbml](./model.dbml). Менять порядок или переиспользовать номера нельзя:
сломается трассировка требований.

Ниже для каждого инварианта зафиксированы формулировка, обоснование, слои
принуждения и **предлагаемая исполняемая проверка**. Проверки станут частью
набора `pnpm test` в рамках IP-11; до этого они специфицированы, но не
реализованы — это осознанное состояние design-only репозитория.

## 0. Как читать принуждение

| Слой | Что это | Пример |
|---|---|---|
| **БД-ограничение** | `NOT NULL`, `CHECK`, `UNIQUE`, внешний ключ, exclusion-ограничение, триггер, права | `UNIQUE (account_id, period)` |
| **Доменный сервис** | Правило в коде модуля: value object, фабрика, метод агрегата | `Money.add` бросает `CURRENCY_MISMATCH` |
| **Транзакция приложения** | Блокировка строк, порядок операций, одна транзакция, outbox | `SELECT … FOR UPDATE` при распределении |
| **Архитектурный тест** | Fitness function по миграциям и импортам | «в каждой финансовой таблице есть `tenant_id NOT NULL`» |

Инвариант считается обеспеченным, только если у него есть **хотя бы один
автоматический** слой принуждения (БД или транзакция/домен с тестом). Комментарий
в коде инвариантом не является.

Соглашения проверок:

- SQL-проверки выполняются на пустой и на заполненной базе; ожидаемый результат —
  **0 строк** нарушений (если не указано иное).
- Проверки «операция отклонена» выполняются как интеграционные тесты
  `tests/integration/invariants/*.spec.ts` и ожидают доменный код ошибки из
  [core-modules.md](../architecture/core-modules.md), §6.
- Для конкурентных инвариантов (INV-06, INV-14, INV-15, INV-20) проверка запускает
  две транзакции параллельно и утверждает, что превышение невозможно ни при каком
  порядке.

## INV-01. Деньги — только целые минорные единицы одной валюты

**Формулировка.** Все денежные суммы хранятся, передаются и вычисляются как целые
минорные единицы (`bigint`, копейки). Плавающая точка и `numeric` для денежных
сумм запрещены. В пределах одного документа и его строк валюта одна; сложение и
вычитание сумм с разными валютами отклоняется с `CURRENCY_MISMATCH`. Цена за
единицу услуги (`tariff.unit_price`) — ставка, а не сумма, поэтому хранится
`numeric(14,4)`; итог начисления округляется до копейки детерминированно
(`ROUND_HALF_UP`).

**Обоснование.** C-02 и денежная природа продукта: ошибки округления в
`float`/`double` накапливаются и разрушают сверку с банком. Одна валюта в документе
исключает бессмысленное сложение и делает отчёты сравнимыми. Допущение DM-A-01:
MVP работает в одной валюте `RUB`, поле валюты зарезервировано под OQ-04.

**Принуждение.**

- **БД-ограничение.** Все `*_minor` — `bigint NOT NULL`; `currency char(3) NOT NULL`;
  `CHECK (amount_minor >= 0)` или `> 0` по смыслу колонки. Для запрета `numeric`
  на денежных колонках — проверка в архитектурном тесте миграций.
- **Доменный сервис.** Value object `Money { amountMinor: bigint; currency }`;
  `add`/`subtract` требуют совпадения валюты, иначе `CURRENCY_MISMATCH`; округление
  ставки выполняет только `TariffCalculator`.
- **Транзакция приложения.** `IssueInvoices`, `RegisterPayment`, `AllocatePayment`
  проверяют валюту счёта, платежа и распределения до записи; смешивание валют
  прерывает транзакцию.
- **Архитектурный тест.** Сканирует SQL-миграции: ни одна колонка с суффиксом
  `_minor` не имеет типа `real`, `double precision`, `float`, `numeric`.

**Исполняемая проверка.**

```sql
-- Ожидается 0 строк: денежные колонки обязаны быть bigint.
SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public'
  AND column_name LIKE '%\_minor' ESCAPE '\'
  AND data_type <> 'bigint';
```

```ts
// Ожидается CURRENCY_MISMATCH, второго эффекта нет.
expect(() => Money.of(10_000, 'RUB').add(Money.of(10_000, 'USD')))
  .toThrowError('CURRENCY_MISMATCH');
```

## INV-02. Период — только `YYYY-MM`

**Формулировка.** Расчётный период — строка из семи символов вида `YYYY-MM`
(год-месяц, месяц 01–12). Период хранится в `period_run.period`, `accrual.period`,
`invoice.period`; произвольные даты и интервалы вместо периода недопустимы.
Значение `Period` — value object с операциями `next()`, `previous()` и
лексикографическим сравнением.

**Обоснование.** C-03 и FR-04/FR-05: начисления и счета привязаны к расчётному
месяцу, а не к дате. Строгий формат позволяет сравнивать периоды без парсинга,
индексировать и однозначно сопоставлять прогон, начисления и счета.

**Принуждение.**

- **БД-ограничение.** `period varchar(7) NOT NULL` +
  `CHECK (period ~ '^[0-9]{4}-(0[1-9]|1[0-2])$')` на `period_run`, `accrual`,
  `invoice`. Индекс по `(tenant_id, period)`.
- **Доменный сервис.** `Period.parse` отклоняет иные формы (`VALIDATION_FAILED`);
  сравнение и арифметика — только через value object.
- **Транзакция приложения.** `RunAccruals` и `IssueInvoices` принимают `Period`,
  а не строку от клиента; приведение — на границе HTTP-адаптера.
- **Архитектурный тест.** В миграциях у каждой колонки `period` есть `CHECK` с
  регулярным выражением; в домене нет `new Date(period)` как источника периода.

**Исполняемая проверка.**

```sql
-- Ожидается 0 строк (при наличии CHECK их быть не может).
SELECT 'accrual' AS t, id FROM accrual
WHERE period !~ '^[0-9]{4}-(0[1-9]|1[0-2])$'
UNION ALL
SELECT 'invoice', id FROM invoice
WHERE period !~ '^[0-9]{4}-(0[1-9]|1[0-2])$';

-- Негативный тест: INSERT с period='2026-13' обязан упасть на CHECK.
```

## INV-03. Начисление принадлежит лицевому счёту, периоду и услуге, сумма > 0

**Формулировка.** Каждое начисление обязательно ссылается на существующие
`account`, `period` и `service`, а его сумма строго больше нуля
(`amount_minor > 0`). Начисление не может существовать без любой из этих трёх
координат и не может быть нулевым или отрицательным. Сторно не нарушает правило:
сторно-запись тоже имеет положительную сумму, а знак задаётся `kind = 'reversal'`.

**Обоснование.** Начисление — документ-основание счёта. Без счёта, периода или
услуги его нельзя ни выставить, ни проверить, ни отчитаться. Нулевое начисление
засоряет документы и ломает проверку INV-05; отрицательное — маскирует сторно под
обычную запись и обходит INV-19.

**Принуждение.**

- **БД-ограничение.** `account_id`, `period`, `service_id`, `amount_minor` —
  `NOT NULL`; `CHECK (amount_minor > 0)`; составные внешние ключи
  `(tenant_id, account_id)`, `(tenant_id, service_id)`, `(tenant_id, tariff_id)`
  гарантируют существование и единый тенант.
- **Доменный сервис.** Фабрика `Accrual.create` требует все три координаты и
  положительную сумму; `TariffCalculator` не возвращает 0.
- **Транзакция приложения.** `RunAccruals` пишет черновики в транзакции прогона;
  начисление без подобранного тарифа не создаётся (`TARIFF_MISSING`).
- **Архитектурный тест.** Проверяет, что колонки `account_id`, `period`,
  `service_id`, `amount_minor` в миграции `NOT NULL` и что `CHECK` присутствует.

**Исполняемая проверка.**

```sql
-- Ожидается 0 строк.
SELECT id
FROM accrual
WHERE account_id IS NULL
   OR service_id IS NULL
   OR period IS NULL
   OR amount_minor <= 0;

-- Негативный тест: INSERT accrual с amount_minor = 0 отклоняется CHECK.
```

## INV-04. Тариф версионирован: на дату начисления применим ровно один тариф

**Формулировка.** Для услуги на дату начисления существует ровно одна версия
тарифа, в интервал действия которой `[valid_from, valid_to)` попадает эта дата
(`valid_to = NULL` — бессрочно). Интервалы действия тарифов одной услуги не
пересекаются. Начисление хранит `tariff_id` фактически применённой версии.
Допущение DM-A-02: датой начисления считается первое число расчётного периода.

**Обоснование.** FR-03 и воспроизводимость расчёта: если тариф можно переписать
задним числом, уже выставленные счета перестают объясняться. Ровно один тариф
исключает неоднозначность выбора и скрытые пересчёты; исключающее ограничение
делает пересечение версий физически невозможным.

**Принуждение.**

- **БД-ограничение.** `EXCLUDE USING gist (service_id WITH =, daterange(valid_from,
  valid_to) WITH &&)` (требуется `btree_gist`); `UNIQUE (service_id, valid_from)`;
  `CHECK (valid_to IS NULL OR valid_to > valid_from)`; внешний ключ
  `accrual.tariff_id → tariff.id`.
- **Доменный сервис.** `TariffSelector.pick(serviceId, date)` возвращает ровно одну
  версию; ноль версий — `TARIFF_MISSING`, больше одной — ошибка конфигурации.
- **Транзакция приложения.** `RunAccruals` разрешает тариф один раз на
  (услуга, дата) и записывает `tariff_id` в начисление; смена тарифа — только
  вставка новой версии.
- **Архитектурный тест.** Проверяет наличие exclusion-ограничения и запрет
  `UPDATE tariff SET unit_price` для уже начавшей действовать версии.

**Исполняемая проверка.**

```sql
-- Пересечение интервалов действия тарифов одной услуги. Ожидается 0 строк.
SELECT a.id AS tariff_a, b.id AS tariff_b
FROM tariff a
JOIN tariff b
  ON a.service_id = b.service_id
 AND a.id < b.id
WHERE daterange(a.valid_from, a.valid_to, '[)')
   && daterange(b.valid_from, b.valid_to, '[)');

-- Начисление использует тариф, не покрывающий начало периода. Ожидается 0 строк.
SELECT ac.id
FROM accrual ac
JOIN tariff t ON t.id = ac.tariff_id
WHERE to_date(ac.period || '-01', 'YYYY-MM-DD') < t.valid_from
   OR (t.valid_to IS NOT NULL
       AND to_date(ac.period || '-01', 'YYYY-MM-DD') >= t.valid_to);
```

## INV-05. Сумма строк счёта равна сумме счёта

**Формулировка.** Для каждого счёта в любом состоянии сумма `invoice_line.amount_minor`
равна `invoice.total_minor`. Строки не могут быть пустыми при положительной сумме
счёта; сумма каждой строки положительна.

**Обоснование.** Счёт — документ, который видит плательщик и по которому
распределяются деньги. Расхождение строк и итога означает, что плательщик не может
проверить начисление, а отчётность теряет сходимость. Проверка должна срабатывать
до выставления, а после выставления уже нечего проверять из-за INV-12.

**Принуждение.**

- **БД-ограничение.** Отложенный (`DEFERRABLE INITIALLY DEFERRED`) constraint-триггер
  на `invoice_line` и `invoice`: при коммите сумма строк обязана совпасть с
  `total_minor`; `CHECK (invoice.total_minor > 0)`.
- **Доменный сервис.** `Invoice.issue()` формирует `total_minor` как сумму строк;
  ручное расхождение невозможно через API агрегата.
- **Транзакция приложения.** `IssueInvoices` пишет счёт и все строки одной
  транзакцией; изменение `total_minor` после выставления запрещено INV-12.
- **Архитектурный тест.** Запрещает прямые `INSERT/UPDATE invoice_line` вне
  репозитория `invoicing`; проверяет наличие отложенного триггера.

**Исполняемая проверка.**

```sql
-- Ожидается 0 строк.
SELECT i.id, i.total_minor, coalesce(sum(l.amount_minor), 0) AS line_sum
FROM invoice i
LEFT JOIN invoice_line l ON l.invoice_id = i.id
GROUP BY i.id, i.total_minor
HAVING coalesce(sum(l.amount_minor), 0) <> i.total_minor;
```

## INV-06. Сумма распределений счёта равна `invoice.paid_minor`

**Формулировка.** Для каждого счёта `invoice.paid_minor` равно сумме всех
распределений этого счёта. `paid_minor` не может быть отрицательным или превышать
`total_minor`. Состояние оплаты (`partially_paid`, `paid`, `overdue`) выводится из
`paid_minor`, `total_minor` и `due_on`, а не задаётся вручную.

**Обоснование.** `paid_minor` — денормализация ради быстрых отчётов и проверки
остатка. Она обязана быть производной от распределений, иначе остаток счёта
разойдётся с фактическими деньгами, а INV-14 потеряет опору.

**Принуждение.**

- **БД-ограничение.** `CHECK (paid_minor >= 0 AND paid_minor <= total_minor)`.
- **Доменный сервис.** `Invoice.applySettlement(delta)` меняет `paid_minor` только
  вместе с состоянием и проверяет границы.
- **Транзакция приложения.** `AllocatePayment` блокирует счёт `FOR UPDATE`,
  вставляет/увеличивает распределение и вызывает `invoicing.ApplySettlement` в той
  же транзакции ([core-modules.md](../architecture/core-modules.md), §7).
- **Архитектурный тест.** `ApplySettlement` вызывается только из `ledger`;
  прямой `UPDATE invoice SET paid_minor` запрещён.

**Исполняемая проверка.**

```sql
-- Ожидается 0 строк.
SELECT i.id, i.paid_minor, coalesce(sum(a.amount_minor), 0) AS allocated
FROM invoice i
LEFT JOIN allocation a ON a.invoice_id = i.id
GROUP BY i.id, i.paid_minor
HAVING coalesce(sum(a.amount_minor), 0) <> i.paid_minor;
```

## INV-07. Сумма распределений платежа ≤ суммы платежа; остаток — аванс

**Формулировка.** Для каждого платежа сумма его распределений не превышает
`payment.amount_minor`. Поле `payment.allocated_minor` равно сумме распределений.
Разница `amount_minor − allocated_minor` — аванс (кредитный остаток) на лицевом
счёте; она может быть распределена позже, но не может стать отрицательной.

**Обоснование.** FR-09: частичная оплата и переплата — штатные ситуации.
Ограничение защищает от распределения денег, которых нет, и делает аванс явным
финансовым объектом, а не «отрицательным долгом». Остаток используется в INV-20.

**Принуждение.**

- **БД-ограничение.** `CHECK (allocated_minor >= 0 AND allocated_minor <= amount_minor)`;
  `CHECK (amount_minor > 0)`.
- **Доменный сервис.** `Payment.remaining()`; `AllocatePayment` проверяет
  `delta <= payment.remaining()` иначе `ALLOCATION_EXCEEDS_PAYMENT`.
- **Транзакция приложения.** Блокировка платежа `FOR UPDATE` на время распределения;
  обновление `allocated_minor` и вставка распределения — атомарно.
- **Архитектурный тест.** Запрещает прямую запись `allocated_minor` вне `ledger`.

**Исполняемая проверка.**

```sql
-- Ожидается 0 строк.
SELECT p.id, p.amount_minor, p.allocated_minor,
       coalesce(sum(a.amount_minor), 0) AS allocated
FROM payment p
LEFT JOIN allocation a ON a.payment_id = p.id
GROUP BY p.id, p.amount_minor, p.allocated_minor
HAVING coalesce(sum(a.amount_minor), 0) <> p.allocated_minor
    OR p.allocated_minor > p.amount_minor;
```

## INV-08. Лицевой счёт нельзя закрыть при ненулевом балансе

**Формулировка.** Переход лицевого счёта в `closed` разрешён только тогда, когда
`account_balance.balance_minor = 0` и `account_balance.credit_balance_minor = 0`.
Ненулевой долг или ненулевой аванс блокируют закрытие с кодом `ACCOUNT_HAS_BALANCE`.
Закрытие необратимо.

**Обоснование.** Закрытый счёт не принимает новые начисления и распределения.
Если закрыть его с долгом, задолженность «повиснет» вне учёта; если с авансом —
деньги плательщика окажутся недоступны для возврата или распределения. Требование
закрытия — явная операция (`CloseAccount`), а не следствие отсутствия активности.

**Принуждение.**

- **БД-ограничение.** Триггер `BEFORE UPDATE OF status ON account`: при
  `NEW.status = 'closed'` читает `account_balance` и поднимает исключение, если
  баланс или аванс не равны нулю. Дополнительно `CHECK` на `account_balance`.
- **Доменный сервис.** `CloseAccount` блокирует счёт и баланс, проверяет оба
  значения, иначе `ACCOUNT_HAS_BALANCE`.
- **Транзакция приложения.** Проверка и смена статуса — в одной транзакции;
  параллельное начисление не может проскочить между проверкой и закрытием.
- **Архитектурный тест.** Проверяет, что `status` меняется только через
  `CloseAccount`/`SuspendAccount`, а не прямым `UPDATE`.

**Исполняемая проверка.**

```sql
-- Ожидается 0 строк.
SELECT a.id
FROM account a
JOIN account_balance b ON b.account_id = a.id
WHERE a.status = 'closed'
  AND (b.balance_minor <> 0 OR b.credit_balance_minor <> 0);

-- Интеграционный тест: CloseAccount при balance_minor = 1 -> ACCOUNT_HAS_BALANCE.
```

## INV-09. Начисления проведённого периода не перезаписываются

**Формулировка.** Проведённое начисление (`status = 'posted'`) неизменяемо:
его сумма, счёт, период, услуга и тариф не редактируются, запись не удаляется.
Исправление выполняется только двумя операциями: сторно-запись
(`kind = 'reversal'`, `reversal_of_id`) и новое регулярное начисление. Повторная
проводка уже проведённого периода запрещена (`PERIOD_CLOSED`).

**Обоснование.** Начисление — документ, на который уже могли выставить счёт и
распределить деньги. Перезапись задним числом делает невозможной сверку и аудит.
Сторно сохраняет исходную запись и создаёт объяснимую обратную, поэтому история
остаётся полной (FR-10, INV-19).

**Принуждение.**

- **БД-ограничение.** Триггер `BEFORE UPDATE OR DELETE ON accrual`: при
  `OLD.status = 'posted'` разрешён только переход `posted → reversed` без изменения
  финансовых полей; `DELETE` запрещён. `period_run.status = 'posted'` защищён
  триггером от повторной проводки.
- **Доменный сервис.** `ReverseAccrual` создаёт сторно и переводит оригинал в
  `reversed`; сеттеров суммы у проведённого начисления нет.
- **Транзакция приложения.** `RunAccruals` проверяет `period_run` под блокировкой;
  повтор с тем же `idempotency_key` возвращает существующий прогон.
- **Архитектурный тест.** Ищет в коде `UPDATE accrual SET amount_minor` и
  `DELETE FROM accrual`; оба запрещены.

**Исполняемая проверка.**

```sql
-- Каждое отменённое начисление имеет ровно одну сторно-запись. Ожидается 0 строк.
SELECT a.id
FROM accrual a
WHERE a.status = 'reversed'
  AND NOT EXISTS (
    SELECT 1 FROM accrual r
    WHERE r.reversal_of_id = a.id AND r.kind = 'reversal'
  );

-- Негативный тест: UPDATE суммы проведённого начисления обязан упасть на триггере.
```

## INV-10. Не более одного действующего счёта на пару «лицевой счёт + период»

**Формулировка.** Для одной пары `(account_id, period)` существует не более одного
счёта, не находящегося в состоянии `void`. Повторное выставление при наличии
действующего счёта отклоняется с `INVOICE_ALREADY_ISSUED`; уникальность
обеспечивается ограничением БД, а не только проверкой в коде. Аннулированный счёт
остаётся в истории и не блокирует выставление корректного счёта за тот же период
(FR-10, US-07).

**Обоснование.** Два счёта за один месяц на один лицевой счёт означают двойное
требование к плательщику и невозможность однозначно распределить платёж FIFO.
Уникальность пары — самый дешёвый и надёжный способ не допустить дубль при
повторном запуске выставления и при гонке двух операторов.

**Принуждение.**

- **БД-ограничение.** Частичный уникальный индекс
  `UNIQUE (tenant_id, account_id, period) WHERE status <> 'void'` на `invoice`
  (в модели — `uq_invoice_account_period_active`).
- **Доменный сервис.** `IssueInvoices` ловит нарушение уникальности и возвращает
  `INVOICE_ALREADY_ISSUED`; предварительная проверка — только для читаемого текста
  ошибки.
- **Транзакция приложения.** Выставление батчами по 500 счетов; каждая порция —
  отдельная транзакция, прогресс — в `period_run`.
- **Архитектурный тест.** Проверяет наличие уникального индекса в миграции.

**Исполняемая проверка.**

```sql
-- Ожидается 0 строк: у пары не может быть двух действующих счетов.
SELECT account_id, period, count(*)
FROM invoice
WHERE status <> 'void'
GROUP BY account_id, period
HAVING count(*) > 1;

-- Негативный тест: второй действующий INSERT с той же парой -> SQLSTATE 23505.
-- Позитивный тест: void-счёт + новый действующий счёт за тот же период -> OK.
```

## INV-11. Счёт можно аннулировать только при отсутствии распределений

**Формулировка.** Переход счёта в `void` разрешён из состояний `draft`, `issued` и `overdue`
(но не из `partially_paid`, `paid`, `closed`) и только если у счёта нет ни одного распределения и
`paid_minor = 0`. Аннулирование счёта с распределениями запрещено
(`INVOICE_IMMUTABLE`): сначала нужно сторнировать начисления и вернуть деньги, но
не «отменять» уже оплаченный документ.

**Обоснование.** Аннулирование — не удаление (FR-10). Если на счёт уже разнесены
деньги, `void` сделал бы распределения висящими и сломал бы INV-06. Запрет
заставляет использовать финансово корректный путь: сторно + новое начисление.

**Принуждение.**

- **БД-ограничение.** Триггер `BEFORE UPDATE OF status ON invoice`: при
  `NEW.status = 'void'` проверяет отсутствие строк в `allocation` по этому счёту и
  `paid_minor = 0`.
- **Доменный сервис.** `VoidInvoice` проверяет состояние, наличие распределений и
  причину; иначе `INVOICE_IMMUTABLE`.
- **Транзакция приложения.** Проверка и смена статуса — под блокировкой счёта;
  параллельное распределение не может появиться после проверки.
- **Архитектурный тест.** `void` меняется только через `VoidInvoice`.

**Исполняемая проверка.**

```sql
-- Ожидается 0 строк: аннулированный счёт не имеет распределений.
SELECT i.id
FROM invoice i
JOIN allocation a ON a.invoice_id = i.id
WHERE i.status = 'void';

-- Интеграционный тест: VoidInvoice после AllocatePayment -> INVOICE_IMMUTABLE.
```

## INV-12. Выставленный счёт неизменяем

**Формулировка.** После перехода в `issued` у счёта нельзя менять содержимое:
`account_id`, `period`, `total_minor`, `currency`, `due_on` и строки
`invoice_line`. Разрешены только служебные изменения: `paid_minor`, состояние,
`closed_at`, `voided_at`/`void_reason`, `version`, `updated_at` — и только через
операции `ApplySettlement`, `VoidInvoice`, закрытия периода.

**Обоснование.** Счёт — юридически значимый документ, который плательщик уже
получил. Любая правка суммы или срока после выставления делает невозможным
доказывание и сверку. Исправление — только сторно начисления и новый документ
(FR-10, INV-09).

**Принуждение.**

- **БД-ограничение.** Триггер `BEFORE UPDATE ON invoice`: при `OLD.status <> 'draft'`
  сравнивает защищаемые поля и поднимает исключение при любом расхождении, кроме
  разрешённого набора. Триггер на `invoice_line` запрещает `UPDATE/DELETE` строк
  выставленного счёта.
- **Доменный сервис.** У `Invoice` нет публичных сеттеров содержимого после
  выставления; доступны только методы жизненного цикла.
- **Транзакция приложения.** `ApplySettlement` и `VoidInvoice` работают под
  блокировкой и пишут аудит (INV-18).
- **Архитектурный тест.** Запрещает прямые `UPDATE invoice SET total_minor` и
  `DELETE FROM invoice_line` вне `invoicing`.

**Исполняемая проверка.**

```ts
// Каждый вызов обязан завершиться INVOICE_IMMUTABLE и не изменить строку.
await expect(invoiceRepo.updateContent(issued.id, { totalMinor: 1 }))
  .rejects.toThrowError('INVOICE_IMMUTABLE');
await expect(invoiceLineRepo.delete(issuedLine.id))
  .rejects.toThrowError('INVOICE_IMMUTABLE');
```

## INV-13. Идемпотентность платежа по `(tenant_id, idempotency_key)`

**Формулировка.** Пара `(tenant_id, idempotency_key)` уникальна. Повторный вызов
регистрации с тем же ключом не создаёт новый платёж, а возвращает существующий.
Повтор с тем же ключом и другим содержимым (сумма, счёт, дата) отклоняется как
`CONFLICT`/`DUPLICATE_IDEMPOTENCY_KEY` и не меняет существующий платёж. Ключ
уникален в границах организации, а не глобально.

**Обоснование.** C-05 и FR-06: банк или эквайринг может доставить вебхук дважды,
оператор — нажать «сохранить» дважды. Идемпотентность на уровне БД защищает от
дублей даже при гонке двух запросов, где предварительная проверка «нет ли такого
ключа» бесполезна.

**Принуждение.**

- **БД-ограничение.** `UNIQUE (tenant_id, idempotency_key)` на `payment`.
- **Доменный сервис.** `RegisterPayment` при `SQLSTATE 23505` читает существующий
  платёж и сверяет содержимое; полное совпадение — успех, расхождение — конфликт.
- **Транзакция приложения.** Вставка платежа + аудит + outbox — одна транзакция
  ([core-modules.md](../architecture/core-modules.md), §7).
- **Архитектурный тест.** Проверяет наличие уникального индекса и отсутствие
  «сначала SELECT, потом INSERT» без обработки конфликта.

**Исполняемая проверка.**

```ts
const [a, b] = await Promise.all([
  registerPayment({ idempotencyKey: 'k-1', amountMinor: 10_000 }),
  registerPayment({ idempotencyKey: 'k-1', amountMinor: 10_000 }),
]);
expect(a.id).toBe(b.id); // один платёж, не два

await expect(registerPayment({ idempotencyKey: 'k-1', amountMinor: 20_000 }))
  .rejects.toThrowError('DUPLICATE_IDEMPOTENCY_KEY');
```

## INV-14. Распределение ≤ остатка счёта

**Формулировка.** Сумма, относимая на счёт, не превышает `total_minor − paid_minor`
на момент операции. Превышение отклоняется с `ALLOCATION_EXCEEDS_INVOICE`.
Кумулятивно сумма всех распределений счёта никогда не превышает суммы счёта.

**Обоснование.** QS-04: параллельные платежи не должны создавать переплату сверх
суммы счёта. Проверка «прочитать остаток, потом записать» без блокировки
недостаточна — две транзакции прочитают одинаковый остаток. Поэтому остаток
проверяется под блокировкой счёта, а итог дополнительно защищён CHECK-ограничением
INV-06.

**Принуждение.**

- **БД-ограничение.** `CHECK (paid_minor <= total_minor)` на `invoice`.
- **Доменный сервис.** `AllocatePayment` вычисляет остаток и отклоняет превышение.
- **Транзакция приложения.** `SELECT … FOR UPDATE` по счёту; проверка и запись в
  одной транзакции; при конфликте — `CONCURRENT_MODIFICATION` (retryable).
- **Архитектурный тест.** Запрещает чтение остатка без блокировки в `ledger`.

**Исполняемая проверка.**

```ts
// Две параллельные попытки распределить по 60 000 на счёт 100 000.
// Ровно одна успешна, вторая — CONCURRENT_MODIFICATION/ALLOCATION_EXCEEDS_INVOICE.
const results = await Promise.allSettled([allocate(60_000), allocate(60_000)]);
expect(results.filter(r => r.status === 'fulfilled')).toHaveLength(1);
expect(await invoiceRepo.get(id)).toMatchObject({ paidMinor: 60_000 });
```

## INV-15. Распределение ≤ нераспределённого остатка платежа

**Формулировка.** Сумма, относимая с платежа, не превышает
`payment.amount_minor − payment.allocated_minor` на момент операции. Превышение
отклоняется с `ALLOCATION_EXCEEDS_PAYMENT`. Остаток после распределений остаётся
авансом и не может быть отрицательным.

**Обоснование.** Нельзя разнести денег больше, чем поступило. Это симметрично
INV-14, но защищает другую сторону: даже если счёт ещё не оплачен, платёж не может
«подарить» лишнее. Аванс — законный остаток, отрицательный аванс — ошибка учёта.

**Принуждение.**

- **БД-ограничение.** `CHECK (allocated_minor <= amount_minor)` на `payment`.
- **Доменный сервис.** `AllocatePayment` проверяет остаток платежа.
- **Транзакция приложения.** Блокировка платежа `FOR UPDATE`; конкурентные вызовы
  сериализуются.
- **Архитектурный тест.** Запрещает запись `allocated_minor` вне `ledger`.

**Исполняемая проверка.**

```sql
-- Ожидается 0 строк.
SELECT p.id
FROM payment p
WHERE p.allocated_minor < 0
   OR p.allocated_minor > p.amount_minor;
```

## INV-16. Платёж, начисление, счёт и распределение всегда принадлежат одной организации

**Формулировка.** Любая связь между финансовыми документами не пересекает границу
тенанта: `invoice.account`, `accrual.account`, `payment.account`,
`allocation.payment`, `allocation.invoice`, строки счёта и позиции сверки ссылаются
только на объекты того же `tenant_id`. Объект чужого тенанта не виден и не может
быть указан внешним ключом.

**Обоснование.** C-01 и QS-05: изоляция организаций — обязательное свойство с
первого дня. Проверка «в приложении» недостаточна: ошибка в одном запросе или
ручной SQL может связать документы разных организаций. Составные внешние ключи
делают это невозможным на уровне БД, RLS добавляет защиту в глубину.

**Принуждение.**

- **БД-ограничение.** Составные внешние ключи
  `(tenant_id, account_id) → account(tenant_id, id)`,
  `(tenant_id, payment_id) → payment(tenant_id, id)`,
  `(tenant_id, invoice_id) → invoice(tenant_id, id)` и аналогичные; у родителей —
  `UNIQUE (tenant_id, id)`. RLS по `tenant_id` (архитектура, §9).
- **Доменный сервис.** Репозитории подставляют `tenant_id` из контекста запроса;
  явная передача чужого идентификатора — `TENANT_MISMATCH`.
- **Транзакция приложения.** Все чтения и записи финансового контура выполняются
  в контексте тенанта; межтенантные операции не предусмотрены.
- **Архитектурный тест.** В каждой финансовой таблице есть `tenant_id NOT NULL`;
  нет прямых SQL-запросов к чужим таблицам; нет запросов без фильтра по `tenant_id`.

**Исполняемая проверка.**

```sql
-- Ожидается 0 строк по каждой связи.
SELECT i.id
FROM invoice i
JOIN account a ON a.id = i.account_id
WHERE a.tenant_id <> i.tenant_id;

SELECT al.id
FROM allocation al
JOIN payment p ON p.id = al.payment_id
JOIN invoice i ON i.id = al.invoice_id
WHERE p.tenant_id <> al.tenant_id
   OR i.tenant_id <> al.tenant_id;

-- Негативный тест: INSERT invoice с account чужого тенанта -> нарушение FK.
```

## INV-17. Сумма распределения > 0; исправления — отдельные операции

**Формулировка.** Каждое распределение имеет строго положительную сумму. Отрицательных
распределений и распределений с нулевой суммой не существует. Исправление
ошибочного начисления или счёта выполняется сторно-операцией с отдельной записью,
а не отрицательным распределением или «тихим» уменьшением суммы.

**Обоснование.** Отрицательное распределение маскирует исправление под обычную
операцию и ломает идемпотентность/аудит: по данным нельзя отличить возврат от
ошибки ввода. Положительные суммы и явное сторно сохраняют историю читаемой
(FR-10, INV-18).

**Принуждение.**

- **БД-ограничение.** `CHECK (amount_minor > 0)` на `allocation`.
- **Доменный сервис.** `AllocatePayment` принимает только `delta > 0`; уменьшение
  отклоняется, исправление — через сторно вышестоящего документа.
- **Транзакция приложения.** Сторно и новое распределение — разные транзакции,
  каждая с аудит-записью.
- **Архитектурный тест.** В коде нет `amount_minor: -` для `allocation`;
  репозиторий не принимает отрицательную дельту.

**Исполняемая проверка.**

```sql
-- Ожидается 0 строк.
SELECT id FROM allocation WHERE amount_minor <= 0;

-- Негативный тест: INSERT allocation с amount_minor = -100 отклоняется CHECK.
```

## INV-18. Каждое изменение финансового документа порождает неизменяемый `audit_event`

**Формулировка.** Любое создание, изменение состояния или содержимого финансового
документа (`accrual`, `invoice`, `invoice_line`, `payment`, `allocation`,
`account_balance`, `tariff`, `account` в части финансовых полей) порождает
аудит-запись в той же транзакции. Запись содержит автора (пользователь или
система), время, действие, сущность, причину и снимки «до»/«после». `audit_event`
не обновляется и не удаляется.

**Обоснование.** FR-13 и QS-06: 100 % финансовых изменений должны иметь запись
аудита. Без этого невозможно разобрать спор с плательщиком и доказать, кто и
почему изменил сумму. Запись в той же транзакции гарантирует: нет изменения без
аудита и нет аудита без изменения.

**Принуждение.**

- **БД-ограничение.** `AFTER INSERT OR UPDATE OR DELETE`-триггер на финансовых
  таблицах пишет `audit_event`, используя контекст транзакции
  (`app.actor_kind`, `app.actor_user_id`, `app.action`, `app.reason`,
  `app.correlation_id`); триггер на `audit_event` запрещает `UPDATE/DELETE`;
  права `REVOKE UPDATE, DELETE` на таблицу.
- **Доменный сервис.** Use case передаёт действие и причину; финансовый метод без
  контекста аудита не выполняется.
- **Транзакция приложения.** `SET LOCAL app.*` выставляется в начале транзакции;
  коммит невозможен без срабатывания триггера.
- **Архитектурный тест.** Проверяет наличие триггеров на всех финансовых таблицах
  и отсутствие `UPDATE/DELETE audit_event` в коде.

**Исполняемая проверка.**

```ts
// Для каждого use case: число изменений = числу audit_event с тем же correlation_id.
const before = await auditRepo.count({ correlationId });
await issueInvoices({ correlationId, actorId, reason: 'плановое выставление' });
const events = await auditRepo.find({ correlationId });
expect(events).toHaveLength(1);
expect(events[0]).toMatchObject({
  entityType: 'invoice', action: 'ISSUE', actorUserId: actorId,
});
await expect(auditRepo.delete(events[0].id)).rejects.toThrow(); // append-only
```

## INV-19. Сторно ссылается на оригинал; двойное сторно запрещено

**Формулировка.** Сторно-запись начисления всегда ссылается на исходное начисление
(`reversal_of_id`), имеет `kind = 'reversal'` и положительную сумму, равную сумме
оригинала. Для одного оригинала допустима ровно одна сторно-запись. Оригинал
переходит в `reversed`, но не удаляется и не редактируется. Для счёта и платежа
аналог сторно — терминальное состояние `void`/`reversed`, также однократное.

**Обоснование.** Двойное сторно вернуло бы долг дважды; сторно без ссылки потеряло
бы связь с исправляемым документом. Явная ссылка и уникальность делают историю
восстановимой: по любому отменённому документу видно, чем именно он отменён.

**Принуждение.**

- **БД-ограничение.** `UNIQUE (reversal_of_id)`; `CHECK`:
  `(kind = 'reversal') = (reversal_of_id IS NOT NULL)`; внешний ключ
  `accrual.reversal_of_id → accrual.id`. Для `invoice`/`payment` — триггеры
  состояния, запрещающие повторный `void`/`reversed`.
- **Доменный сервис.** `ReverseAccrual` проверяет статус оригинала, равенство сумм
  и отсутствие существующего сторно; иначе `REVERSAL_ALREADY_EXISTS`.
- **Транзакция приложения.** Оригинал блокируется `FOR UPDATE`; проверка и вставка
  сторно — атомарно.
- **Архитектурный тест.** Запрещает `DELETE` финансовых документов и повторное
  сторно в обход доменного сервиса.

**Исполняемая проверка.**

```sql
-- Дубли сторно. Ожидается 0 строк.
SELECT reversal_of_id, count(*)
FROM accrual
WHERE reversal_of_id IS NOT NULL
GROUP BY reversal_of_id
HAVING count(*) > 1;

-- Сторно без kind='reversal' или без ссылки. Ожидается 0 строк.
SELECT id FROM accrual
WHERE (kind = 'reversal') <> (reversal_of_id IS NOT NULL);
```

## INV-20. Баланс лицевого счёта всегда равен разнице начислений и распределений

**Формулировка.** Для каждого лицевого счёта в любой момент выполняется:

```
accrual_total   = Σ(regular, status ∈ {posted, reversed}) − Σ(reversal, status = posted)
allocated_total = Σ(allocation)
credit_balance  = Σ(payment.amount_minor − payment.allocated_minor), payment.status ≠ reversed
balance_minor   = accrual_total − allocated_total
```

`account_balance` хранит эти значения и пересчитывается в той же транзакции, что и
любое начисление, сторно или распределение. Аванс (`credit_balance`) учитывается
отдельным слагаемым и не уменьшает `balance_minor` до момента распределения.
Положительный баланс означает долг, нулевой — закрытые расчёты; отрицательный
баланс не предусмотрен и трактуется как дефект данных, переплата выражается
отдельным авансом.

**Обоснование.** Это главная сверка предметной области: сумма долга должна
восстанавливаться из первичных документов, а не быть «мнением» отдельного поля.
Формула замыкает INV-06 и INV-07: если `paid_minor` и `allocated_minor` верны,
баланс сходится; расхождение — сигнал ошибки, а не норма.

**Принуждение.**

- **БД-ограничение.** `CHECK (balance_minor = accrual_total_minor − allocated_total_minor)`;
  триггеры/транзакционные вызовы пересчёта при изменении `accrual`, `allocation`,
  `payment`; запрет прямого `UPDATE account_balance` вне `ledger`.
- **Доменный сервис.** `AccountBalance.recalculate()` — единственный способ
  изменить агрегат; вызывается из `billing` и `ledger` в их транзакциях.
- **Транзакция приложения.** Блокировка `account_balance` `FOR UPDATE`; обновление
  после записи документа; периодическая сверка (rebuild job) пересчитывает и
  сообщает расхождения.
- **Архитектурный тест.** Запрещает `UPDATE account_balance` вне `ledger`;
  проверяет наличие CHECK-формулы.

**Исполняемая проверка.**

```sql
WITH acc AS (
  SELECT account_id,
         sum(CASE
               WHEN kind = 'regular' AND status IN ('posted','reversed') THEN amount_minor
               WHEN kind = 'reversal' AND status = 'posted' THEN -amount_minor
               ELSE 0
             END) AS accrual_total
  FROM accrual
  GROUP BY account_id
), al AS (
  SELECT i.account_id, sum(a.amount_minor) AS allocated_total
  FROM allocation a
  JOIN invoice i ON i.id = a.invoice_id
  GROUP BY i.account_id
), cr AS (
  SELECT account_id, sum(amount_minor - allocated_minor) AS credit
  FROM payment
  WHERE status <> 'reversed'
  GROUP BY account_id
)
SELECT b.account_id
FROM account_balance b
LEFT JOIN acc ON acc.account_id = b.account_id
LEFT JOIN al  ON al.account_id  = b.account_id
LEFT JOIN cr  ON cr.account_id  = b.account_id
WHERE b.accrual_total_minor   <> coalesce(acc.accrual_total, 0)
   OR b.allocated_total_minor <> coalesce(al.allocated_total, 0)
   OR b.credit_balance_minor  <> coalesce(cr.credit, 0)
   OR b.balance_minor         <> b.accrual_total_minor - b.allocated_total_minor;
-- Ожидается 0 строк.
```
