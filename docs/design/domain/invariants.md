# Инварианты предметной области

Нумерация `INV-01 … INV-23` — **контракт**: на неё ссылаются архитектура,
трассировка и тесты. Удалённый номер не переиспользуется; новый инвариант
получает следующий свободный номер.

Слой принуждения: **домен** — value object или use case; **БД** — ограничение,
индекс или триггер; **тест** — что обязано падать при нарушении. Для каждого
инварианта указано, где он физически удерживается; «только на ревью» запрещено.

## 1. Деньги и периоды

### INV-01 — Деньги только в целых минорных единицах

**Формулировка.** Любая денежная величина хранится и вычисляется как целое число
копеек; `float`, `double`, `real` и денежные строки запрещены.
**Почему.** Ошибка округления в копейках накапливается и ломает баланс.
**Принуждение.** Домен: тип `Money` (`bigint` + валюта). БД: `INTEGER` и `CHECK`.
**Проверка.** `validate-docs` (`DBML_MONEY_TYPE`), unit-тест «сложение и вычитание
сохраняют целочисленность».

### INV-02 — Период всегда `YYYY-MM`

**Формулировка.** Колонка `period` содержит ровно 7 символов вида `YYYY-MM`, месяц
01–12; сравнение — лексикографическое.
**Почему.** Периоды — ключ группировки и уникальности; свободная строка ломает
отчёты и сортировку.
**Принуждение.** Домен: тип `Period`. БД: `varchar(7)` + `CHECK` с regex.
**Проверка.** `validate-docs` (`DBML_PERIOD_TYPE`), unit-тест отклонения `2026-13`.

## 2. Квитанции и тарифы

### INV-03 — Одна не-аннулированная квитанция на лицевой счёт и период

**Формулировка.** Для пары `(account_id, period)` существует не более одной записи
`invoice` в состоянии, отличном от `void`; после аннулирования допускается
исправленная квитанция за тот же период.
**Почему.** Две активные квитанции за один период делают долг неоднозначным, а
запрет перевыпуска делает исправление ошибки невозможным.
**Принуждение.** БД: частичный `UNIQUE (account_id, period) WHERE status <> 'void'`.
Домен: проверка перед фиксацией.
**Проверка.** `validate-docs` (`DBML_INVOICE_UNIQUE`), интеграционный тест повторной
фиксации и тест перевыпуска после `void`.

### INV-04 — Тарифы одной услуги поставщика не пересекаются по датам

**Формулировка.** Интервалы `[valid_from, valid_to)` для одной услуги поставщика
(`supplier_service`) не пересекаются; новый тариф закрывает предыдущий. У разных
поставщиков одного типа услуги тарифы независимы.
**Почему.** Иначе не определить цену на дату.
**Принуждение.** Домен + БД: проверка пересечения при вставке.
**Проверка.** Unit-тест «пересечение отклоняется», интеграционный тест выбора тарифа.

### INV-05 — Сумма квитанции равна сумме строк; после фиксации — неизменяемость

**Формулировка.** `invoice.total_minor = SUM(invoice_line.amount_minor)`;
после перехода в `issued` поля квитанции и её строк не изменяются.
**Почему.** Квитанция — документ-основание; правка после выставления уничтожает
историю и аудит.
**Принуждение.** Домен + БД-триггер, запрещающий `UPDATE` при `issued`.
**Проверка.** Интеграционный тест «сумма = строки», тест «правка issued отклоняется».

### INV-06 — Аннулировать можно только квитанцию без активных распределений

**Формулировка.** Переход `draft|issued|partially_paid → void` разрешён, если по
квитанции нет активных распределений; иначе сначала отменяются распределения
(`allocation.reversed_at` с причиной и аудитом), затем квитанция аннулируется;
исправление начислений — сторно.
**Почему.** Аннулирование оплаченной квитанции оставило бы «висящие» деньги.
**Принуждение.** Домен: `VoidInvoice` проверяет активные распределения; отмена —
`ReverseAllocation`. БД: триггер.
**Проверка.** Unit-тест двух веток; интеграционный тест «оплаченная не
аннулируется, пока распределения активны»; тест отмены распределения.

## 3. Платежи и распределения

### INV-07 — Распределения по платежу не превышают платёж

**Формулировка.** `SUM(allocation.amount_minor) WHERE payment_id = P AND
reversed_at IS NULL` ≤ `payment.amount_minor`.
**Почему.** Иначе распределяется больше денег, чем поступило.
**Принуждение.** Домен + транзакция с пересчётом суммы.
**Проверка.** Конкурентный интеграционный тест; property-тест распределения.

### INV-08 — Распределение не превышает остаток квитанции

**Формулировка.** Новая сумма распределений по квитанции ≤ `invoice.total_minor`.
**Почему.** Переплата по квитанции должна становиться авансом, а не «минусом».
**Принуждение.** Домен + транзакция.
**Проверка.** Интеграционный тест частичной оплаты и переплаты.

### INV-09 — Переплата хранится как аванс

**Формулировка.** Неразнесённый остаток платежа отражается в
`balance.advance_minor`; квитанция не может иметь отрицательный остаток.
**Почему.** Переплата — актив пользователя, её нельзя терять.
**Принуждение.** Домен: `ledger` обновляет баланс в транзакции.
**Проверка.** Интеграционный тест «платёж больше квитанции».

### INV-10 — Баланс согласован с операциями

**Формулировка.** Для каждого лицевого счёта
`accrued_minor − paid_minor = debt_minor − advance_minor`, где `debt_minor ≥ 0` и
`advance_minor ≥ 0`, а хотя бы одно из них равно нулю.
**Почему.** Баланс — то, что видит пользователь; рассогласование подрывает доверие.
**Принуждение.** Домен: единственная точка обновления баланса; БД: `CHECK`.
**Проверка.** Инвариантный тест после каждого сценария; пересчёт «с нуля» и сверка.

### INV-11 — Сторно однократно и без потери оригинала

**Формулировка.** Для одного начисления/квитанции существует не более одной
связанной обратной записи; исходная запись остаётся видимой.
**Почему.** История изменений должна быть восстанавливаемой.
**Принуждение.** БД: уникальность `reversal_of`; домен: проверка.
**Проверка.** Unit-тест повторного сторно.

## 4. Лицевые счета и счётчики

### INV-12 — По закрытому лицевому счёту не создаются документы

**Формулировка.** Если `account.closed_on` заполнен, новые начисления, квитанции и
платежи по нему запрещены; закрытие при долге невозможно.
**Почему.** Закрытый счёт — архив, а не рабочий контур.
**Принуждение.** Домен + триггер БД.
**Проверка.** Интеграционный тест.

### INV-13 — Идемпотентность импорта и повторных операций

**Формулировка.** Повторная операция с тем же `idempotency_key` (или тем же
`batch_key` для импорта; CSV-импорт — после первой версии, R-06) не создаёт новых
записей и возвращает результат первого выполнения.
**Почему.** Импорт повторяют после ошибки; будущая синхронизация повторяет доставку.
**Принуждение.** БД: `UNIQUE (payment.idempotency_key)`, `UNIQUE (import_job.batch_key)`,
частичный `UNIQUE (accrual.account_id, accrual.service_type_id, accrual.period)
WHERE reversal_of IS NULL`; домен: чтение существующей записи.
**Проверка.** `validate-docs` (`DBML_PAYMENT_UNIQUE`), интеграционный тест повтора
импорта и платежа.

### INV-14 — Одно показание на счётчик и период, значения не убывают

**Формулировка.** Для `(meter_id, period)` — одно показание; новое значение не
меньше предыдущего в пределах жизни счётчика. Убывающее значение допускается
только как явно подтверждённое исправление с причиной и аудитом; замена счётчика
оформляется отдельной операцией с начальными показаниями нового прибора.
**Почему.** Убывающее показание — почти всегда опечатка; но замена/переход
счётчика требуют нового отсчёта.
**Принуждение.** БД: `UNIQUE (meter_id, period)`; домен: сравнение с предыдущим,
подтверждение и аудит для исключения; `ReplaceMeter` создаёт новый `meter`.
**Проверка.** Unit-тест убывания без подтверждения (отказ) и с подтверждением
(успех + аудит), интеграционный тест дубля периода и замены счётчика.

### INV-15 — Показание принимается только в срок поверки

**Формулировка.** Если последняя запись `meter_verification.valid_until < taken_on`,
показание отклоняется с `VERIFICATION_EXPIRED`; после поверки создаётся новая
запись истории, а `meter.verified_on`/`valid_until` обновляются как зеркало.
**Почему.** Просроченный счётчик не даёт юридически значимых показаний.
**Принуждение.** Домен; история — `meter_verification`; напоминание создаётся заранее.
**Проверка.** Unit-тест граничных дат и истории поверок.

## 5. Профили, аудит, данные

### INV-16 — Последний владелец и права ролей

**Формулировка.** В файле данных всегда есть хотя бы один активный `owner`;
последний `owner` не отключается и не понижается. `member` не управляет профилями,
не восстанавливает бэкап и не аннулирует квитанции.
**Почему.** Иначе файл данных остаётся без администратора.
**Принуждение.** Домен: `identity` проверяет количество владельцев.
**Проверка.** Unit-тест «последний owner», матрица прав.

### INV-17 — Аудит append-only и полный

**Формулировка.** Каждое финансовое изменение (начисление, квитанция, платёж,
распределение, сторно, показание) создаёт ровно одну запись `audit_event` в той же
транзакции; `UPDATE`/`DELETE` по `audit_event` запрещены.
**Почему.** Нужно ответить «кто и почему изменил», даже спустя годы.
**Принуждение.** Домен: порт аудита; БД: триггеры запрета изменения.
**Проверка.** Трансформационный тест «изменение без аудита невозможно».

### INV-18 — Журнал изменений append-only и упорядочен

**Формулировка.** `change_log` не изменяется и не удаляется; для сущности
`logical_clock` строго возрастает; пара `(entity_type, entity_id, logical_clock)`
уникальна.
**Почему.** Журнал — основа будущей синхронизации; перезапись ломает доставку.
**Принуждение.** БД: уникальный индекс и триггер; домен: счётчик часов.
**Проверка.** Интеграционный тест порядка и повтора.

### INV-19 — Вложение ссылается на существующий документ

**Формулировка.** `attachment.entity_type/entity_id` указывает на существующую
запись; `sha256` и размер заполнены; BLOB `content` не пуст и совпадает с хешем.
**Почему.** Битая ссылка на скан равносильна потере документа.
**Принуждение.** Домен: проверка при прикреплении; фоновая проверка целостности.
**Проверка.** Интеграционный тест «файл удалён — ссылка помечена битой».

### INV-20 — Версия схемы совместима и миграции только вперёд

**Формулировка.** Приложение открывает файл, если `schema_version` ≤ версии
приложения; миграции применяются последовательно и не откатываются автоматически.
**Почему.** Открытие старой версией файла новой схемы разрушает данные.
**Принуждение.** `portability` проверяет версию до открытия; миграции идемпотентны.
**Проверка.** Интеграционный тест «файл новее приложения отклонён», тест миграции
с копией данных.

## 6. Распознавание квитанций

### INV-21 — Распознанное не становится документом без подтверждения

**Формулировка.** Данные из `recognition_candidate` не создают `accrual`,
`invoice` или `payment`, пока пользователь явно не подтвердил задание импорта;
поля с низкой уверенностью подсвечиваются и требуют проверки; отказ не создаёт
финансовых записей.
**Почему.** OCR ошибается; молчаливое создание документа из распознанного текста
портит баланс и историю.
**Принуждение.** Домен: `recognition` передаёт данные в `billing`/`invoicing`
только после статуса `confirmed`; аудит фиксирует подтверждение и исправления.
**Проверка.** Интеграционный тест «кандидат без подтверждения → нет документов»;
тест «исправленное поле сохраняется в кандидате и не меняет шаблон».

### INV-23 — Шаблон квитанции версионируется и меняется только явной правкой

**Формулировка.** `supplier_template` создаётся пользователем в модуле настройки
или разработчиком по образцу; изменение шаблона создаёт новую версию, а
существующие версии не перезаписываются и не удаляются (архивирование допустимо).
Исправления распознанных полей и подтверждение квитанции шаблон не меняют:
шаблон изменяется только явной операцией создания версии.
**Почему.** Иначе «самообучение» на ошибках пользователя незаметно меняет правила
разбора и ломает распознавание; теряется воспроизводимость результата.
**Принуждение.** Домен: `recognition` создаёт версию `max(version) + 1`; БД:
уникальный индекс `(supplier_id, name, version)` и запрет `UPDATE` областей и
правил существующей версии; UI не сохраняет шаблон неявно.
**Проверка.** Интеграционный тест «правка поля не меняет шаблон»; тест
«редактирование создаёт новую версию, старая доступна»; e2e «разметка → сохранение
→ повторное распознавание».

## 7. Платежи в первой версии

### INV-22 — Ручной платёж создаётся сразу с распределением

**Формулировка.** При ручной регистрации платежа пользователь указывает хотя бы
одну квитанцию; платёж и его активные распределения создаются в одной транзакции.
Остаток сверх выбранных квитанций остаётся авансом (`balance.advance_minor`), но
сам платёж без распределения не создаётся.
**Почему.** Так исключается «платёж-сирота», который непонятно к чему относить, и
упрощается баланс; пользователь сразу видит, что закрыто.
**Принуждение.** Домен: `RegisterPayment` принимает распределения и проверяет их;
UI не даёт сохранить без выбора квитанции.
**Проверка.** Unit-тест «платёж без распределения отклонён»; e2e «оплата →
выбор квитанции → баланс»; интеграционный тест переплаты (аванс).
