# Сущности и агрегаты

Каждая сущность описана полями, состояниями, владельцем (модуль) и инвариантами.
Физическая схема — в [model.dbml](model.dbml); правила — в
[invariants.md](invariants.md); термины — в [glossary.md](glossary.md).

Общие соглашения: `id` — UUIDv7 в `TEXT`; деньги — `INTEGER` в копейках;
период — `varchar(7)` `YYYY-MM`; время — ISO-8601 UTC в `TEXT`; строки не удаляются
физически, если на них есть финансовые ссылки.

## 1. Профили и настройки

### `profile` — профиль члена семьи

| Поле | Смысл |
|---|---|
| `name` | Отображаемое имя; уникально в файле данных |
| `role` | `owner` или `member` |
| `password_hash` | Argon2id-хеш; открытый пароль не хранится |
| `is_active` | Профиль можно отключить, но не удалить, если на него ссылается аудит |

В первой версии существует один профиль `owner`; `member` — зона развития.
Состояния: активен → отключён. Последний `owner` не отключается и не понижается
(INV-16). Владелец: `identity`.

### `device` — устройство

Устройство, на котором открывался файл: `id`, `name`, `created_at`, `last_seen_at`.
Нужно для будущей синхронизации: каждая запись журнала помечается `device_id`.
Владелец: `portability`.

### `setting` — настройка

Пара «ключ — значение»: тема, порог напоминаний, формат даты, параметры окна напоминаний.
Владелец: `identity`.

## 2. Справочники

### `property` — объект

`type_id` (ссылка на `property_type`), `label` (свободное название, например
«Карабайка 36»), `address`, `area_m2`, `share_bp` (доля в базисных пунктах),
`note`, `status` (`active` / `archived`). Объект архивируется, но не удаляется:
статус убирает его из рабочего списка, история сохраняется. Владелец: `catalog`.

### `property_type` — тип объекта

`name` (единое написание — нижний регистр: «квартира», «дом», «земельный
участок»; так тип хранится и так показывается на всех экранах), `name_key` (ключ
уникальности, совпадает с `name`), `sort_order`, `is_active`. Уникальность — по
`name_key`: «Квартира», «квартира» и «КВАРТИРА» считаются одним типом. Встроенные
типы засеяны миграцией; пользователь может добавить свой тип и переименовать
существующий. Используемый тип не удаляется, а скрывается из выбора
(`is_active = 0`), чтобы старые объекты не потеряли тип. Владелец: `catalog`.

### `supplier` — поставщик

`name`, `name_key` (trim + нижний регистр; **не** уникален — дубли разрешены),
`kind` (`uk` / `tsj` / `rso` / `other`), `contacts`, `note`, `is_active`.
Поставщик не удаляется физически: `is_active = 0` скрывает его из выбора, счета и
история остаются. Дубль названия — предупреждение в UI, а не ошибка: одинаковые
названия бывают у разных организаций. Владелец: `catalog`.

### `account` — лицевой счёт

Связка `property_id` + `supplier_id` + `number`; уникальна. `opened_on`,
`closed_on`, `is_active`; `cabinet_url` — ссылка на личный кабинет поставщика,
`cabinet_note` — памятка, куда и как передавать показания/оплачивать (FR-19).
Закрытие — `closed_on`; по закрытому счёту новые документы не создаются (INV-12).
Закрытие при ненулевом балансе запрещено; до E-06 порт баланса возвращает 0,
поэтому фактическая проверка появится вместе с E-06.
Владелец: `catalog`.

### `service` — услуга

`name`, `unit` (код единицы: `m3` / `gcal` / `kwh` / `person` / `m2` / `month` /
`piece`; подписи — в [glossary.md](glossary.md) и `shared/units.ts`), `category`,
опциональная привязка к поставщику (`supplier_id`), `is_active`. Услуга не
удаляется физически: архив скрывает её из выбора, начисления и тарифы сохраняют
историю. Справочник общий: привязка к поставщику сужает выбор в E-04, но не
обязательна. Владелец: `catalog`.

### `tariff` — тариф

`service_id`, `price_minor` (копейки, ADR-0002), `unit` — **снимок** единицы
услуги на момент тарифа (правка единицы услуги не переписывает историю),
`valid_from`, `valid_to`. Периоды действия одной услуги не пересекаются (INV-04);
изменение тарифа — новая запись, старый закрывается `valid_to` = день до
`valid_from` нового. Правки суммы на месте нет. Владелец: `catalog`.

## 3. Счётчики

### `meter` — счётчик

`account_id`, `service_id`, `serial`, `kind`, `installed_on`, `verified_on`,
`valid_until`, `retired_on`, `replaced_meter_id`, `unit`. `verified_on`/`valid_until` —
зеркало последней записи `meter_verification`; после `valid_until` показания не
принимаются без новой поверки (INV-15). `retired_on` — вывод из эксплуатации;
`replaced_meter_id` — счётчик, который был заменён этим. Владелец: `metering`.

### `meter_verification` — поверка

`meter_id`, `verified_on`, `valid_until`, `certificate`, `note`, `created_by`.
История поверок; последняя запись задаёт текущий срок. Владелец: `metering`.

### `meter_reading` — показание

`meter_id`, `period`, `value numeric(14,3)`, `taken_on`, `submitted_on`,
`submission_marked_at`, `submission_channel`, `created_by`. Одно показание на
счётчик и период (INV-14); значение не меньше предыдущего, кроме явно
подтверждённого исправления с причиной (ошибка ввода, замена/переход счётчика) и
записи в аудите. Отметка о передаче не меняет значение; `submission_marked_at`
ставится автоматически, `submitted_on` — опциональная фактическая дата,
`submission_channel` — опциональный способ (личный кабинет/телефон/бумага).
Владелец: `metering`.

## 4. Начисления и квитанции

### `accrual` — начисление

`account_id`, `service_id`, `period`, `amount_minor`, `source`
(`manual` / `template` / `import` / `recognition`), `external_ref`, `reversal_of`,
`created_by`. Начисление не редактируется после создания: исправление — сторно и
новая запись (INV-11). Уникальность `(account_id, service_id, period)` действует
только для несторнированных строк (partial index `WHERE reversal_of IS NULL`), а
`reversal_of` уникален и ссылается на исходное начисление: дубли при повторном
импорте и повторное сторно запрещены (INV-13). Владелец: `billing`.

### `invoice` — квитанция

`account_id`, `period`, `total_minor`, `due_on`, `status`, `issued_at`, `voided_at`.
Состояния: `draft → issued → partially_paid → paid`, а также `void`. Правила:
одна не-`void` квитанция на лицевой счёт и период (INV-03); после аннулирования
допускается выпуск исправленной квитанции за тот же период; сумма равна сумме
строк (INV-05); после `issued` содержимое неизменяемо (INV-05); аннулирование —
только без активных распределений (INV-06). Оплата отражается статусом
(`partially_paid`/`paid`), датой и комментарием; `total_minor` не меняется.
Владелец: `invoicing`.

### `invoice_line` — строка квитанции

`invoice_id`, `accrual_id` (основание строки, nullable), `service_id`,
`amount_minor`, `basis` — основание расчёта для пользователя (тариф, показание,
норматив). Владелец: `invoicing`.

## 5. Платежи и распределения

### `payment` — платёж

`account_id`, `amount_minor`, `paid_on`, `channel` (`manual` / `import` / `other`),
`reference`, `idempotency_key`, `reversed_at`, `reversal_reason`, `created_by`.
Повтор с тем же ключом возвращает существующий платёж (INV-13). Ручной платёж
создаётся сразу с распределением по выбранным квитанциям (INV-22); остаток сверх
выбранных квитанций — аванс. Платёж не привязан к квитанции напрямую; ошибочный
платёж исправляется сторно (обратной записью) с причиной, а не удалением.
Владелец: `payments`.

### `allocation` — распределение

`payment_id`, `invoice_id`, `amount_minor`, `reversed_at`, `reversal_reason`,
`created_by`. Сумма активных распределений по платежу не превышает сумму платежа
(INV-07); по квитанции — не превышает остаток (INV-08). Пара
«платёж — квитанция» уникальна среди активных распределений; отмена распределения
возвращает деньги в аванс и пишется в аудит. Владелец: `ledger`.

### `balance` — баланс лицевого счёта

`account_id` (PK), `accrued_minor`, `paid_minor`, `debt_minor`, `advance_minor`,
`updated_at`. Не материализованное представление, а транзакционная таблица:
обновляется в той же транзакции, что и платёж/распределение/сторно (INV-10).
Владелец: `ledger`.

## 6. Напоминания и вложения

### `reminder` — напоминание

`kind` (`invoice_due` / `meter_submission` / `meter_verification`), `title`,
`due_on`, `target_type`, `target_id`, `status` (`pending` / `done` / `dismissed`).
Создаётся при фиксации квитанции, вводе показания или приближении поверки.
Владелец: `reminders`.

### `attachment` — вложение

`entity_type` (`invoice` / `payment` / `meter` / `accrual` / `import_job`), `entity_id`,
`file_name`, `mime`, `size_bytes`, `sha256`, `content` (BLOB). Содержимое хранится
в том же файле данных; дедупликация не выполняется — одно фото/скан соответствует
одному вложению, `sha256` нужен для проверки целостности. Изображение сжимается
при добавлении, хранится только сжатая копия (R-01). Ссылка на несуществующий
документ запрещена (INV-19). Владелец: `documents`.

## 7. Распознавание квитанций

### `import_job` — задание импорта

`kind` (`scan` / `pdf` / `csv`), `attachment_id`, `batch_key`, `status` (`uploaded` /
`processing` / `recognized` / `confirmed` / `failed` / `dismissed`), `page_count`,
`created_by`, `completed_at`, `error_code`. Одно задание — одна квитанция (фото,
скан, PDF) или, после первой версии, один CSV-файл; `batch_key` — хеш файла и
параметров импорта для идемпотентного повтора (ADR-0004, R-06). Владелец: `recognition`.

### `recognition_candidate` — кандидат распознавания

`import_job_id`, `page`, `line_no`, `field` (`period`, `supplier`, `account`,
`service`, `amount`, `total`, `due_on`), `value`, `service_id`, `amount_minor`,
`confidence_bp`, `bbox`, `accepted`, `corrected`. Несколько строк услуг одной
квитанции различаются `line_no`; `service_id`/`amount_minor` задают услугу и сумму
строки. Кандидат не является финансовым документом; он превращается в
начисление/квитанцию только после подтверждения пользователем (INV-21).
Владелец: `recognition`.

### `supplier_template` — шаблон поставщика

`supplier_id`, `sample_attachment_id`, `name`, `regions_json`, `rules_json`,
`version`, `created_by`, `created_at`. Шаблон задаёт области полей (период,
поставщик, лицевой счёт, итог, срок оплаты) и таблицы услуг в долях страницы
(`regions_json`) и правила разбора значений (`rules_json`); создаётся
пользователем в модуле настройки по скану нового формата (FR-20, E-15).
Версии не перезаписываются: изменение создаёт новую версию, старые доступны для
истории (INV-23). Исправления распознанных полей шаблон не меняют. Образец
хранится в `attachment` и нужен для редактирования и предпросмотра. Владелец:
`recognition`.

## 8. Аудит, журнал, версия схемы

### `audit_event` — аудит

`profile_id`, `occurred_at`, `action`, `entity_type`, `entity_id`, `reason`,
`correlation_id`, `details_json`. Append-only: `UPDATE` и `DELETE` запрещены на
уровне репозитория и SQLite-триггера (INV-17). Владелец: `identity`; аудит как
сквозная функция подключается через порт в `shared`.

### `change_log` — журнал изменений

`entity_type`, `entity_id`, `operation`, `payload_json`, `device_id`,
`logical_clock`, `occurred_at`, `synced_at`. Append-only; уникальность
`(entity_type, entity_id, logical_clock)`; основа будущей синхронизации (INV-18).
Владелец: `sync`; порт записи — в `shared`.

### `schema_version` — версия схемы

`version`, `applied_at`, `note`. Применённые миграции; приложение отказывается
открывать файл с версией новее поддерживаемой (INV-20). Владелец: `portability`.

## 9. Агрегаты и границы транзакций

| Агрегат | Корень | Внутри | Внешние ссылки |
|---|---|---|---|
| Профиль | `profile` | `setting` | аудит |
| Объект | `property` | — | `account`, `property_type` |
| Лицевой счёт | `account` | — | `meter`, `accrual`, `invoice`, `payment`, `balance` |
| Счётчик | `meter` | `meter_reading`, `meter_verification` | `account`, `service` |
| Начисление | `accrual` | — | `account`, `service` |
| Квитанция | `invoice` | `invoice_line` | `account`, `accrual` |
| Платёж | `payment` | — | `account` |
| Распределение | `allocation` | — | `payment`, `invoice` |
| Задание импорта | `import_job` | `recognition_candidate` | `attachment`, `supplier_template` |

Транзакция охватывает один агрегат и его зависимости, которые обязаны быть
согласованы сразу: платёж + выбранные распределения + баланс + аудит + журнал —
одна транзакция; отмена распределения + баланс + аудит + журнал — также одна
транзакция. Квитанция и начисления связаны логически, но фиксируются раздельно.

## 10. Допущения модели

| ID | Допущение | Влияние |
|---|---|---|
| DM-A-01 | Одна валюта — рубль; `currency` в модели не хранится | Мультивалютность не поддерживается |
| DM-A-02 | Пользователь ведёт учёт только своих объектов недвижимости | Нет совместного владения с другими людьми |
| DM-A-03 | Вложения хранятся в файле данных как BLOB | Бэкап — это один файл |
| DM-A-04 | Доля владения — базисные пункты, а не площадь для расчёта | Расчёты по доле не автоматизируются |
| DM-A-05 | Показания не пересчитываются в начисления автоматически | Начисление вводится отдельно |
| DM-A-06 | Импорт начислений — CSV; другие форматы после первой версии | Адаптер расширяется отдельно |
| DM-A-07 | Распознавание локальное (OCR + правила), без ML-моделей в первой версии | Точность зависит от качества скана |
| DM-A-08 | В первой версии один профиль `owner`; модель профилей/ролей готова к нескольким членам семьи | Многопользовательский UI — после первой версии |
| DM-A-09 | Одно фото/скан — одно вложение; дедупликация содержимого не выполняется | Одинаковые файлы занимают место повторно |
| DM-A-10 | Файл данных не шифруется в первой версии; защита — вход по паролю и ОС | Шифрование файла — отдельное решение |
