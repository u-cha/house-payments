# ADR-0017: Свежий `main` перед пушем

## Статус

`accepted`, 2026-11-04. Владелец решения: пользователь-собственник. Согласовано с
владельцем 2026-11-04 в задаче доски `t-mw2erq3o-no4erd`: выбран вариант C — текст
правил + детерминированный скрипт + локальный `pre-push`-хук + серверное требование
актуальной ветки в ruleset; синхронизация — через `merge`, без rebase. Дополняет
[ADR-0013](0013-repository-docs-and-versioning.md) и [ADR-0014](0014-public-repo-and-enforced-rules.md)
в части процесса git; правила CI из [ADR-0015](0015-ci-tests-and-status-polling.md)
не меняет.

## Контекст

- `main` защищён ruleset: push только через PR, линейная история, запрет
  force-push (ADR-0014). CI (`pull_request` в `main`) проверяет merge-превью
  PR (ADR-0016/ADR-0015): конфликт с `main` обнаруживается при создании PR, а не
  при пуше, и уж точно не в момент, когда агент заканчивает работу.
- Правила не требовали свежего `main` перед пушем: AGENTS.md §3 говорил о
  зелёном `pnpm check` до пуша и о CI после пуша, но не об актуальности ветки.
  Ветка могла жить на устаревшем `main` дни и «встретить» конфликт в конце.
- `strict_required_status_checks_policy` в ruleset `protect-main` (id 26541613)
  выключен: GitHub не требует, чтобы ветка PR содержала актуальный `main`.
  Серверного гейта актуальности сейчас нет.
- Разрешать конфликт — содержательное решение, а не механика. Плохая
  автоматика (выбор `--ours`/`--theirs`, удаление чужой правки, отключение
  тестов) маскирует потерю решения. Пользователь требует: при непонимании —
  остановиться и спросить.
- Агенты работают и из основного каталога, и из worktree изоляции; локальный хук
  можно обойти (`--no-verify`), поэтому нужен и серверный слой.
- Проверки `pnpm check` не зависят от сети; синхронизация — единственный шаг,
  который требует `git fetch`.

## Рассмотренные варианты

### 1. Только текст в AGENTS.md (выбран как база, но недостаточен)

Новый пункт в §3 и критерий в §5: перед пушем `git fetch` + `git merge
origin/main`, конфликты по правилам.

**Плюсы:** дёшево, без нового кода; правило действует для любого агента и любой
машины, включая environments, где скрипты/хуки не установлены.

**Минусы:** соблюдение держится только на дисциплине агента; ADR-0014 прямо
отверг такой способ как единственный («gate на сервере, а не на дисциплине»).
Команды каждый раз пишутся по-своему — расходятся rebase/merge и обработка
конфликтов.

### 2. Текст + `pnpm sync:main` + `pre-push`-хук (выбран)

Одна команда синхронизации; хук блокирует пуш ветки без свежего `origin/main`.

**Плюсы:** поведение воспроизводимо (merge, коды выхода, отчёт о конфликтах);
агент не выбирает команды сам; хук ловит забывчивость в момент пуша; тесты
доказывают, что и скрипт, и хук падают на конфликте и на устаревшей ветке.

**Минусы:** хук локальный — обходится `--no-verify`, не действует на машине без
`core.hooksPath`; `git fetch` в хуке добавляет сетевой шаг к пушу; появляется
скрипт, который надо поддерживать.

### 3. Только серверный гейт в ruleset

Включить `strict_required_status_checks_policy` в `protect-main`, ничего не
менять в репозитории.

**Плюсы:** работает для всех машин и агентов; не обходится локально; одна
настройка.

**Минусы:** гейт стоит на merge, а не на пуше: пуш устаревшей ветки проходит,
конфликт всплывает позже; merge-превью CI уже проверяет слияние с `main`, поэтому
сам по себе гейт не учит агента синхронизироваться вовремя и не задаёт порядок
разрешения конфликтов.

### 4. Rebase на `origin/main` вместо merge

**Плюсы:** линейная история ветки, без merge-коммитов.

**Минусы:** переписывает уже запушенную ветку и требует force-push; для агентских
сессий и ревью это лишний риск, а `main` всё равно получает линейную историю
через squash-merge. Отклонён.

## Решение

1. **Правило в [AGENTS.md](../../../../AGENTS.md) §3.8.** Перед каждым пушем — в
   том числе перед первым пушем новой ветки:

   ```bash
   pnpm sync:main    # git fetch origin + git merge origin/main
   pnpm check
   git push
   ```

   Конфликт разрешается вручную и только при понимании обеих сторон. Смысловой
   конфликт (обе стороны меняют одно решение, логику, инвариант) или непонимание,
   чья версия верна, — **остановка и вопрос пользователю** с файлами, обеими
   сторонами и предложением. Запрещены `--ours`/`--theirs`/`-X ours`/`-X theirs`,
   отключение или ослабление тестов ради зелёного `pnpm check`, пуш без свежего
   `origin/main`. Обход хука `--no-verify` — только с явного разрешения
   пользователя.
2. **Команда `pnpm sync:main`** — [scripts/sync-main.mjs](../../../../scripts/sync-main.mjs):
   `git fetch origin main`; если `origin/main` уже предок HEAD — ничего не делает;
   иначе `git merge origin/main` с сообщением `chore: sync with origin/main`.
   Конфликты не разрешаются и сторона не выбирается: скрипт печатает конфликтные
   файлы и выходит с кодом `1`; `0` — свежо, `2` — нельзя (не git, detached HEAD,
   `main`, локальные изменения), `3` — не удалось получить `origin/main`.
3. **Локальный `pre-push`-хук** [.githooks/pre-push](../../../../.githooks/pre-push):
   для каждой запушенной ветки требует, чтобы `refs/remotes/<remote>/main` был
   предком запушенного коммита; блокирует пуш в `main`, пуш при незавершённом
   merge и пуш без актуального `main`, печатая следующий шаг. Хук включается
   `pnpm bootstrap` (`git config core.hooksPath .githooks`); чужой `core.hooksPath`
   не перезаписывается.
4. **Серверный слой:** в ruleset `protect-main` (id 26541613) включён
   `strict_required_status_checks_policy: true` — «Require branches to be up to
   date before merging» (применено 2026-11-04, проверено через GitHub API). Это
   действие владельца репозитория в настройках GitHub (agents не правят ruleset в
   обход). Гейт не заменяет пуш-правило, а страхует merge, если локальный хук
   обойдён или не установлен.
5. **Критерий завершённости** — [AGENTS.md](../../../../AGENTS.md) §5: ветка
   содержит свежий `origin/main`, конфликты разрешены осознанно или вынесены
   пользователю.
6. **Проверки:** `tests/sync-main.test.mjs` и `tests/pre-push.test.mjs` на
   временных git-репозиториях доказывают: свежая ветка не меняется; устаревшая
   сливается merge-коммитом, а не rebase; конфликт даёт код 1, список файлов и
   незавершённый merge без автоматического выбора стороны; хук блокирует
   устаревшую ветку и пуш в `main`.

## Последствия

**Положительные:**

- Конфликт с `main` обнаруживается до пуша, а не при merge PR; разрешается
  осознанно, с сохранением обоих решений или вопросом пользователю.
- Поведение одинаково у всех агентов и людей: одна команда, один порядок,
  понятные коды выхода.
- Локальный хук и серверное требование актуальности закрывают разные слои:
  забывчивость на машине и обход/отсутствие хука.
- `merge` не переписывает запушенную ветку — не нужен force-push; `main` остаётся
  линейным за счёт squash-merge.

**Отрицательные:**

- В истории ветки появляются merge-коммиты `chore: sync with origin/main`; при
  squash-merge в `main` они схлопываются, но диффы PR становятся шумнее.
- `git fetch` внутри хука требует сети; офлайн-пуш либо блокируется, либо
  проверяется по устаревшей ссылке (хук предупреждает).
- Хук локальный: не установлен — не работает; обходится `--no-verify`; на машине
  без `pnpm bootstrap` его нет. Поэтому серверный гейт обязателен.
- Серверное требование актуальности заставляет обновлять ветку после любого
  изменения `main`, то есть добавляет шаг перед merge каждому PR.
- `strict` в ruleset — настройка владельца: агент не может включить её сам, без
  прав администратора.

## Условия пересмотра

- Merge-коммиты в ветках начнут мешать ревью или конфликтов станет больше, чем
  пользы от синхронизации, — рассмотреть merge queue GitHub или rebase-политику
  отдельным ADR.
- `git fetch` в хуке станет заметно замедлять пуш или сломает офлайн-сценарий —
  вынести проверку в отдельный шаг/CI, оставив только серверный гейт.
- Появятся несколько человек с правом merge — пересмотреть approvals и `strict`
  вместе с CODEOWNERS (ADR-0014, условия пересмотра).
- GitHub изменит семантику `strict_required_status_checks_policy` или rulesets —
  пересмотреть серверный слой, сохранив принцип «конфликт не разрешается вслепую».
