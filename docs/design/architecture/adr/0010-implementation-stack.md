# ADR-0010: Стек реализации — TypeScript, Electron, React, SQLite

## Статус

`proposed`, 2026-11-04. Владелец решения: пользователь-собственник. Решение
вынесено на ревью; до принятия это обоснованная рекомендация, а не факт.

## Контекст

- C-06: TypeScript, Electron, React, SQLite; модульный монолит.
- ADR-0001 — локальное настольное приложение; ADR-0009 — платформы и установщики;
  ADR-0008 — один файл SQLite; ADR-0005 — транзакции и журнал.
- QS-10: онбординг нового инженера ≤ 1 дня; QS-02: сохранение платежа p95 ≤ 300 мс;
  QS-05: защита данных; QS-09: 10× объём без смены стиля.
- Пользователь просил обоснование, а не выбор «модного» инструмента. Критерии:
  один язык, предсказуемые транзакции, зрелые библиотеки, низкий порог входа,
  возможность собрать установщик под три ОС.

Силы: скорость разработки (тянет к «всё готово»), контроль над SQL (тянет к
простым драйверам), меньше зависимостей (тянет к стандартной библиотеке),
безопасность (тянет к строгим границам и валидации).

## Рассмотренные варианты

### 1. TypeScript + Electron + React + SQLite (выбран)

- Node.js 22 LTS и Electron (main/preload/renderer);
- React 19 + Vite в renderer; TypeScript strict;
- SQLite через `better-sqlite3` в main-процессе (синхронный, транзакционный);
- Zod на границе IPC; TanStack Query для кэша чтения; Zustand для локального UI-состояния;
- Recharts для графиков; CSS Modules и токены оформления;
- OCR и разбор документов: `Tesseract.js` (русский и английский), `pdf.js`,
  `sharp` для предобработки; тяжёлая обработка — в `worker_threads`;
- Vitest (unit/integration), Playwright (e2e), `dependency-cruiser` (архитектурные тесты);
- electron-builder (установщики), electron-updater (обновления);
- pnpm, ESLint, Prettier.

**Плюсы:** один язык на всех слоях; прямой SQL без генераторов; синхронный драйвер
упрощает транзакции и тесты; зрелая экосистема и документация; низкий порог входа;
сборка установщиков поддерживается из коробки.

**Минусы:** Electron тяжёлый; `better-sqlite3` — нативный модуль (нужна
пересборка под каждую платформу/версию Electron); renderer нужно держать в строгой
изоляции; нет типовой безопасности БД на уровне языка.

### 2. Tauri + Rust + React

**Плюсы:** маленький установщик и память; строгая безопасность; нативный Rust для
транзакций.

**Минусы:** второй язык (Rust) и отдельная сборка; различия webview между ОС;
нативная часть усложняет онбординг (QS-10); для первой версии выгода не оправдывает
стоимость. Отклонён; пересматривается по ADR-0009.

### 3. Flutter

**Плюсы:** один код на desktop и mobile; быстрый UI.

**Минусы:** Dart и отдельная экосистема; доступ к SQLite и файлам иной; команда
ориентирована на TypeScript; переиспользование домена в будущем веб-клиенте
невозможно. Отклонён.

### 4. .NET MAUI / WPF

**Плюсы:** зрелость на Windows.

**Минусы:** C# и другая экосистема; поддержка macOS/Linux слабее; нет причин
менять язык при C-06. Отклонён.

### 5. Electron + ORM (Prisma/TypeORM)

**Плюсы:** меньше ручного SQL; миграции «из коробки».

**Минусы:** генерация SQL скрывает запросы; для финансового домена нужен явный
контроль транзакций и индексов; Prisma плохо работает с нативными бинарниками в
Electron; миграции и файл данных усложняются. Отклонён в пользу явного SQL и
нумерованных миграций.

## Решение

1. Язык — **TypeScript strict** на всех слоях; домен не зависит от Electron.

   **Почему Electron, а не Tauri — ответ на вопрос пользователя.** Electron выбран
   не «по умолчанию», а по четырём причинам:
   - один язык на UI, ядре и распознавании; не нужно добавлять Rust и собирать
     нативную часть под три ОС;
   - Electron несёт свой Chromium, поэтому интерфейс одинаков на Windows, macOS и
     Linux; у Tauri используется системный WebView, и различия между ОС придётся
     обходить;
   - экосистема под новое требование FR-18 уже есть в JavaScript: `Tesseract.js`,
     `pdf.js`, обработка изображений;
   - установщики, подпись и автообновление закрываются `electron-builder` и
     `electron-updater` без отдельной инфраструктуры.
   Цена — размер установщика и памяти. Tauri даёт ~10–20 МБ и меньше памяти, но
   добавляет второй язык и различия WebView. Для домашнего приложения с локальным
   OCR выгода Tauri не перекрывает стоимость поддержки; решение пересматривается по
   условиям ниже.
2. Оболочка — **Electron**: main (ядро и адаптеры), preload (минимальный мост),
   renderer (React). `contextIsolation: true`, `nodeIntegration: false`,
   `sandbox: true`; renderer не имеет доступа к файлам и БД.
3. Данные — **SQLite** через `better-sqlite3`; WAL, `foreign_keys=ON`,
   `busy_timeout`; миграции — нумерованные SQL-файлы, только вперёд.
4. Валидация границы — **Zod**; ошибки — единый `AppError` (core-modules §6).
5. UI — **React + Vite**, **TanStack Query** для чтения, **Zustand** для
   локального состояния, **Recharts** для графиков, **CSS Modules**.
6. Тесты — **Vitest** (unit, интеграционные с временным файлом SQLite),
   **Playwright** (e2e), **dependency-cruiser** (границы модулей).
7. Сборка — **electron-builder** (NSIS/DMG/AppImage/deb), обновления —
   **electron-updater** с подписью; пакетный менеджер — **pnpm**. CI — **GitHub
   Actions**: матрица macOS/Windows/Linux, пересборка `better-sqlite3` под Electron
   и сборка установщиков (R-03).
8. Наблюдаемость — локальные структурированные логи без PII; аварийные отчёты
   не отправляются автоматически.

## Последствия

**Положительные:**

- Один язык и один набор инструментов — быстрый онбординг (QS-10).
- Прямой SQL и синхронные транзакции дают предсказуемое поведение финансовых
  операций (QS-02, QS-04).
- Зрелые библиотеки установки и обновления закрывают ADR-0009.
- Домен можно переиспользовать в будущем веб-клиенте при включении синхронизации.

**Отрицательные:**

- Размер установщика и потребление памяти выше, чем у Tauri.
- `better-sqlite3` — нативная зависимость: нужна пересборка под Electron и CI
  для трёх ОС; поломка после обновления Electron ловится на каждом изменении (R-03).
- Языковые данные OCR и `sharp` увеличивают установщик; распознавание требует
  отдельного воркера, иначе блокирует UI.
- Больше зависимостей, чем хотелось бы; нужна дисциплина обновлений.
- TypeScript не защищает от ошибок SQL — нужны интеграционные тесты и ревью.

**Запрещено:** бизнес-логика в renderer; прямой SQL в renderer; ORM с
автогенерацией миграций; `nodeIntegration: true`; хранение секретов в коде.

## Условия пересмотра

- Переход на Tauri/Flutter по ADR-0009 — стек пересматривается целиком.
- `better-sqlite3` перестаёт собираться под актуальный Electron — рассматривается
  `node:sqlite` или WASM-драйвер с сохранением транзакционной модели.
- Появляется мобильный клиент — домен выносится в общий пакет, UI — отдельный.
- Команда переходит на другой язык по организационным причинам — решение
  фиксируется новым ADR, домен сохраняется.
