# ADR-0002: Деньги — целые копейки, период — `YYYY-MM`

## Статус

`proposed`, 2026-11-04. Владелец решения: пользователь-собственник.

## Контекст

- C-02: деньги — только целые минорные единицы, без плавающей точки.
- C-03: расчётный период — `YYYY-MM`.
- Домен сравнивает суммы, суммирует начисления, распределяет платежи и считает
  баланс (INV-01, INV-02, INV-10). Ошибка округления накапливается и ломает доверие.
- Хранилище — SQLite: 64-битный `INTEGER` точен до 9 223 372 036 854 775 807.
- Пользователь видит рубли с копейками, но вводит и хранит данные в копейках.

Силы: точность (тянет к целым), удобство ввода (тянет к десятичным строкам),
переносимость (тянет к простым типам, которые понимает любая СУБД и Excel).

## Рассмотренные варианты

### 1. Целые минорные единицы (`INTEGER` копейки) (выбран)

**Плюсы:** точная арифметика; сравнение и индексация; одинаково читается в SQLite,
PostgreSQL и Excel; нет проблем с локалью и разделителями; `bigint` в TypeScript.

**Минусы:** на границе API и в UI нужна конвертация в рубли; `JSON.stringify` не
умеет `bigint` — нужен явный сериализатор; нельзя хранить дробные копейки.

### 2. Числа с плавающей точкой (`REAL`)

**Плюсы:** просто; сумма выглядит «как деньги».

**Минусы:** `0.1 + 0.2 ≠ 0.3`; накопление ошибки в балансе и отчётах; сравнение
сумм ненадёжно; прямой конфликт с C-02. Отклонён.

### 3. Десятичная строка (`TEXT`, `numeric`)

**Плюсы:** произвольная точность; читаемо в БД.

**Минусы:** арифметика только через библиотеку; сортировка и индексация требуют
приведения; легко случайно сложить строки; производительность ниже; для копеек
избыточно. Отклонён.

### 4. Период как дата или диапазон дат

**Плюсы:** гибкость для произвольных интервалов.

**Минусы:** неоднозначность «месяц» (начало/конец, часовой пояс); сложнее
уникальность «одна квитанция на период»; ломает C-03. Отклонён.

## Решение

1. Все денежные величины хранятся как `INTEGER` в копейках. В коде — тип `Money`
   (`amountMinor: bigint`, `currency: 'RUB'`); арифметика только между одинаковыми
   валютами.
2. В БД для денежных колонок — `INTEGER` и `CHECK`; `float`, `real`, `numeric` для
   денег запрещены и проверяются валидатором.
3. В JSON и IPC суммы передаются строкой (`"12345"`), чтобы не терять точность;
   на границе — явная сериализация.
4. Период хранится как `varchar(7)` `YYYY-MM` с `CHECK` на regex; сравнение —
   лексикографическое; `Period` предоставляет `next()`/`previous()`.
5. Тарифы (цена за единицу) — тоже целые копейки за единицу; дробные ставки не
   поддерживаются в первой версии.

## Последствия

**Положительные:**

- Баланс сходится копейка в копейку; отчёты не «плывут».
- Простые индексы и сортировка по периоду.
- Данные одинаково понимаются SQLite, CSV, Excel и будущим сервером.

**Отрицательные:**

- Конвертация в рубли и обратно — на UI и в экспорте; нужна аккуратность.
- `bigint` требует явной сериализации в IPC и JSON.
- Дробные копейки (например, при делении на долю) не поддерживаются: округление
  выполняется доменом по явному правилу `ROUND_HALF_UP` до записи.

**Запрещено:** хранить суммы в `REAL`, складывать строки, использовать `Date` для
периода, определять месяц по часовому поясу.

## Условия пересмотра

- Появляется требование мультивалютности (отдельный OQ) — добавляется `currency`
  и правило пересчёта; тип `Money` уже готов.
- Регуляторика требует иной точности (например, доли копейки) — вводится
  масштабируемый `amount_scaled` с фиксированной шкалой, но не `float`.
- Тарифы требуют дробных ставок — вводится отдельный тип `Rate` с явной шкалой,
  не смешиваемый с `Money`.
