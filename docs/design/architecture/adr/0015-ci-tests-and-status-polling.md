# ADR-0015: CI тестов и опрос результатов прогонов

## Статус

`accepted`, 2026-11-04. Владелец решения: пользователь-собственник. Согласовано с
владельцем 2026-11-04 в задаче доски `t-mw29vbip-ndi6ba`: выбран один job на
Ubuntu сейчас (матрица трёх ОС — позже), опрос результатов скриптом поверх `gh`,
фиксация решения этим ADR и добавление `check` в обязательные проверки после
первого зелёного прогона на `main`.

## Контекст

- В репозитории уже есть проверки: `pnpm check` = `pnpm validate` + `pnpm test`
  (`node --test`), тесты проверяют артефакты документации и сами проверки, включая
  негативные случаи. Локально `pnpm check` зелёный.
- Серверного прогона этих проверок нет: `.github/workflows/` отсутствует, поэтому
  PR в защищённый `main` не проверяется автоматически. [ADR-0014](0014-public-repo-and-enforced-rules.md)
  прямо отложил required status checks до появления CI; [ADR-0013](0013-repository-docs-and-versioning.md)
  выбрал GitHub Actions с матрицей macOS/Windows/Linux для будущего кода.
- Репозиторий публичный: стандартные GitHub-hosted раннеры бесплатны без лимита
  минут, включая macOS (ADR-0014). Секретов, пользовательских данных и сборки в
  проверках сейчас нет; CI не должен получать секреты.
- Проверки документации не зависят от ОС и от `third_party/`/`.dsh/skills`:
  в чистом клоне достаточно `pnpm install --frozen-lockfile` и `pnpm check`
  (`pnpm bootstrap` не нужен, он нужен только для скиллов и локальной разработки).
- Агентам и человеку нужен воспроизводимый способ **опрашивать** результаты CI:
  после пуша понять «ещё идёт / упало / зелёное», получить ссылку и логи для
  доработки. Ручной просмотр веб-интерфейса плохо подходит для цикла «прогон →
  исправление → повторный прогон».
- Ограничение GitHub: workflow для события `pull_request` берётся из ветки по
  умолчанию. Пока workflow нет в `main`, PR-проверки не запустятся; для проверки
  самого workflow нужен триггер `push` на ветку задачи.
- R-03 (нативная сборка `better-sqlite3` под три ОС) и E-12 (установщики) ещё
  впереди: сейчас тестировать под Windows/macOS нечего.

## Рассмотренные варианты

### Форма CI

#### 1. Один job `check` на Ubuntu для `pnpm check` (выбран)

Workflow `.github/workflows/ci.yml` запускает `pnpm install --frozen-lockfile` и
`pnpm check` на `ubuntu-latest`, Node.js 22, pnpm из поля `packageManager`.
Триггеры: push в любую ветку, PR в `main`, ручной запуск; параллельные прогоны
одной ветки отменяют друг друга.

**Плюсы:** минимальная стоимость и время; проверки не зависят от ОС; серверный
гейт появляется до кода приложения; `push` на ветку позволяет проверить сам
workflow и опрос, пока workflow нет в `main`.

**Минусы:** не ловит платформенные различия; матрицу придётся добавлять позже;
push в каждую ветку расходует минуты (на публичном репозитории — бесплатно).

#### 2. Сразу матрица Ubuntu/macOS/Windows

Тот же job в трёх экземплярах.

**Плюсы:** заранее закрывает R-03; одинаковая проверка на всех целевых ОС.

**Минусы:** сейчас тестируется только документация, платформенные различия
отсутствуют; macOS-прогоны заметно дольше; усложняет отладку без выигрыша;
матрица станет осмысленной с кодом приложения (E-01) и сборкой (E-12).

#### 3. Внешний CI (GitLab CI, CircleCI, self-hosted runner)

**Плюсы:** не зависит от GitHub Actions; self-hosted даёт полный контроль.

**Минусы:** второй аккаунт/интеграция и секреты; бесплатных macOS-раннеров на
GitLab.com нет (ADR-0013); self-hosted требует машины и обслуживания; ADR-0013
уже выбрал GitHub Actions как хостинг CI.

### Опрос результатов

#### 1. Скрипт `pnpm ci:status` поверх `gh` (выбран)

`scripts/ci-status.mjs` вызывает `gh run list`/`gh pr view`, выбирает свежий
прогон по ветке/коммиту/PR, печатает статус, итог, ссылку и подсказку
`gh run view <id> --log-failed`; умеет `--wait`, `--json` и возвращает коды
выхода 0/1/2/64. Авторизацию целиком берёт на себя `gh`.

**Плюсы:** одинаковый детерминированный ответ человеку и агенту; коды выхода
позволяют строить цикл доработок; не требует токенов в репозитории; одна
зависимость — уже используемый `gh`; тестируется юнит-тестами без сети.

**Минусы:** нужен установленный и авторизованный `gh`; скрипт — новый код,
который надо сопровождать; `gh` меняет JSON-поля между версиями (покрыто
тестами, но не контрактом).

#### 2. Только документированные команды `gh` без скрипта

**Плюсы:** ноль кода; любые команды `gh` доступны.

**Минусы:** каждый раз вручную собирать `gh run list --json` и разбирать вывод;
агент и человек получают разные форматы; нет стабильных кодов выхода для
автоматического цикла.

#### 3. Веб-интерфейс GitHub / уведомления

**Плюсы:** наглядно; ничего не настраивать.

**Минусы:** не автоматизируется, агент не может опросить результат, цикл
доработок остаётся ручным; не годится для «процесса доработок после тестирования».

## Решение

1. **CI — GitHub Actions, один job `check`.** Файл
   [`.github/workflows/ci.yml`](../../../../.github/workflows/ci.yml):
   `ubuntu-latest`, Node.js 22, pnpm из `packageManager`, шаги
   `pnpm install --frozen-lockfile` и `pnpm check`. Триггеры: `push` в любую
   ветку, `pull_request` в `main`, `workflow_dispatch`. Параллельные прогоны одной
   ветки отменяются (`concurrency`), права — только `contents: read`, таймаут
   15 минут. Имя job `check` — будущий контекст обязательной проверки.
2. **Матрица macOS/Windows/Linux и фильтры по путям откладываются** до появления
   кода приложения (E-01) и сборки установщиков (E-12), когда они начнут что-то
   проверять. До этого тестируются только артефакты документации, не зависящие
   от ОС. Добавление матрицы и path-фильтров не меняет процесс из этого ADR.
3. **Опрос результатов — `pnpm ci:status`** (`scripts/ci-status.mjs`) поверх
   авторизованного `gh`. Скрипт опрашивает последний прогон текущей ветки по
   умолчанию, поддерживает `--branch`, `--commit`, `--pr`, `--repo`, `--limit`,
   `--wait[=<сек>]`, `--timeout`, `--json`; печатает статус, итог, ссылку и
   подсказку для логов упавшего прогона. Коды выхода: `0` — успех, `1` — неуспех,
   `2` — прогон идёт или не найден, `64` — ошибка аргументов.
4. **Цикл доработок после тестов:** запушить ветку → `pnpm ci:status --wait` →
   при неуспехе `gh run view <id> --log-failed`, исправить, запушить снова.
   Локальный `pnpm check` перед пушем остаётся обязательным и повторяется в CI.
5. **`check` становится обязательным status check** в ruleset `protect-main`
   после первого зелёного прогона на `main`. Порядок важен: workflow для
   `pull_request` берётся из ветки по умолчанию, поэтому сначала PR с workflow
   мержится владельцем, затем проверка добавляется в ruleset. До этого PR
   остаётся под правилами ADR-0014 без required checks.
6. **Секретов в CI нет.** Workflow не использует секреты и не пишет в
   репозиторий; `pnpm bootstrap` в CI не запускается, потому что проверки не
   зависят от вендоренных скиллов. Артефакты прогона не публикуются: единственный
   результат — статус проверки и логи GitHub Actions.
7. **Документация процесса:** README и [AGENTS.md](../../../../AGENTS.md)
   описывают команду опроса и правило «зелёный CI до merge»; индекс ADR и карта
   решений обновлены этим изменением.

## Последствия

**Положительные:**

- Каждый PR и каждая ветка проверяются сервером, а не только локальной
  дисциплиной; падение проверок видно до merge.
- `pnpm check` остаётся единственной точкой входа: одинаково локально и в CI.
- Агент и человек получают одинаковый ответ об итоге прогона и коды выхода для
  автоматического цикла доработок.
- Требование ADR-0014 о required checks выполнено без изменения его текста.
- Публичный репозиторий делает стандартные прогоны бесплатными; секреты не
  задействованы, поверхность атаки минимальна.

**Отрицательные:**

- Push в любую ветку запускает прогон: при активной работе это лишние (хоть и
  бесплатные) минуты и шум в списке прогонов.
- Платформенные различия до E-01/E-12 не проверяются; Windows- и macOS-проблемы
  проявятся позже.
- Появляется зависимость от доступности GitHub Actions и от корректности `gh` в
  окружении агента.
- Обязательная проверка после её включения блокирует merge при падении тестов,
  включая случаи, когда падение не связано с содержанием PR (флаки).

## Условия пересмотра

- Появился код приложения (E-01) или началась сборка установщиков (E-12) —
  добавить матрицу macOS/Windows/Linux и фильтры по путям, обновив этот ADR или
  выпустив новый.
- Прогон `pnpm check` стабильно дольше 10–15 минут или упирается в лимиты
  GitHub Actions — разделить job'ы, включить кэш зависимостей или пересмотреть
  хостинг.
- Появились флаки, из-за которых обязательная проверка блокирует корректные PR, —
  стабилизировать тесты; при систематической проблеме пересмотреть набор
  обязательных проверок.
- Появились тесты, требующие секретов, сети или платформы (E2E, нативная сборка),
  — вынести их в отдельный job с явными правилами доступа, не смешивая с `check`.
- `gh` перестал быть доступен агентам или сменился хостинг CI — заменить
  реализацию опроса, сохранив коды выхода и формат ответа.
