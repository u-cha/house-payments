# ADR-0014: Публичный репозиторий и форсируемые правила `main`

## Статус

`accepted`, 2026-11-04. Владелец решения: пользователь-собственник. Согласовано с
владельцем 2026-11-04 (выбран вариант B — сделать репозиторий публичным вместо
платного плана). Уточняет пункт 5 ADR-0013 в части видимости репозитория.

## Контекст

- ADR-0013 выбрал монорепо, protected `main` и GitHub как remote; репозиторий был
  создан приватным.
- GitHub не форсирует rulesets и branch protection на приватных репозиториях
  личного аккаунта на плане Free: API репозитория отвечает
  `403 Upgrade to GitHub Pro or make this repository public to enable this feature`.
  То есть на Free + private серверного гейта нет — правила можно создать, но они
  не применяются.
- Гейт нужен до начала разработки, а не после: агенты и человек должны физически
  не мочь запушить в `main` мимо PR.
- Для CI трёх ОС (E-12, R-03) важна стоимость минут: macOS расходует минуты с
  множителем ×10. На публичных репозиториях стандартные GitHub-hosted раннеры
  бесплатны без лимита, на приватных Free — 2 000 минут/мес.
- В репозитории сейчас только проектная документация и инструменты: секретов,
  персональных данных и файлов пользователя нет. Приложение локальное, данные
  пользователя в репозиторий не попадают (C-01, C-04).

## Рассмотренные варианты

### 1. Публичный репозиторий (выбран)

Репозиторий `u-cha/house-payments` переводится в public; включаются rulesets.

**Плюсы:** rulesets и branch protection форсируются бесплатно; Actions-минуты
бесплатны без лимита, включая macOS и Windows (это снимает главный риск бюджета
CI); публичный код можно показывать и открывать для contributions; secret
scanning и push protection доступны на публичных репозиториях бесплатно.

**Минусы:** код и вся история (включая архив старой SaaS-проработки) видны всем;
случайно закоммиченный секрет станет публичным навсегда; форки и внешние PR
потребуют модерации; приватность продукта не гарантируется.

### 2. GitHub Pro с приватным репозиторием

**Плюсы:** репозиторий остаётся закрытым; rulesets форсируются; ~3 000 минут
Actions в месяц, macOS ×10.

**Минусы:** платно (~$4/мес); лимит минут на сборку под три ОС может стать узким
местом при активном CI; для одного разработчика платить только за гейт — не
лучшее соотношение цены и пользы.

### 3. Остаться на Free + private с локальным хуком

**Плюсы:** бесплатно, репозиторий закрыт.

**Минусы:** серверного гейта нет; `pre-push` обходится `--no-verify`, сменой
`core.hooksPath` или пушем с другой машины; PR-гейт и обязательные проверки
невозможны; дисциплина агентов остаётся единственной защитой. Отклонён как
основной механизм (может быть дополнением).

### 4. Организация на GitHub Team

**Плюсы:** форсируются rulesets; репозиторий может быть приватным.

**Минусы:** та же цена за пользователя, плюс организация, роли и лишняя
административная обвязка для проекта одного человека; предупреждение GitHub
предлагает Team как апселл, но Pro даёт тот же гейт для личного репозитория.
Отклонён.

## Решение

1. **Видимость:** репозиторий `u-cha/house-payments` — **public** с 2026-11-04.
   Это осознанный обмен приватности на форсируемый гейт и бесплатные минуты CI.
2. **Ruleset `main-protection`** (branch, enforce active, target `main`):
   - Require a pull request before merging — обязателен, approvals **0** (владелец
     один и не может одобрить собственный PR);
   - Require linear history — только squash/rebase, без merge-коммитов;
   - Block force pushes (`non_fast_forward`) и Block deletions;
   - администратор **не** в списке обхода: прямой push в `main` запрещён всем,
     включая агентов, работающих под аккаунтом владельца; чтобы изменить правила,
     владелец редактирует ruleset в настройках, а не пушит в обход;
   - Required status checks добавляются, когда появится CI (E-12) и названия
     job'ов станут стабильными.
3. **Ruleset `release-tags`** (tag, target `v*`): запрет удаления и перемещения
   тегов — выпущенные версии неизменяемы.
4. **CI (E-12)** строится на GitHub Actions: публичный репозиторий даёт бесплатные
   минуты стандартных раннеров, поэтому матрица macOS/Windows/Linux допустима;
   job'ы фильтруются по путям, чтобы правки `docs/` не запускали сборку.
5. **Секреты и PII:** в репозитории не хранятся секреты, токены, сертификаты,
   файлы пользователя и образцы реальных квитанций. Публичность истории означает,
   что ошибочно закоммиченный секрет считается раскрытым — его нужно отзывать, а
   не только удалять из истории. Для страховки включаются secret scanning и push
   protection (бесплатны для публичных репозиториев).
6. **Процесс из ADR-0013 не меняется:** ветки по задачам, Conventional Commits,
   PR, squash-merge, теги `vX.Y.Z`, документация версионируется вместе с кодом.
   Пункт 5 ADR-0013 в части «приватный репозиторий» заменяется этим решением;
   остальные пункты ADR-0013 действуют.

## Последствия

**Положительные:**

- Прямой push в `main` невозможен для всех — гейт работает на сервере, а не на
  дисциплине.
- CI под три ОС не упирается в лимит минут; macOS-матрица становится доступной.
- Secret scanning и push protection бесплатны; случайная утечка ловится до пуша.
- Правила видны всем читателям репозитория — прозрачная история решений.

**Отрицательные:**

- Код, документация и архив видны публично; приватность проекта ограничена.
- Merge в `main` теперь только через PR — даже мелкая правка требует ветки и PR
  (для агентов это норма, для владельца — лишний шаг).
- Владелец не может одобрить свой PR; approvals = 0, поэтому содержательное
  ревью остаётся человеческим решением, а не блокировкой.
- Внешние форки и PR потребуют внимания, если проект станет популярным.
- Вся история коммитов публична: персональные данные, случайно попавшие в
  коммиты, придётся вычищать из истории.

## Условия пересмотра

- Появилась необходимость закрыть код (коммерциализация, секреты, партнёры) —
  перейти на GitHub Pro/Team или self-hosted и вернуться к приватному режиму.
- Появился второй человек с правом merge — поднять required approvals до 1 и
  включить CODEOWNERS.
- CI упирается в лимиты или публичные ранеры недоступны — пересмотреть хостинг,
  сохранив матрицу трёх ОС.
- В репозиторий понадобится добавить реальные образцы квитанций или данные
  пользователя — вынести их из репозитория (fixtures без PII) и перепроверить
  публичность.
- GitHub меняет условия планов или правила rulesets — пересмотреть механизм
  (ADR-0013, вариант 2).
