# ADR-0003: Квитанция, платёж и распределение — отдельные сущности

## Статус

`proposed`, 2026-11-04. Владелец решения: пользователь-собственник.

## Контекст

- C-02, C-03; FR-06, FR-07, FR-08; INV-05…INV-09.
- Один платёж в банке часто закрывает несколько квитанций (ЖКХ, содержание,
  капремонт), а квитанция может быть оплачена частями.
- Переплата не должна «сгорать»: она остаётся на лицевом счёте как аванс.
- Квитанция — документ с неизменяемым после фиксации содержимым (ADR-0007).

Силы: простота интерфейса (тянет к «платёж = оплата квитанции»), корректность
(тянет к разделению), отчётность (тянет к движению по лицевому счёту).

## Рассмотренные варианты

### 1. Три сущности: `invoice`, `payment`, `allocation` (выбран)

**Плюсы:** частичная оплата и переплата выражаются естественно; один платёж
закрывает несколько квитанций; история распределений — часть аудита; квитанция
остаётся неизменяемой.

**Минусы:** больше связей и агрегатов; распределение нужно поддерживать при сторно;
UI обязан объяснять «платёж → распределения».

### 2. Платёж ссылается на квитанцию напрямую

**Плюсы:** простая модель; один платёж — одна квитанция.

**Минусы:** не выражает частичную оплату и один платёж на несколько квитанций;
переплата теряется или требует отдельного поля; исправление ломает историю.
Отклонён.

### 3. Распределение внутри платежа как JSON-поле

**Плюсы:** меньше таблиц.

**Минусы:** нельзя запросить «остаток квитанции» без разбора JSON; нет ссылочной
целостности и уникальности; аудит распределений невозможен. Отклонён.

### 4. Полноценный двойной учёт (проводки, счета, дебет/кредит)

**Плюсы:** универсально, знакомо бухгалтерам.

**Минусы:** для личного учёта избыточно; пользователь не должен думать проводками;
усложняет UI и валидацию. Отклонён как преждевременный.

## Решение

1. `invoice` — квитанция за период с суммой и сроком; после фиксации не
   редактируется (ADR-0007).
2. `payment` — факт уплаты; не привязан к квитанции; имеет `idempotency_key`.
3. `allocation` — отнесение суммы платежа на квитанцию; сумма по платежу не больше
   платежа (INV-07), по квитанции — не больше остатка (INV-08); пара
   «платёж — квитанция» уникальна среди активных строк.
4. Остаток квитанции вычисляется как `total_minor − SUM(активных allocation)`, а
   агрегат по лицевому счёту поддерживается в `balance` в той же транзакции (INV-10).
5. Неразнесённый остаток платежа — аванс (`balance.advance_minor`), а не отдельная
   «переплата по квитанции».
6. Автоматическое распределение — FIFO по сроку оплаты, затем по периоду; ручное —
   явный выбор квитанции. Ручной платёж сохраняется сразу вместе с выбранными
   распределениями (INV-22); неразнесённый остаток — аванс.
7. Отмена распределения — обратная запись (`allocation.reversed_at` + причина),
   возвращающая деньги в аванс; она нужна, чтобы аннулировать квитанцию по INV-06.

## Последствия

**Положительные:**

- Один платёж закрывает несколько квитанций, частичная оплата и аванс работают
  без специальных полей.
- Распределения видны в аудите и отчётах; историю можно восстановить.
- Квитанция не меняется после фиксации — доверие к документам.

**Отрицательные:**

- Транзакция распределения блокирует лицевой счёт; конкурентный доступ требует
  повторной попытки (INV-07, QS-04).
- Сторно квитанции с распределениями запрещено (INV-06): сначала нужно отменить
  распределение или вернуть деньги.
- UI сложнее: нужно показывать и платёж, и его распределения.

**Требующие дисциплины:** любое изменение распределений проходит через `ledger`;
`invoicing.ApplySettlement` обновляет только статус/оплаченную информацию, но не
`total_minor` (INV-05); баланс не пересчитывается «кнопкой», только транзакцией.

## Условия пересмотра

- Продукт сводится к «оплата одной квитанции» без частичных платежей — модель можно
  упростить, но не в первой версии.
- Появляется совместное владение с другими людьми и разделение расходов по долям —
  распределение получает измерение «кто платил» и «на кого относится».
- Нужен бухгалтерский экспорт с проводками — добавляется маппинг на счета, модель
  остаётся.
