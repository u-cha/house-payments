# ADR-0004: Идемпотентность импорта и повторных операций

## Статус

`proposed`, 2026-11-04. Владелец решения: пользователь-собственник.

## Контекст

- C-05: импорт, повторные операции и будущая синхронизация обязаны быть
  идемпотентными.
- FR-05, FR-07, FR-16; QS-03; INV-13.
- В будущем пользователь импортирует выгрузку из личного кабинета поставщика и
  часто повторяет импорт после ошибки или не помнит, загружал ли файл. Импорт CSV
  отложен после первой версии (R-06), но правило идемпотентности остаётся для
  платежей и будущего импорта.
- Будущая синхронизация (ADR-0011) будет доставлять изменения повторно.

Силы: простота (тянет к «импортировать как есть»), корректность (тянет к
дедупликации), доверие пользователя (тянет к «ничего не задвоилось»).

## Рассмотренные варианты

### 1. Ключ операции + `batchKey` импорта (выбран)

Для платежа — `idempotency_key` (UUIDv7 или детерминированный ключ), для импорта —
`batchKey` (хеш файла и параметров) плюс `external_ref` строки.

**Плюсы:** повтор возвращает результат первого выполнения; не требует доверия к
сумме и дате; работает для будущей синхронизации.

**Минусы:** клиент обязан генерировать ключ; при ручном вводе ключ создаётся
приложением; нужна очистка старых ключей.

### 2. Дедупликация по сумме, дате и лицевому счёту

**Плюсы:** не требует ключей; работает «само».

**Минусы:** два реальных одинаковых платежа в один день ошибочно схлопываются;
разные квитанции с одинаковой суммой путаются. Отклонён.

### 3. Без дедупликации, ручная проверка

**Плюсы:** ноль сложности.

**Минусы:** повторный импорт создаёт дубли; пользователь не заметит; прямой
конфликт с C-05 и QS-03. Отклонён.

### 4. Полный журнал операций с идемпотентным воспроизведением (event sourcing)

**Плюсы:** максимальная воспроизводимость.

**Минусы:** избыточно для личного приложения; усложняет модель и UI. Отклонён,
хотя журнал изменений (ADR-0005) частично закрывает потребность.

## Решение

1. Каждая операция создания платежа несёт `idempotency_key`, уникальный в файле
   данных. Повтор с тем же ключом возвращает существующий платёж и не создаёт
   нового (INV-13).
2. Импорт начислений несёт `batchKey` — хеш содержимого файла и параметров импорта;
   ключ сохраняется в `import_job.batch_key`. Повторный импорт того же файла
   возвращает тот же отчёт и не создаёт записей.
3. Каждая импортируемая строка имеет `external_ref`; частичная уникальность
   `(account_id, service_id, period) WHERE reversal_of IS NULL` не даёт дубля даже
   при другом файле; `reversal_of` уникален и ссылается на исходное начисление.
4. Отчёт импорта перечисляет каждую строку в одной из категорий: `created`,
   `duplicate`, `rejected`; число строк в отчёте равно числу строк файла.
5. Ключи не переиспользуются; при очистке по возрасту сохраняется аудит и журнал.
   Ручной платёж создаётся сразу с распределением (INV-22).

## Последствия

**Положительные:**

- Повторный импорт безопасен; пользователь может не бояться нажать «ещё раз».
- Дедупликация не зависит от суммы и даты — реальные одинаковые платежи не
  схлопываются.
- Та же механика пригодится синхронизации.

**Отрицательные:**

- Нужно хранить ключи и следить за их уникальностью.
- Клиентский код обязан генерировать ключ; при ручном вводе это делает приложение.
- Хеш файла требует чтения файла целиком (приемлемо для CSV до десятков тысяч строк).

**Запрещено:** считать отсутствие ключа «нормальным» и вставлять запись без
проверки; молча пропускать дубликаты без строки в отчёте.

## Условия пересмотра

- Внешний источник начнёт давать стабильные идентификаторы строк — `external_ref`
  становится основным ключом, `batchKey` — вспомогательным.
- Появится синхронизация (ADR-0011) — ключи операций переезжают в журнал изменений.
- Объём импорта превысит 100 000 строк — хеширование файла заменяется
  потоковым и частичным.
