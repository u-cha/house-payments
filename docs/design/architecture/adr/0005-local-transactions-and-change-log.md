# ADR-0005: Локальная транзакция и журнал изменений вместо распределённых событий

## Статус

`proposed`, 2026-11-04. Владелец решения: пользователь-собственник.

## Контекст

- C-01, C-05, C-06; FR-05…FR-17; QS-04, QS-06; INV-17, INV-18.
- Финансовая операция меняет несколько таблиц: платёж, распределение, баланс,
  аудит, журнал. Это обязано быть атомарно.
- Отчёты и напоминания — производные: их можно пересчитать, но нельзя терять.
- Синхронизация в будущем (ADR-0011) требует журнала изменений с порядком и
  идентификатором устройства.
- Внешнего брокера нет и не будет: приложение локальное.

Силы: атомарность (тянет к одной транзакции), отзывчивость (тянет к асинхронной
обработке), будущая синхронизация (тянет к журналу), простота (тянет к прямым
вызовам).

## Рассмотренные варианты

### 1. Одна транзакция + append-only журнал изменений (выбран)

Use case пишет состояние, аудит и `change_log` в одной транзакции; после коммита
внутрипроцессный диспетчер уведомляет подписчиков (отчёты, напоминания).

**Плюсы:** нет dual-write; события не теряются; журнал готов к синхронизации;
подписчики идемпотентны и не влияют на транзакцию.

**Минусы:** журнал растёт и требует очистки; подписчики могут отставать;
дублирующая обработка при повторном запуске.

### 2. Прямые синхронные вызовы между модулями

**Плюсы:** просто и предсказуемо.

**Минусы:** отчёты и напоминания удлиняют финансовую транзакцию; связанность
модулей растёт; нет истории изменений для синхронизации. Отклонён как основной
механизм (допустим только через явный порт владельца).

### 3. Event sourcing как единственный источник состояния

**Плюсы:** полная история; воспроизводимость.

**Минусы:** избыточно для личного приложения; сложные миграции событий; UI
запрашивает проекции; риск ошибки в проекции. Отклонён.

### 4. Синхронизация копированием файла (облачная папка)

**Плюсы:** нулевая разработка.

**Минусы:** конфликты копий файла SQLite приводят к повреждению или потере данных;
нет порядка изменений. Отклонён и запрещён.

## Решение

1. Каждая операция записи выполняется в одной транзакции SQLite (WAL): состояние +
   `audit_event` + `change_log`.
2. `change_log` — append-only: `entity_type`, `entity_id`, `operation`,
   `payload_json`, `device_id`, `logical_clock`, `occurred_at`, `synced_at`.
   Уникальность `(entity_type, entity_id, logical_clock)` (INV-18).
3. `logical_clock` — монотонный счётчик в границах сущности; при синхронизации
   сравниваются часы и `device_id`, а не настенные часы.
4. После коммита диспетчер уведомляет подписчиков (`reporting`, `reminders`).
   Подписчики идемпотентны, читают только опубликованные контракты и не пишут в
   чужие таблицы.
5. Межмодульные изменения внутри транзакции — только через явный порт владельца
   (например, `invoicing.ApplySettlement` из `ledger`); всё остальное — журнал.
6. Очистка журнала — по возрасту и только для записей, уже синхронизированных
   (или всех, если синхронизация выключена); аудит не удаляется.

## Последствия

**Положительные:**

- Атомарность финансовых операций без распределённых протоколов.
- События и аудит не могут «разойтись» с состоянием.
- Журнал даёт готовую основу для синхронизации без переделки модели.
- Отчёты и напоминания не удлиняют критическую транзакцию.

**Отрицательные:**

- Журнал растёт; нужна политика очистки и архивации.
- Подписчики могут отставать; UI должен показывать «данные на момент».
- Повторная обработка требует идемпотентности подписчиков.

**Требующие дисциплины:** ни один use case не пишет состояние без записи в
`change_log`; `payload_json` версионируется; секреты и PII в журнал не попадают.

## Условия пересмотра

- Включается синхронизация (ADR-0011) — выбирается транспорт и политика
  конфликтов; структура журнала уже готова.
- Журнал превышает 5 лет или 200 000 записей — вводится архивация; порог
  фиксируется отдельным триггером (T-12) при появлении реальных данных.
- Появляется второй процесс-писатель — пересматривается модель конкурентного
  доступа (сейчас один писатель).
