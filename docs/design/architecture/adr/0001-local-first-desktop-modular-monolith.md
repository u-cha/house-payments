# ADR-0001: Локальное настольное приложение как модульный монолит

## Статус

`proposed`, 2026-11-04. Владелец решения: пользователь-собственник. До принятия
описывает предлагаемый стиль, а не факт.

## Контекст

- A-01: продукт — для частного лица, собственника помещений. Пользователь один,
  вместе с ним — члены семьи на одном устройстве.
- C-01: приложение работает офлайн, данные лежат в файле на устройстве.
- C-06: стек — TypeScript, Electron, React, SQLite; модульный монолит.
- QS-08: 100 % функций доступны без сети, запуск ≤ 3 с. QS-07: восстановление из
  резервной копии без администратора.
- Финансовые операции (платёж + распределение + баланс + аудит) обязаны быть
  атомарны (INV-07…INV-10, INV-17); распределённые протоколы здесь не нужны и
  только повышают риск.
- Пользователь не должен знать, что такое Docker, сервер или администратор БД.

Силы: простота установки (тянет к одному приложению), целостность данных (тянет к
одной транзакционной БД), доступ с телефона (тянет к серверу), цена сопровождения
(тянет к отсутствию инфраструктуры).

## Рассмотренные варианты

### 1. Локальное настольное приложение, модульный монолит (выбран)

Один установщик; main-процесс с модулями и одной SQLite; renderer — тонкий UI;
никакого сервера.

**Плюсы:** работает офлайн; данные у пользователя; ACID без сети; нет хостинга и
подписок; установка обычным установщиком; простое восстановление копированием
файла; QS-08 и QS-07 достижимы без DevOps.

**Минусы:** данные доступны только на одном устройстве; обновления ставит
пользователь; резервные копии — ответственность пользователя; нет общего доступа
с родственниками с другого устройства; размер приложения больше, чем у веб-версии.

### 2. Облачный SaaS с веб-интерфейсом

Сервер, PostgreSQL, аккаунты, доступ с любого устройства.

**Плюсы:** доступ отовсюду; централизованные обновления и бэкапы; проще совместное
ведение.

**Минусы:** нужен сервер, хостинг, администрирование и оплата; данные пользователя
хранятся у третьей стороны; требуется защита аккаунтов и соответствие требованиям
к персональным данным; для одного пользователя это инфраструктура без выгоды;
противоречит C-01.

### 3. Локальный демон + браузерный интерфейс

Фоновый сервис на устройстве, UI в браузере, база на диске.

**Плюсы:** UI-технологии как у веб-приложения; возможен доступ с другого устройства
в домашней сети.

**Минусы:** два процесса и порт на localhost; вопросы безопасности и автозапуска;
пользователь видит «сервер», который надо чинить; установка сложнее, чем один
установщик; нет выгоды по сравнению с вариантом 1.

### 4. Файловая «таблица» без приложения

Электронная таблица или документ с формулами.

**Плюсы:** нулевая стоимость разработки.

**Минусы:** нет инвариантов, аудита, напоминаний, вложений и защиты; ошибки в
формулах не отслеживаются; не масштабируется по функциям из брифа. Отклонён как
несовместимый с требованиями.

## Решение

Принимается **локальное настольное приложение с модульным монолитом**:

1. Один установленный пакет Electron; main-процесс содержит домен и use cases,
   renderer — только UI. Renderer не имеет доступа к файловой системе и БД.
2. Одна база SQLite в файле данных пользователя, режим WAL, один писатель.
   Модули владеют таблицами; прямой доступ к чужим таблицам запрещён.
3. Модуль экспортирует только `api.ts` (use case, события, DTO). Зависимости —
   `shared` и публичные контракты; циклы запрещены и проверяются тестом.
4. Межмодульные изменения в одной транзакции допускаются только через явный порт
   владельца данных (ADR-0005); всё остальное — через журнал изменений после коммита.
5. Синхронизация между устройствами не входит в первую версию, но модель к ней
   готова: UUIDv7, `device_id`, `change_log`, append-only аудит (ADR-0011).

## Последствия

**Положительные:**

- Финансовые операции атомарны локально, без саг и компенсаций.
- Нет сервера, хостинга, Docker и администрирования — установка сводится к
  установщику, восстановление — к копии файла.
- Работа без интернета и без подписки; данные остаются у пользователя.
- Один язык (TypeScript) и один процесс упрощают онбординг (QS-10).

**Отрицательные:**

- Данные живут на одном устройстве; перенос — вручную (FR-16).
- Обновления распространяются через установщик; нужна подпись пакетов (ADR-0009).
- Резервное копирование — обязанность пользователя, которую приложение должно
  делать заметной (QS-07).
- Общий домен отказа: ошибка в main-процессе роняет приложение; частично
  компенсируется отдельными процессами Electron и восстановлением из копии.

**Требующие дисциплины:**

- Renderer не должен «помогать» считать деньги: все вычисления — в ядре.
- Любая операция записи обязана проходить через use case и транзакцию.
- Новые сущности получают UUIDv7 и запись в `change_log` с первого дня, иначе
  будущая синхронизация потребует миграции.

## Условия пересмотра

- Появляется требование постоянного доступа с нескольких устройств (T-07) —
  включается ADR-0011, стиль остаётся локальным с синхронизацией.
- Размер файла > 2 ГБ или время открытия > 2 с после сжатия вложений (T-01, T-02) —
  пересматривается физическая организация, не стиль.
- Требуется совместное ведение с людьми вне семьи — пересматривается модель
  доступа и, возможно, появляется серверный контур.
- Нужен мобильный клиент как основной — пересматривается ADR-0009 и ADR-0010.
