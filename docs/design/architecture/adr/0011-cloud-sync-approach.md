# ADR-0011: Подход к синхронизации с облаком (зона развития)

## Статус

`proposed`, 2026-11-04. Владелец решения: пользователь-собственник. Первая версия
синхронизацию **не включает**; решение фиксирует, как модель к ней готовится.

## Контекст

- FR-17: синхронизация между устройствами — после первой версии.
- Пользователь хочет заложить возможность синхронизации сразу: «если приложением
  будет пользоваться несколько членов семьи».
- ADR-0001 — локальное приложение; ADR-0005 — журнал изменений; ADR-0008 — один
  файл; C-05 — идемпотентность; C-04 — защита персональных данных.
- Синхронизация «потом» не должна требовать переписывания модели и пересчёта
  идентификаторов.

Силы: простота первой версии (тянет к отсутствию синхронизации), будущая
многодевайсность (тянет к журналу и конфликтам), сохранность (тянет к серверу),
приватность (тянет к шифрованию).

## Рассмотренные варианты

### 1. Журнал изменений + сервер-ретранслятор (выбран как направление)

Каждое устройство пишет `change_log`; сервер хранит журнал и раздаёт изменения
другим устройствам по курсору; вложения — по `sha256`.

**Плюсы:** модель уже готова; не нужен CRDT для финансовых документов; можно
включить позже без миграции данных; понятная диагностика.

**Минусы:** нужен сервер и аккаунт; конфликты правок справочников нужно разрешать;
приватность зависит от шифрования на сервере.

### 2. Синхронизация через облачную папку (файл SQLite в Dropbox/OneDrive)

**Плюсы:** нулевая разработка.

**Минусы:** одновременная запись двух устройств повреждает файл; конфликтные копии
не сводятся; нет порядка изменений. Отклонён и запрещён.

### 3. CRDT (бесконфликтные типы данных) с первого дня

**Плюсы:** офлайн-правки сливаются автоматически.

**Минусы:** финансовые документы и так append-only; CRDT усложняет модель, аудит и
отладку; избыточно для семьи. Отклонён для первой версии.

### 4. Серверная БД как единственный источник истины

**Плюсы:** нет конфликтов; централизованный бэкап.

**Минусы:** противоречит C-01 (офлайн и локальные данные); требует постоянной сети;
ломает модель первой версии. Отклонён.

## Решение

1. **В первой версии синхронизация выключена.** Приложение не делает сетевых
   запросов, кроме проверки обновлений (ADR-0009).
2. **Модель готова к синхронизации:**
   - идентификаторы — UUIDv7 (глобально уникальны, сортируемы);
   - `device_id` у каждой записи журнала;
   - `change_log` append-only с `logical_clock` в границах сущности;
   - финансовые документы неизменяемы или исправляются сторно (ADR-0007), поэтому
     конфликтов «двух правок одного поля» почти нет;
   - вложения адресуются по `sha256` и неизменяемы — синхронизируются как контент.
3. **Транспорт (когда включим):** сервер-ретранслятор журнала; каждое устройство
   хранит курсор последней полученной записи; повторная доставка безопасна
   (INV-18); сервер не является источником истины, а только пересылает изменения.
4. **Конфликты:**
   - финансовые документы — append-only, конфликт невозможен; при расхождении
     баланса выполняется пересчёт из журнала и показывается предупреждение;
   - справочники (помещение, поставщик, тариф) — последняя запись по
     `logical_clock` и `device_id`; при равных часах — детерминированное сравнение
     `device_id`; пользователь видит историю и может исправить;
   - удаление — только tombstone-запись в журнале, физического удаления нет.
5. **Приватность:** синхронизируемые данные шифруются на устройстве; ключ — у
   пользователя; сервер хранит зашифрованные блобы и метаданные маршрутизации.
6. **Границы:** синхронизация не входит в критерии приёмки первой версии; при её
   включении оформляется новый ADR с политикой хранения на сервере и SLA.

## Последствия

**Положительные:**

- Включение синхронизации не потребует переделки модели и миграции идентификаторов.
- Финансовые конфликты сведены к минимуму самой моделью (append-only).
- Вложения не дублируются благодаря `sha256`.
- Первая версия остаётся простой и офлайн.

**Отрицательные:**

- Журнал и tombstone-записи нужно поддерживать с первого дня, даже без сервера.
- Справочники требуют политики конфликтов, которую нельзя проверить до включения.
- Сервер и шифрование — отдельная стоимость и ответственность.
- Пользователь может ожидать синхронизацию раньше, чем она появится; нужно
  честно указывать статус в UI.

**Запрещено:** синхронизировать файл SQLite через облачную папку; переиспользовать
идентификаторы; физически удалять синхронизированные записи; включать сеть без
явного согласия пользователя.

## Условия пересмотра

- Пользователь решает включить синхронизацию (OQ-04) — новый ADR: сервер,
  аутентификация, шифрование, политика хранения.
- Появляется более двух устройств на семью (T-07) — проверить конфликты и курсоры.
- Требуется совместное ведение с людьми вне семьи — пересматривается модель
  владения и ролей (ADR-0006).
- Серверная политика хранения противоречит C-04 — синхронизация ограничивается
  шифрованными блобами без метаданных.
