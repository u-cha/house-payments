# ADR-0007: Неизменяемая зафиксированная квитанция, исправление через сторно

## Статус

`proposed`, 2026-11-04. Владелец решения: пользователь-собственник.

## Контекст

- FR-06; INV-03, INV-05, INV-06, INV-11; ADR-0003.
- Квитанция — документ, по которому пользователь сверяется с поставщиком и
  банком. Если её можно молча переписать, история платежей теряет смысл.
- Ошибки в начислениях бывают: неверный тариф, дубль, не тот период.
- Пользователь должен видеть, что было исправлено и почему.

Силы: удобство (тянет к правке на месте), доверие (тянет к неизменяемости),
простота (тянет к удалению ошибочной записи).

## Рассмотренные варианты

### 1. Неизменяемая зафиксированная квитанция + сторно (выбран)

После `issued` содержимое не меняется; ошибка исправляется сторно начислений или
аннулированием квитанции без распределений, затем создаётся новая.

**Плюсы:** история достоверна; аудит осмыслен; можно объяснить любое расхождение.

**Минусы:** больше записей; UI обязан показывать пары «документ — сторно»;
пользователь делает лишний шаг.

### 2. Правка на месте с записью в аудит

**Плюсы:** быстро; одна запись.

**Минусы:** прошлое состояние не восстановить; нельзя доказать, что было; аудит
фиксирует факт, но не содержание. Отклонён.

### 3. Мягкое удаление (`deleted_at`)

**Плюсы:** просто скрыть ошибку.

**Минусы:** удалённая квитанция влияет на баланс непрозрачно; нет причины
исправления; отчёты требуют фильтра везде. Отклонён.

### 4. Полное версионирование документов

**Плюсы:** любая версия доступна.

**Минусы:** избыточно для личного учёта; сложнее модель и UI; сторно уже даёт
необходимую прослеживаемость. Отклонён как преждевременный.

## Решение

1. `invoice` имеет состояния `draft`, `issued`, `partially_paid`, `paid`, `void`.
   В `draft` допустима правка; после `issued` — только чтение.
2. Сумма квитанции равна сумме строк (INV-05); при фиксации проверяется.
3. Аннулирование (`void`) разрешено только без распределений (INV-06); причина
   обязательна и попадает в аудит.
4. Ошибочное начисление исправляется сторно: создаётся связанная обратная запись с
   `reversal_of`, исходная остаётся (INV-11). Повторное сторно запрещено.
5. Исправленная квитанция создаётся заново за тот же период (частичный
   уникальный индекс по INV-03); в интерфейсе документы связаны. Оплата отражается
   статусом и оплаченной информацией, но не меняет `total_minor`.
6. Все переходы состояний пишут `audit_event` и `change_log` в одной транзакции.

## Последствия

**Положительные:**

- История квитанций и платежей восстанавливается полностью.
- Пользователь может объяснить поставщику или банку любое расхождение.
- Баланс всегда выводится из неизменяемых записей.

**Отрицательные:**

- Объём записей растёт; сторно-пары нужно показывать в UI.
- Исправление ошибки — два-три действия вместо одного.
- Отчёты обязаны корректно исключать сторнированные суммы.

**Запрещено:** `UPDATE` полей `issued`-квитанции; удаление квитанции; аннулирование
оплаченной квитанции; повторное сторно.

## Условия пересмотра

- Появится требование юридически значимого архива (OQ-05 переоткрывается) —
  добавляется версия и подпись, сторно остаётся.
- Появится совместное ведение с поставщиком — стороны обмениваются неизменяемыми
  документами, модель совместима.
- Практика покажет, что сторно слишком дорого для типовых ошибок — можно добавить
  «черновик» с явным сроком жизни, не трогая `issued`.
