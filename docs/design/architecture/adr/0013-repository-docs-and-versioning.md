# ADR-0013: Репозиторий, хранение документации и процесс ведения git

## Статус

`accepted`, 2026-11-04. Владелец решения: пользователь-собственник. Согласовано с
владельцем в сессии «вести гит» 2026-11-04 (выбран вариант 1 — один репозиторий);
до этого решение вынесено на ревью с тремя вариантами.

## Контекст

- До этого решения у проекта не было системы контроля версий: проектные артефакты
  (`docs/design/`, 39 файлов), архив прежней проработки и инструменты проверок
  существовали только на диске. Любая правка была необратима, историю решений
  нельзя было восстановить, а потеря каталога означала потерю проекта.
- Разработка ещё не начата (код появится в E-01), поэтому структуру репозитория
  можно выбрать без миграции истории.
- Нужен удалённый репозиторий: CI под три ОС (R-03, E-12) требует хостинга с
  раннерами macOS/Windows/Linux; стабильная версия и развитие должны иметь
  воспроизводимые точки (теги).
- Пользователь не знаком с тем, как это устроено в DSH; решение должно быть
  простым, объяснимым и не требовать ручной синхронизации двух деревьев.
- Ограничения DSH: один воркспейс — один корень каталога; задачи доски привязаны к
  проекту-воркспейсу; файловая песочница сессии ограничена этим корнем; изоляция
  задач в режиме `worktree` умеет корневой репозиторий и вложенные независимые
  репозитории.
- В каталоге уже есть `third_party/` — три частичных git-клона чужих скиллов,
  которые не должны попасть в репозиторий, но должны восстанавливаться.

Силы: простота и сохранность (тянут к одному репозиторию), чистота истории
продукта (тянет к разделению дизайна и кода), сквозные изменения «решение + код»
(тянут к одному корню), стоимость сопровождения (тянет к меньшему числу
репозиториев).

## Рассмотренные варианты

### 1. Один репозиторий (монорепо): воркспейс = репозиторий продукта (выбран)

Документация — `docs/`, код — `apps/desktop` (и будущие `packages/`), архив —
`archive/`. Один remote, один CI, один тег на версию; код и решения
версионируются вместе.

**Плюсы:** одно дерево и одна история; сквозное изменение «ADR + код» — один PR;
документация не может «отстать» от кода, потому что тег один; минимальная
церемония для одного разработчика и агентов; `pnpm check` проверяет документацию
рядом с кодом; изоляция задач DSH работает по одному корневому репозиторию.

**Минусы:** в репозитории продукта остаются дизайн-артефакты и архив прежней
проработки; CI нужно фильтровать по путям, чтобы правка документа не запускала
сборку установщиков; если когда-нибудь понадобится открыть код отдельно от
дизайн-истории, потребуется выделение истории.

### 2. Два репозитория: дизайн в корне, код — вложенный независимый репозиторий

Корень — репозиторий дизайна и документации; `app/` — отдельный git-репозиторий
исходников со своим remote и CI. DSH умеет зеркалить оба репозитория при
изоляции задач.

**Плюсы:** чистая история продукта; CI только по коду; репозиторий кода можно
открыть, не публикуя архив и историю дизайна.

**Минусы:** два remote и два git-контекста; сквозное изменение — два коммита и
два PR; связь версий кода и документации — соглашением (тег кода + sha
документации в release notes), а не свойством системы; после свежего клона нужен
bootstrap-скрипт, который клонирует вложенный репозиторий (родительский git его
игнорирует); `git clean -xdf` в корне уничтожает вложенный репозиторий; агенты
чаще путают, в каком из двух репозиториев коммит.

### 3. Два отдельных воркспейса DSH: дизайн и код — разные проекты

`/DSH-Projects/house-payments` — дизайн, `/DSH-Projects/house-payments-app` — код,
у каждого своя доска задач и песочница.

**Плюсы:** жёсткая граница: сессия дизайна физически не может изменить код;
естественное разделение CI и прав.

**Минусы:** две доски задач и два проекта вместо одного; сквозная задача «решение
+ реализация» не выполняется в одном проекте (нужны две задачи и ручная связка);
из дизайн-воркспейса нельзя запустить тесты кода; документация и код снова
расходятся по версиям, как в варианте 2.

### 4. Только локальный git без remote

**Плюсы:** ничего не публикуется, настройка минимальна.

**Минусы:** нет резервной копии вне машины, нет CI под три ОС (R-03), нет
возможности смотреть PR и стабильные теги на GitHub. Отклонён.

## Решение

1. **Один репозиторий = DSH-воркспейс** `/Users/grandpraline/DSH-Projects/house-payments`;
   все задачи ведутся в одном проекте доски. Структура:
   - `docs/design/` — проектные артефакты и ADR (источник истины по решениям);
   - `archive/` — прежние проработки, не действующие;
   - `apps/desktop/` — код приложения с E-01 (Electron: `src/main/modules/…`,
     `src/preload/`, `src/renderer/`), `apps/*/` и `packages/*/` — будущие пакеты;
   - `scripts/`, `tests/` — проверки артефактов и рендер диаграмм;
   - `third_party/` — не коммитится, восстанавливается `pnpm bootstrap`.
2. **Документация хранится в этом же репозитории** в `docs/` и версионируется тем
   же тегом, что код: релизный тег фиксирует одновременно состояние кода и
   документации, поэтому они не могут разъехаться. Пользовательская документация
   появится в `docs/user/` в E-12. Диаграммы — из `.mmd`/`.dbml`; `.svg`/`.png` —
   производные, не коммитятся. ADR после принятия не переписываются: новое
   решение — новый ADR со ссылкой «Заменяет: ADR-NNNN».
3. **Процесс git:** `main` — защищённая ветка, в неё не коммитят напрямую; работа
   в ветках `<тип>/<id-задачи>-<слаг>`; Conventional Commits с `Task: <id>` в
   теле; PR с зелёным `pnpm check` (и CI, когда появится); squash-merge, ветка
   удаляется. Merge в `main` подтверждает владелец.
4. **Версионирование:** аннотированные теги `vMAJOR.MINOR.PATCH` на `main`, до
   1.0 — `0.x`; GitHub Releases по тегам; `CHANGELOG.md` по Keep a Changelog.
   Вехи roadmap отображаются на теги: M0 — `v0.1.0`, M1 — `v0.2.0`, M2 — `v0.3.0`,
   M3 — `v0.4.0`, M4 — `v1.0.0`. Исправления — `PATCH`, новые возможности —
   `MINOR`, несовместимые изменения данных/формата — `MAJOR`.
5. **Remote:** `origin` = приватный GitHub-репозиторий
   `git@github.com:u-cha/house-payments.git`. CI — GitHub Actions с матрицей
   macOS/Windows/Linux (E-12, R-03); причина выбора GitHub — на нём есть раннеры
   всех трёх ОС, у GitLab.com бесплатных macOS-раннеров нет.
6. **Вендоренные скиллы:** `third_party/` в `.gitignore`; источник истины —
   `skills.lock.json` (репозиторий, sparse-пути, коммит, лицензия);
   `scripts/bootstrap-skills.mjs` (`pnpm bootstrap`) восстанавливает клоны и
   симлинки `.dsh/skills/*`. Симлинки коммитятся, потому что описывают набор
   скиллов проекта; до `pnpm bootstrap` они битые — это ожидаемо и задокументировано
   в [README](../../../../README.md).
7. **Интеграция с DSH:** воркспейс и проект доски совпадают; имя ветки содержит id
   карточки доски; изоляция задач `worktree` доступна, но включается только после
   проверки, что в зеркале доступны `.dsh/skills/` и `third_party/`; каталог
   `.dsh-worktrees/` игнорируется. Правила для агентов — [AGENTS.md](../../../../AGENTS.md).
8. **Запрещено:** коммитить `node_modules/`, `third_party/`, `.dsh-worktrees/`,
   `.env*`, секреты и производные диаграммы; хранить документацию вне репозитория;
   force-push и переписывание истории `main`; менять принятый ADR по существу;
   `git clean -xdf` в корне репозитория.

## Последствия

**Положительные:**

- Любая правка документа, решения или кода имеет точку отката и историю.
- Один `git clone`, один `pnpm check`, один тег — меньше мест, где можно ошибиться.
- Код и решения в одном PR: ревью видит, что решение и реализация согласованы.
- Удалённая копия и теги защищают от потери каталога; CI под три ОС разблокирован.
- Воспроизводимость окружения: версии скиллов закреплены, клоны восстанавливаются.

**Отрицательные:**

- История продукта начинается вместе с историей дизайна: релизные теги содержат
  и проектную документацию, и код.
- CI должен фильтровать изменения по путям, чтобы правка документа не собирала
  установщики.
- Репозиторий крупнее, чем нужно было бы только для кода (архив, документация,
  инструменты).
- Свежий клон требует двух шагов подготовки (`pnpm install`, `pnpm bootstrap`).
- На Windows симлинки `.dsh/skills` требуют режима разработчика или WSL; CI эти
  скиллы не использует, но локальная разработка на Windows потребует внимания.
- Первый push в пустой репозиторий выполнен до включения защиты ветки — это
  осознанная инициализация; после неё прямые пуши в `main` запрещены.

## Условия пересмотра

- Репозиторий превышает ~2 ГБ или клон/проверки дольше 5 минут — пересмотреть
  хранение архива и вложений, возможно выделить историю дизайна.
- Понадобилось открыть исходный код отдельно от дизайна и архива — выделить код в
  отдельный репозиторий (вариант 2) с явной миграцией.
- Появилась команда более одного человека с раздельными правами — пересмотреть
  правило merge и, возможно, разделение воркспейсов (вариант 3).
- Лимиты GitHub Actions или стоимость приватного CI становятся значимыми —
  пересмотреть тариф или хостинг, сохранив матрицу трёх ОС.
- DSH меняет модель изоляции задач или перестаёт зеркалить репозиторий — проверить
  `.dsh-worktrees/` и при необходимости оставить изоляцию выключенной.
- Релиз 1.0: `0.x`-схема заменяется на строгую семантическую версию, фиксируется
  процедура выпуска (подпись, артефакты, release notes).
