# ADR-0016: Триггеры CI — только pull request в `main`

## Статус

`accepted`, 2026-11-04. Владелец решения: пользователь-собственник. Согласовано с
владельцем 2026-11-04 в задаче доски `t-mw2egs8j-kpfaxq`: проверки запускаются на
pull request в `main` и по ручному запуску, триггер `push` по веткам отменён.
Заменяет: [ADR-0015](0015-ci-tests-and-status-polling.md) — остальные его решения
(job, опрос результатов, обязательный контекст `check`) перенесены сюда без
изменений.

## Контекст

- [ADR-0015](0015-ci-tests-and-status-polling.md) п. 1 зафиксировал триггеры:
  `push` в любую ветку, `pull_request` в `main`, `workflow_dispatch`. Причина
  `push` — проверить сам workflow и опрос результатов, пока workflow нет в ветке по
  умолчанию: workflow для события `pull_request` берётся из ветки по умолчанию.
- Workflow добавлен в `main` (PR #2, коммит `b2058f9`); причина `push`-триггера
  исчерпана.
- Наблюдаемое дублирование: каждый пуш в ветку с открытым PR даёт **два** прогона
  на один и тот же коммит — `push` и `pull_request` (`synchronize`). Пример:
  2026-11-04 17:28 две поставленные в очередь проверки одного коммита ветки
  `docs/t-mw2b1est-uua0mm-m0-gates` (`push` 17:28:27, `pull_request` 17:28:34);
  ранее то же было на ветке `test/t-mw29vbip-ci-tests`.
- Ruleset `protect-main` требует статус `check`; контекст даёт PR-прогон.
  `strict_required_status_checks_policy` выключен, поэтому прогон на `main` после
  merge для гейта не нужен.
- Публичный репозиторий: стандартные прогоны бесплатны (ADR-0014). Цена
  дублирования — не минуты, а шум в списке прогонов и неоднозначность опроса:
  `pnpm ci:status` видит два прогона одного коммита, а `concurrency` гасит их
  независимо (группы `refs/heads/<ветка>` и `refs/pull/N/merge` различаются).
- Ограничение GitHub: `pull_request`-прогон проверяет merge-превью (слияние PR с
  `main`), а не итоговый коммит, попавший в `main` после squash-merge. Это принято
  осознанно: гейт стоит на PR.
- Ветка без открытого PR не проверяется автоматически. Для таких веток остаётся
  ручной запуск, а проверить содержимое до merge можно черновиком PR.
- Проверки (`pnpm check`) не зависят от секретов и от вендоренных скиллов;
  workflow не запускает `pnpm bootstrap` и ничего не публикует.

## Рассмотренные варианты

### 1. Только `pull_request` в `main` + `workflow_dispatch` (выбран)

`push`-триггер убран. Один прогон на пуш в PR-ветку плюс ручной запуск по
требованию.

**Плюсы:** ровно один прогон на коммит в PR; список прогонов и `pnpm ci:status`
однозначны; проверяется merge-превью, то есть ровно то, что намерены смержить;
меньше шума и лишней нагрузки; не нужны фильтры по путям, чтобы приглушить
`push`-прогоны.

**Минусы:** ветка без PR не проверяется, пока PR не открыт; итоговый коммит в
`main` после merge отдельно не проверяется; дисциплина «сначала PR, потом CI»
переходит из автоматики в правила процесса.

### 2. `pull_request` в `main` + `push` только в `main` + `workflow_dispatch`

`push` сужен с «любой ветки» до `main`, дублирование по PR-веткам исчезает.

**Плюсы:** сохраняет проверку реального `main` после merge — видно, если слияние
что-то сломало; зелёный статус на `main` всегда означает проверенный коммит.

**Минусы:** лишний прогон на каждый merge; `push`-триггер остаётся, и его нужно
учитывать в описании процесса; дублирование лишь переносится с PR-ветки на
`main` (PR-прогон + merge-прогон на тот же набор изменений).

### 3. Оставить оба триггера, гасить дубли через `concurrency` по head-ветке

Группа вида `ci-${{ github.workflow }}-${{ github.head_ref || github.ref_name }}`
отменяла бы один из двух прогонов одного коммита.

**Плюсы:** сохраняются оба триггера; нет изменений в правилах процесса.

**Минусы:** прогоны стартуют одновременно, и «выживший» прогон — лотерея; если
отменяется `pull_request`-прогон, обязательный контекст `check` для PR не
появится и merge заблокируется ложно; отмена не гарантирует экономию. Отклонён:
недетерминированное поведение в гейте недопустимо.

## Решение

1. **Триггеры [`ci.yml`](../../../../.github/workflows/ci.yml): только
   `pull_request: branches: [main]` и `workflow_dispatch`.** `push`-триггер по
   веткам убран; теги не запускают CI, как и раньше.
2. **Ручной запуск сохраняется** как штатный способ проверить ветку без PR или
   изменение самого workflow: `gh workflow run ci.yml --ref <ветка>`. Workflow должен
   существовать в ветке по умолчанию — он там есть.
3. **Проверка остаётся обязательной на PR:** контекст `check` в ruleset
   `protect-main` не меняется; ruleset правится отдельно и этим ADR не затрагивается.
4. **`concurrency` остаётся прежним:** группа по `github.ref` с
   `cancel-in-progress: true`; для PR `github.ref` — `refs/pull/N/merge`, то есть
   новый пуш в PR отменяет предыдущий прогон этого PR.
5. **Порядок работы:** ветка → пуш → PR (можно черновик) → `pnpm ci:status --wait`.
   Локальный `pnpm check` перед пушем остаётся обязательным и повторяется в CI.
   Ветку без PR проверяют ручным запуском.
6. **Остальные решения ADR-0015 сохраняются:** один job `check` на
   `ubuntu-latest`, Node.js 22, pnpm из `packageManager`, `pnpm install
   --frozen-lockfile` + `pnpm check`, права `contents: read`, таймаут 15 минут,
   секретов нет, артефакты не публикуются; опрос — `scripts/ci-status.mjs` с кодами
   выхода `0/1/2/64`; матрица трёх ОС и path-фильтры откладываются до E-01/E-12.
7. **Документация процесса:** README, [AGENTS.md](../../../../AGENTS.md), индекс
   ADR и карта решений обновлены этим изменением.

## Последствия

**Положительные:**

- Один прогон на один коммит в PR: нет дублей, которые сейчас даёт
  `push` + `pull_request`.
- `pnpm ci:status` и список прогонов GitHub однозначны: меньше шума при разборе.
- Проверяется merge-превью PR, то есть то, что попадёт в `main` при merge.
- Меньше нагрузки на Actions и меньше поводов отлаживать расхождения между
  `push`- и `pull_request`-прогонами.

**Отрицательные:**

- Ветка без открытого PR не проверяется автоматически; CI до PR — только ручным
  запуском.
- Итоговый коммит в `main` после merge отдельно не проверяется; если понадобится,
  это отдельное решение (вариант 2).
- Появляется зависимость от дисциплины «открыть PR, чтобы получить CI»; нарушение
  обнаруживается не автоматикой, а ревью.

## Условия пересмотра

- Появится потребность проверять ветки до PR регулярно (агентские циклы, черновые
  ветки) — вернуть `push`-триггер или добавить отдельный лёгкий workflow.
- `main` начнёт ломаться после merge незамеченным — перейти к варианту 2
  (`push` только в `main`) новым ADR.
- Появятся код приложения (E-01) или сборка установщиков (E-12) — пересмотреть
  триггеры вместе с матрицей ОС и path-фильтрами.
- Ruleset начнёт требовать статус на итоговом коммите `main` (`strict` или
  отдельная проверка) — включить `push` в `main`.
- Сменится хостинг CI или опрос результатов — триггеры переопределить вместе с
  реализацией опроса, сохранив принцип «один прогон на коммит в PR».
