# ADR-0018: Единый «последний» запускаемый артефакт

## Статус

`accepted`, 2026-11-05. Владелец решения: пользователь-собственник. Требование
согласовано с владельцем 2026-11-05 в сессии по задаче `t-mw2b1etr-hqc7ws`:
для ручных проверок нужен только последний запускаемый экземпляр. Дополняет
[ADR-0009](0009-cross-platform-desktop-and-installers.md) (установщики),
[ADR-0013](0013-repository-docs-and-versioning.md) (репозиторий) и
[ADR-0016](0016-ci-triggers-on-pull-request.md) (CI на PR в `main`).

## Контекст

- Гейты V0–V3 проверяются запуском: V0 — `pnpm dev`, M0-03 — первый черновой
  `.dmg`, V3 — установщики трёх ОС из CI. Пользователь проверяет их вручную.
- До сих пор не зафиксировано, **где** искать проверяемый экземпляр. Локальные
  сборки electron-builder ложатся в `release/`, но версионные копии, несколько
  сборок рядом и ручной выбор «какая из них последняя» — источник путаницы.
- `main` защищён: изменения приходят только через PR, CI запускается на PR
  (ADR-0016), merge — squash. Значит, «то, что в `main`» и «то, что проверено CI»
  — один и тот же коммит.
- Пользователь сформулировал требование прямо: «мне нужен будет только последний
  всегда». Накопление сборок не нужно; нужен один предсказуемый способ получить
  самый свежий запускаемый экземпляр.
- Ограничения: нет платного хранилища и релизного канала до 1.0; артефакты
  GitHub Actions имеют retention (90 дней по умолчанию); локальная машина —
  macOS.

Силы: простота проверки (тянет к одному пути и одной команде) против сохранения
истории сборок (тянет к версионированию каждого прогона); доверие к экземпляру
(тянет к «только зелёный CI») против скорости (тянет к локальной сборке «прямо
сейчас»).

## Рассмотренные варианты

### 1. Один перезаписываемый локальный каталог + последний артефакт CI (выбран)

Локально сборка всегда идёт в единственный `release/` и перезаписывает предыдущую.
С M0-13 CI публикует артефакты с фиксированными именами, а `pnpm app:latest`
скачивает артефакт последнего зелёного прогона `main` и открывает приложение.

**Плюсы:** проверяется ровно то, что в `main`; одна команда; ничего не
накапливается; «последний» определяется однозначно (зелёный прогон), а не
памятью человека.

**Минусы:** проверка зависит от GitHub Actions, `gh` и сети; к старой сборке
вернуться нельзя; нужны дисциплина имён артефактов и поддержка скрипта.

### 2. Версионированные каталоги и релизы на каждую сборку

`release/0.0.1/`, `release/0.0.2/`, GitHub Releases на каждый merge.

**Плюсы:** история и возможность вернуться к конкретной сборке.

**Минусы:** ровно то накопление, которого не хочет пользователь; нужно каждый раз
выбирать, какая сборка последняя; публичные теги и релизы до 1.0 создают шум и
обещают больше, чем есть.

### 3. Только локальная сборка, без артефактов CI

`pnpm dist:mac` на машине разработчика, CI проверяет только тесты.

**Плюсы:** не зависит от CI и сети; проще.

**Минусы:** «последний» означает «последний раз, когда кто-то собрал», а не то,
что в `main`; локальная сборка может отличаться от CI (другая ОС, другой кэш);
проверка перестаёт быть воспроизводимой.

### 4. GitHub Releases на каждый зелёный merge

**Плюсы:** публичная и стабильная ссылка; история.

**Минусы:** версии до 1.0 не имеют смысла и требуют решения о нумерации; релизы
на каждый merge засоряют канал; подписи и нотаризации до R-04 всё равно нет.

## Решение

1. **Локально — один каталог.** Сборка electron-builder всегда пишет в `release/`
   и перезаписывает предыдущий результат. Версионные подкаталоги не создаются;
   `release/` остаётся в `.gitignore`. Повторный `pnpm dist:mac` даёт ровно один
   актуальный `.dmg`.
2. **CI — только последний и только зелёный.** Начиная с M0-13 артефакты
   установщиков имеют фиксированные имена `house-payments-<os>-latest`
   (`dmg`, `nsis`, `appimage`, `deb`). Артефакт публикуется только прогоном,
   который завершился успешно; красный прогон не публикует ничего. Новый зелёный
   merge в `main` делает свой артефакт «последним»; отдельные версии до 1.0 не
   публикуются.
3. **`pnpm app:latest` — одна команда проверки.** Скрипт находит последний
   успешный прогон `ci.yml` на `main` (`gh run list --branch main --workflow ci.yml
   --status success --limit 1`), скачивает его артефакт, распаковывает в
   `.app-latest/` (в `.gitignore`) с перезаписью предыдущего содержимого и
   открывает приложение. Локальная сборка при этом не выполняется.
4. **Источник истины.** Для приёмки «последний экземпляр» — это артефакт зелёного
   прогона на `main`. Локальная сборка — инструмент разработки и отладки, а не
   источник приёмочного экземпляра.
5. **Устаревшее не хранится.** Актуальны только `release/`, `.app-latest/` и
   последний артефакт CI; retention GitHub Actions покрывает окно проверки.
   Долгосрочное хранение версий появляется вместе с релизами 1.0 (ADR-0009).

## Последствия

**Положительные:**

- Пользователь проверяет одну и ту же команду `pnpm app:latest` на каждом гейте;
  не нужно искать «какая сборка свежая» и удалять старые.
- Проверяется ровно тот коммит, который прошёл CI и попал в `main`.
- Локальный диск не забивается версионными сборками.

**Отрицательные:**

- `pnpm app:latest` зависит от GitHub Actions, авторизованного `gh` и сети;
  задержка между merge и доступностью артефакта.
- Вернуться к конкретной старой сборке в первой версии нельзя — только пересобрать
  или дождаться нового прогона.
- Нужна дисциплина: фиксированные имена артефактов, `.app-latest/` в `.gitignore`,
  скрипт в составе M0-13.
- Неподписанный macOS `.dmg` по-прежнему требует обхода Gatekeeper (M0-03).

**Запрещено:** копить версионные сборки в `release/`; публиковать или считать
проверяемыми артефакты красных прогонов; выдавать локальную сборку за «последний
экземпляр» при приёмке.

## Условия пересмотра

- Появляется потребность проверить конкретный исторический прогон — добавляется
  `pnpm app:latest --run <id>`, принцип «последний по умолчанию» сохраняется.
- Retention или лимиты GitHub Actions перестают покрывать цикл проверки.
- Выходит релиз 1.0: версии, подписанные каналы и обновления (ADR-0009) заменяют
  `latest`; появляется история релизов.
- Появляется второй канал поставки (магазин приложений) — нужна отдельная схема
  артефактов.
