# ADR-0008: Один файл данных, резервные копии и миграции

## Статус

`proposed`, 2026-11-04. Владелец решения: пользователь-собственник.

## Контекст

- C-01, C-09: данные локальны; один переносимый файл; файл можно перенести на
  другое устройство; приложение не должно требовать сервера.
- FR-12, FR-16; QS-07; INV-19, INV-20.
- Пользователь не должен администрировать СУБД и вручную собирать каталоги.
- Вложения (сканы квитанций) — главный источник роста (A-06, [scaling.md](../scaling.md) §2); дедупликация не выполняется, изображения сжимаются при добавлении (R-01).
- Новая версия приложения обязана открывать старый файл, а старая версия — не
  открывать новый (INV-20).

Силы: простота переноса (тянет к одному файлу), производительность (тянет к
отдельным файлам для сканов), сохранность (тянет к версионированию и копиям),
защита (тянет к шифрованию всего).

## Рассмотренные варианты

### 1. Один файл SQLite, вложения — BLOB в нём (выбран)

`*.hpd` — SQLite-файл: все таблицы и содержимое вложений. Рядом ничего не нужно.

**Плюсы:** перенос — копирование одного файла; бэкап атомарен; нет
«осиротевших» файлов; целостность проверяется одной командой; формат допускает
шифрование в будущем.

**Минусы:** файл растёт до гигабайт; `VACUUM` и копирование дороже; крупный BLOB
требует аккуратной потоковой записи.

### 2. Файл БД + каталог вложений

**Плюсы:** база остаётся маленькой и быстрой; сканы можно открывать напрямую.

**Минусы:** перенос требует копировать папку целиком; пользователь легко скопирует
только БД и потеряет сканы; шифрование нужно для двух мест; появляются битые ссылки.

### 3. Проприетарный формат или JSON-файл

**Плюсы:** полный контроль над форматом.

**Минусы:** нет транзакций и индексов; восстановление после сбоя ненадёжно;
инструменты просмотра отсутствуют; JSON не годится для сканов. Отклонён.

### 4. Серверная БД (PostgreSQL) с локальным клиентом

**Плюсы:** привычная эксплуатация для разработчика.

**Минусы:** противоречит C-01 и требованию «пользователь не знает про Docker»;
нужен сервер. Отклонён.

## Решение

1. **Рабочий файл** `house-payments.hpd` — SQLite (WAL, `foreign_keys=ON`,
   `busy_timeout`, `synchronous=NORMAL`). Расширение своё, но формат — открытый
   SQLite: файл можно открыть любым SQLite-клиентом.
2. **Вложения** хранятся в таблице `attachment` как BLOB (`content`), с `sha256`
   и размером; одно фото — одно вложение, дедупликация не выполняется.
   Изображение сжимается при добавлении (ориентир 0,5–0,7 МБ на скан при
   сохранении читаемости); хранится **только сжатая копия**, оригинал не
   сохраняется (R-01). Отдельного каталога нет.
3. **Схема** описана в [model.dbml](../../domain/model.dbml); миграции — нумерованные,
   только вперёд. Перед применением создаётся копия файла; при ошибке файл
   возвращается из копии, данные не теряются (INV-20).
4. **Версия схемы** — в `schema_version`. Приложение отказывается открывать файл
   новее себя с понятной ошибкой `SCHEMA_VERSION_UNSUPPORTED`.
5. **Резервные копии:** две копии состояния — текущая и предыдущая — в выбранной
   пользователем папке, обновляются при запуске/закрытии; перед перезаписью
   выполняется проверка целостности (`PRAGMA quick_check`), поэтому испорченное
   состояние не затирает обе копии. Плюс ручная команда «Сохранить копию»; копия —
   цельный файл (R-02, QS-07).
6. **Экспорт/импорт:** CSV и XLSX по сущностям, JSON — полный дамп для переноса;
   импорт начислений из CSV — после первой версии (R-06), в v1 — ручной ввод и
   распознавание. Экспорт не заменяет бэкап: он теряет часть связей, но читается
   без приложения.
7. **Архив:** в первой версии отсутствует; все данные в одном файле. Вынос старых
   лет в `archive-YYYY.hpd` — зона развития, включается решением при срабатывании
   T-01. Юридически значимого архива нет (OQ-05): для личного архива достаточно
   сжатой копии, даты добавления, `sha256` и записи аудита.
8. **Шифрование:** в первой версии не выполняется — решение OQ-02 закрыто
   2026-11-04 ([risks.md](../../risks.md) §3); защита — пароль профиля и ОС.
9. **Повреждение файла:** приложение не перезаписывает файл, показывает ошибку и
   предлагает восстановление из копии; `PRAGMA quick_check` при открытии.

## Последствия

**Положительные:**

- Перенос на другое устройство — копирование одного файла.
- Бэкап и восстановление понятны пользователю и не требуют администратора.
- Целостность данных и вложений проверяется одной командой.
- Открытый формат: данные не «заперты» в приложении.

**Отрицательные:**

- Файл может вырасти до нескольких гигабайт; копирование и `VACUUM` заметны.
- Крупные BLOB требуют потокового чтения, а не загрузки целиком в память.
- Оригиналы фото не сохраняются: остаётся сжатая читаемая копия (R-01).
- Две копии занимают до двух объёмов файла; при повреждении обеих остаётся ручная копия.
- Архив по годам отложен; при росте файла понадобится отдельное решение.

**Запрещено:** хранить вложения вне файла; писать в файл без миграции; открывать
файл новее приложения; откатывать миграцию автоматически; делать бэкап «только
когда пользователь вспомнил».

## Условия пересмотра

- Файл > 2 ГБ или бэкап > 5 мин (T-01, T-03) — сжать вложения, рассмотреть архив
  по годам и инкрементальную копию.
- Появляется синхронизация (ADR-0011) — вложения синхронизируются по `sha256`,
  файл перестаёт быть единственным носителем.
- Требуется совместная работа с другими людьми — пересматривается серверный контур.
- Появится требование юридически значимого архива (OQ-05 переоткрывается) — архив
  получает подпись и неизменяемое хранение.
