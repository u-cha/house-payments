# Сценарии качества: измеримые требования и проверки

Статус: **proposed** (ревью 2026-11-04). Основание: [brief.md](../brief.md) §5
(QS-01…QS-12), ограничения C-01…C-11. Связанные решения:
[core-modules.md](core-modules.md), ADR-0001…ADR-0012, [scaling.md](scaling.md).

## 1. Как читать и что означает «проверка»

Сценарий качества — не пожелание, а утверждение с порогом и способом опровержения.
У каждого сценария шесть полей: источник, стимул, окружение, ответ, мера, проверка.
Формулировки «быстро» и «надёжно» запрещены. Приоритеты взяты из брифа:
QS-01, QS-02, QS-04…QS-06, QS-11 и QS-12 — приоритет 1; QS-07…QS-09 — приоритет 2;
QS-10 — приоритет 3. QS-03 (импорт CSV) отложен после первой версии решением R-06.

Для локального приложения часть привычных серверных сценариев (доступность, RPO/RTO,
горизонтальное масштабирование) переформулирована в терминах одного устройства и
файла данных; это осознанная замена, а не пропуск.

## 2. Сценарии

### QS-01 — Отзывчивость при открытии и навигации

| Поле | Значение |
|---|---|
| Источник | Пользователь-собственник |
| Стимул | Открытие файла данных за 10 лет (≈ 50 000 записей) и переход к списку за период |
| Окружение | Ноутбук 4 ядра / 8 ГБ ОЗУ / SSD; файл не повреждён; приложение уже установлено |
| Ответ | Открытие файла, проверка версии схемы, прогрев соединения; списки — по индексам, без полного сканирования |
| Мера | Открытие файла ≤ 2 с; список за период ≤ 200 мс; переход между экранами ≤ 100 мс; 0 полных сканов таблиц на типовых запросах |
| Проверка | Замер на синтетическом файле 50 000 записей и 1 500 вложений (`tests/performance/`); ревью планов запросов (`EXPLAIN QUERY PLAN`). Владелец: техлид |

### QS-02 — Задержка записи

| Поле | Значение |
|---|---|
| Источник | Пользователь, распознавание, напоминания |
| Стимул | Сохранение платежа вместе с распределением по выбранным квитанциям при открытом списке квитанций |
| Окружение | Файл с боевым объёмом, WAL, один писатель, параллельно открыт отчёт |
| Ответ | Одна транзакция: платёж + выбранные распределения + баланс + аудит + журнал (INV-22); UI не блокируется, показывает прогресс |
| Мера | p95 сохранения ≤ 300 мс, p50 ≤ 80 мс; интерфейс отвечает на ввод ≤ 50 мс; 0 потерянных операций при повторном открытии окна |
| Проверка | Инструментированный интеграционный тест (SQLite + домен), замер на 50 000 записей. Владелец: разработчик (`ledger`/`payments`) |

### QS-03 — Импорт начислений (после первой версии)

Импорт CSV вне первой версии: основные квитанции вносятся фото/сканом и
распознаванием, иногда вручную (решение R-06). Сценарий сохраняется для будущего
импорта выгрузок из личных кабинетов.

| Поле | Значение |
|---|---|
| Источник | Пользователь, выгрузка из личного кабинета поставщика |
| Стимул | Импорт CSV на 12 000 строк за год; повторная загрузка того же файла |
| Окружение | Батч по 1 000 строк, staging в памяти, дедупликация по `batchKey` и `external_ref` |
| Ответ | Разбор и валидация → дедупликация → пачечная вставка → отчёт по строкам |
| Мера | ≤ 10 с на 12 000 строк; повтор — 0 новых начислений; 100 % строк отражены в отчёте (`created` / `duplicate` / `rejected`); ни одна строка не теряется молча |
| Проверка | Интеграционный тест с фикстурой 12 000 строк и повтором; property-тест дедупликации. Владелец: разработчик (`billing`) |

### QS-04 — Консистентность при параллельных операциях

| Поле | Значение |
|---|---|
| Источник | Пользователь, работающий в двух окнах/операциях |
| Стимул | В одном окне вносится платёж, в другом — показание и правка черновика квитанции в том же файле |
| Окружение | Два окна приложения, один файл, WAL, блокировка записи |
| Ответ | Каждая операция — транзакция; конфликт записи возвращает `CONCURRENT_MODIFICATION` с предложением повторить; UI перечитывает состояние |
| Мера | 0 потерянных обновлений; 0 нарушений INV-05…INV-10 после 500 чередующихся операций; 100 % конфликтов возвращают retryable-код; тупиковые блокировки < 0,1 % |
| Проверка | Конкурентный интеграционный тест двумя соединениями; проверка инвариантов «с нуля» после прогона. Владелец: техлид |

### QS-05 — Защита данных

| Поле | Значение |
|---|---|
| Источник | Чужой доступ к файлу, ошибка логирования |
| Стимул | Попытка открыть файл без профиля; проверка журналов |
| Окружение | Пароли — Argon2id; файл не шифруется в первой версии (OQ-02); журналы только локальные |
| Ответ | Вход по паролю профиля; защита файла — средствами ОС и входом в приложение; логи не содержат сумм, адресов и ФИО |
| Мера | 0 секретов и PII в журналах (проверка шаблонов); профиль владельца имеет стойкий хеш; 0 операций без активной сессии |
| Проверка | Тест шаблонов логов; тест входа; тест «журнал не содержит PII». Владелец: техлид |

### QS-06 — Прослеживаемость финансовых изменений

| Поле | Значение |
|---|---|
| Источник | Пользователь, член семьи, будущий аудит |
| Стимул | Запрос всех изменений документа за период с автором и причиной |
| Окружение | Любая финансовая операция, включая импорт и сторно |
| Ответ | `audit_event` пишется в той же транзакции; запись содержит профиль, время, действие, объект, причину, `correlation_id`; аудит append-only |
| Мера | 100 % финансовых изменений имеют ровно одну запись аудита; 0 успешных `UPDATE`/`DELETE` по `audit_event`; цепочка «причина → документ → распределение» восстанавливается |
| Проверка | Трансформационный тест «изменение без аудита невозможно»; триггеры БД; e2e-сценарии. Владелец: техлид |

### QS-07 — Сохранность и восстановление

| Поле | Значение |
|---|---|
| Источник | Сбой диска, ошибка пользователя, повреждение файла |
| Стимул | Потеря файла данных; повреждение файла |
| Окружение | Две автокопии (текущая и предыдущая) при запуске/закрытии + ручная копия; проверка целостности при открытии и перед копированием |
| Ответ | Восстановление из текущей или предыдущей копии; проверка `PRAGMA integrity_check`; журнал изменений и аудит восстанавливаются вместе с файлом |
| Мера | RPO ≤ 24 ч при регулярном запуске; RTO ≤ 1 ч; успешная репетиция восстановления не реже 1 раза в квартал; 0 молчаливых повреждений; испорченное состояние не перезаписывает обе копии |
| Проверка | План с владельцем и протокол репетиции; автотест «повреждённый файл → понятная ошибка, данные не перезаписаны». Владелец: техлид |

### QS-08 — Автономность и запуск

| Поле | Значение |
|---|---|
| Источник | Пользователь без интернета |
| Стимул | Запуск приложения и полный цикл работы при отключённой сети |
| Окружение | Офлайн, без сервера, без внешних API |
| Ответ | Все функции доступны офлайн; сеть нужна только для будущей синхронизации и проверки обновлений |
| Мера | 100 % функций первой версии работают офлайн; запуск ≤ 3 с; 0 запросов к сети при обычной работе (проверяется перехватом) |
| Проверка | e2e-прогон с отключённой сетью; замер холодного старта. Владелец: техлид |

### QS-09 — Эволюционность при 10× росте

| Поле | Значение |
|---|---|
| Источник | Рост числа помещений, лет учёта и документов |
| Стимул | 10 помещений, 10 лет, ≈ 50 000 записей, 1 500 вложений |
| Окружение | Та же архитектура: один файл SQLite, один процесс |
| Ответ | Индексы по ключам выборки, сжатие вложений, отчёты на read-model; архив по годам — отдельное решение по триггеру T-01 [scaling.md](scaling.md) §7 |
| Мера | Пороги QS-01 и QS-02 удерживаются на 10× объёме (QS-03 — после v1); размер файла ≤ 2 ГБ; отсутствует обязательный переход на сервер |
| Проверка | Нагрузочный прогон на 10× синтетике; ревью триггеров раз в полгода. Владелец: техлид |

### QS-10 — Сопровождаемость и онбординг

| Поле | Значение |
|---|---|
| Источник | Разработчик и сопровождающий |
| Стимул | Новый инженер на чистом ноутбуке с доступом к репозиторию |
| Окружение | Документация в git, `pnpm install`, детерминированные seed-данные |
| Ответ | README с шагами запуска, `pnpm check` как единая точка проверки, ADR как объяснение решений, сборка установщика одной командой |
| Мера | ≤ 8 ч от клонирования до зелёного `pnpm check`; ≤ 1 ч до собранного установщика; 0 шагов, требующих устной передачи знаний |
| Проверка | Онбординг-протокол с таймером; CI (GitHub Actions) «`pnpm check` на чистом клоне». Владелец: техлид |

### QS-11 — Распознавание квитанций

| Поле | Значение |
|---|---|
| Источник | Пользователь, скан или фото квитанции от поставщика |
| Стимул | 20 квитанций от трёх поставщиков: сканы, фото и PDF, часть — с наклоном и неравномерным освещением |
| Окружение | Офлайн, ноутбук 4 ядра / 8 ГБ, локальный OCR (русский язык), без отправки изображений в сеть |
| Ответ | Предобработка изображения → OCR (или разбор PDF с текстовым слоем) → правила/шаблон поставщика → кандидаты полей → экран подтверждения; финансовые документы создаются только после подтверждения. Шаблоны создаёт пользователь по скану (QS-12); разработчик может дать стартовые шаблоны; правки пользователя шаблон не меняют (INV-23) |
| Мера | Точность полей `period`, `supplier`, `account`, `total` ≥ 90 % на эталонном наборе чётких печатных квитанций (фото, скан, PDF); рукописный текст и плохие фото — без гарантии, с ручной правкой; обработка страницы ≤ 15 с; 0 финансовых документов без подтверждения (INV-21); 100 % полей с низкой уверенностью подсвечены |
| Проверка | Эталонный набор 20 квитанций (фото/скан/PDF) и протокол ручной проверки; e2e «файл → подтверждение → квитанция»; тест «без подтверждения документов нет»; тест «правка не меняет шаблон»; замер времени на 4 ядрах. Владелец: техлид |

### QS-12 — Настройка шаблона квитанции по скану

| Поле | Значение |
|---|---|
| Источник | Пользователь, квитанция незнакомого формата или новый поставщик |
| Стимул | Пришла квитанция, для которой нет шаблона, либо поставщик сменил формат |
| Окружение | Офлайн, ноутбук, без разработчика и без сети |
| Ответ | «Шаблоны» → «Создать по скану» → выбрать образец и поставщика → обвести мышью области полей и таблицу услуг → предпросмотр распознавания → сохранить шаблон (версия 1) → перераспознать квитанцию |
| Мера | Шаблон создаётся ≤ 15 мин без участия разработчика; на образце после сохранения распознаются обязательные поля (`period`, `supplier`, `account`, `total`); предпросмотр создаёт 0 финансовых документов; правки полей шаблон не меняют (INV-23); старая версия не перезаписана |
| Проверка | e2e «незнакомый скан → разметка → сохранение → повторное распознавание»; тест «правка поля не меняет шаблон»; тест «изменение создаёт новую версию, старая доступна»; замер времени создания шаблона. Владелец: техлид |

## 4. Конфликты характеристик и выбранное разрешение

**Правило приоритета.** Сначала — целостность финансовых данных и защита (QS-04,
QS-05, QS-06), затем отзывчивость (QS-01, QS-02), затем сохранность и автономность
(QS-07, QS-08), затем эволюционность (QS-09). Сценарий более низкого приоритета
уступает, но не отключается: он деградирует управляемо и видимо.

### Удобство против корректности (QS-02 vs QS-04, QS-06)

Соблазн — сохранять платёж «оптимистично» и синхронизировать баланс позже. Это
создаёт переплату и дыры в аудите. Решение: финансовые операции — синхронная
транзакция; при конфликте UI показывает retryable-ошибку и перечитывает состояние.
Скорость ввода выигрывается не отложенной записью, а формой без лишних шагов.

### Резервные копии против отката (QS-07)

Пользователь выбрал две резервные копии — текущую и предыдущую, — которые
создаются при запуске/закрытии. Перед перезаписью копии приложение проверяет
целостность файла (`PRAGMA quick_check`), поэтому испорченное состояние не может
молча затереть обе копии; ошибки показываются явно. Ручная команда «Сохранить
копию» остаётся. Цена — до двух объёмов файла на диске; риск R-02 закрыт
решением от 2026-11-04 ([risks.md](../risks.md) §2).

### Отчёты против записи (QS-01 vs QS-02)

Отчёты по 10 годам не должны конкурировать с вводом платежа. Решение: отчёты
читают read-model и индексы, не блокируют писателя (WAL); тяжёлые агрегаты
пересчитываются по требованию с индикатором прогресса, а не в транзакции операции.

### Локальность против будущей синхронизации (C-01 vs ADR-0011)

Синхронизация «потом» не должна требовать переписывания модели. Решение: UUIDv7,
`change_log` с `device_id` и логическими часами, append-only аудит и отсутствие
автоинкрементных ключей — с первого дня. Сама синхронизация в первой версии
выключена (FR-17 после MVP).

### Точность распознавания против приватности (QS-11 vs C-11)

Облачный OCR дал бы выше точность, но отправляет изображения квитанций (адрес,
ФИО, лицевой счёт) третьей стороне. Решение: распознавание локальное; при
недостаточной точности пользователь видит, какие поля не уверены, и правит их
вручную. Облачный OCR возможен только как явная опция с согласием пользователя и
отдельным ADR, а не по умолчанию.

### Гибкость шаблонов против предсказуемости (QS-12 vs QS-11, INV-23)

Пользователь должен сам добавлять форматы, но приложение не должно «самообучаться»
на его ошибках. Решение: шаблон меняется только явной разметкой и сохранением
новой версии; правки распознанных полей идут в аудит и шаблон не трогают. Так
новый формат появляется без разработчика (QS-12, R-10), а результат распознавания
остаётся воспроизводимым: у каждой версии шаблона известны области, правила и
образец.
