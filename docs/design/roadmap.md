# Roadmap: вехи, эпики и декомпозиция работ

Статус: **proposed** (ревью 2026-11-04). Основание: [brief.md](brief.md) §4 (FR),
§9; [architecture/core-modules.md](architecture/core-modules.md);
[architecture/quality-scenarios.md](architecture/quality-scenarios.md); ADR-0001…0012.

Документ отвечает на вопрос «из каких крупных кусков состоит работа и в каком
порядке их можно делать». Порядок зафиксирован решением пользователя OQ-01
(2026-11-04): распознавание квитанций входит в первый полезный контур (M2), а не
переносится в конец. Основание и остальные решения — [risks.md](risks.md).
Архитектура от порядка не зависит: эпики независимы там, где указано, и
опираются только на уже зафиксированные контракты.

## 1. Правила декомпозиции

1. Эпик — законченная пользовательская ценность, а не слой кода.
2. Эпик дробится на задачи размером до 3 дней, каждая задача имеет проверяемый
   результат и тест (или явное «почему теста нет»).
3. Задача не выходит за границы одного модуля; если выходит — это два эпика или
   явный порт между ними.
4. Задача не начинается, пока не выполнены её зависимости из таблицы §5.
5. Каждая задача ссылается на FR и инварианты; приёмка — по критериям эпика.
6. Эпик считается готовым, когда зелёный `pnpm check`, обновлены артефакты и
   выполнены критерии DoD эпика; «работает у меня» не является критерием.
7. Читаемость ревью: PR ≤ 200 строк изменений; lock-файлы и сгенерированные
   артефакты в лимит не входят. Не влезает — задача делится до старта, а не
   после ревью.

## 2. Вехи

| Веха | Название | Что можно показать пользователю | Эпики |
|---|---|---|---|
| M0 | Фундамент | Приложение устанавливается, создаёт файл данных, входит по профилю, делает резервную копию | E-01, E-02, E-12 (каркас) |
| M1 | Справочники | Внесены объекты и их типы, поставщики, лицевые счета, услуги, тарифы | E-03 |
| M2 | Квитанции, распознавание и оплата | Фото/скан/PDF квитанции → распознавание → подтверждение → квитанция; настройка шаблона по скану; платёж, распределение, долг и переплата | E-04, E-05, E-06, E-10, E-14, E-15 |
| M3 | Быт и контроль | Счётчики, показания, напоминания, отчёты | E-07, E-08, E-09 |
| M4 | Переносимость и поставка | Экспорт, бэкап, установщики под три ОС, обновления | E-11, E-12 |
| M5 | Развитие | Синхронизация между устройствами (зона развития) | E-13 |

Вехи M0–M2 — минимально полезный продукт: пользователь вносит квитанции фото,
сканом или PDF, распознаёт их, подтверждает и отмечает оплату; новый формат
квитанции пользователь добавляет сам в модуле настройки шаблонов. Порядок внутри
M2: E-04 → E-05 → E-10 → E-14 → E-15; E-06 может идти параллельно E-10 после E-05.
M3–M4 делают продукт удобным и переносимым. M5 — отдельное решение (ADR-0011).

## 3. Гейты первой запускаемой версии (M0)

Веха M0 нарезана на 14 задач (M0-00…M0-13) и проверяется гейтами: гейт — это
запускаемый результат, который можно показать, а не «код написан». Гейты
согласованы с пользователем 2026-11-04; задачи заведены на доске.

| Гейт | Когда | Что проверяется |
|---|---|---|
| V0 | после M0-02 | Пустое окно Electron запускается — первая рабочая версия приложения |
| V1 | после M0-09 | Окно + файл данных + вход по профилю владельца |
| V2 | после M0-11 | Создание объекта; данные сохраняются после перезапуска (прототип) |
| V3 | после M0-13 | Установщики и CI на macOS, Windows и Linux; последние артефакты `latest-*` |

Порядок задач M0 (слева направо; M0-03 сознательно сразу после V0: пользователь
просил `.dmg` как можно раньше, подпись — на V3):

| Задача | Что делает | Гейт |
|---|---|---|
| M0-00 | Гейты V0–V3 и порядок M0 в этом документе | — |
| M0-01 | Каркас pnpm-workspace и `apps/desktop` | — |
| M0-02 | Окно Electron и типизированный IPC ping | V0 |
| M0-03 | Черновой `.dmg` без подписи (electron-builder), единый `release/` | — |
| M0-04 | SQLite: подключение, WAL, раннер миграций, `schema_version` | — |
| M0-05 | `shared`: Money, Period, UUIDv7, AppError, clock | — |
| M0-06 | Транзакционный раннер, `change_log` и аудит | — |
| M0-07 | Файл данных: открытие/создание и проверка версии схемы | — |
| M0-08 | `identity`: профиль владельца, вход, сессия | — |
| M0-09 | UI входа и каркас навигации | V1 |
| M0-10 | `catalog`: вертикальный срез «объект» (типы, архив) | — |
| M0-11 | UI объектов: список, форма и типы; сессия и аудит catalog-команд | V2 |
| M0-12 | Архитектурные тесты границ модулей и e2e smoke | — |
| M0-13 | CI на трёх ОС и артефакты `latest-*` установщиков | V3 |

**Артефакты для ручных проверок — всегда только последний** (ADR-0018). Локально
`pnpm dist:mac` перезаписывает единственный `release/` и даёт стабильное имя
`release/house-payments-mac-arm64-latest.dmg`. С M0-13 CI публикует артефакты
`house-payments-<os>-latest` только с зелёных прогонов `main`, а `pnpm app:latest`
скачивает последний, распаковывает в `.app-latest/` с перезаписью и открывает
приложение без локальной сборки. Версионные копии не накапливаются; история
сборок появится с релизами 1.0.

**Каждая итерация с кодом заканчивается пересборкой и ссылкой** (ADR-0019):
итерация — задача доски, меняющая код приложения; её завершение — `pnpm dist:mac`,
а в отчёте по задаче — ссылка на `release/house-payments-mac-arm64-latest.dmg`.
До M0-13 это единственный проверяемый экземпляр; после M0-13 — дополнительная
ссылка, а приёмка идёт по артефакту зелёного `main`. Гейт не закрывается словами
«код написан»: у сдачи должна быть ссылка на запускаемый экземпляр.

Гейт не переносится: если задача гейта не влезает в лимит читаемости (§1 п. 7),
она делится до старта, а гейт остаётся за последней задачей цепочки. M0-12
ставит архитектурные тесты и e2e smoke до V3, чтобы CI трёх ОС запускал уже
проверенный набор.

## 4. Эпики

### E-01 — Каркас приложения и файл данных

**Цель:** запускаемое приложение с одним файлом данных, миграциями и транзакциями.
**Требования:** C-01, C-06, C-09; QS-01, QS-07, QS-08. **ADR:** 0001, 0005, 0008, 0009, 0010.
**Результат:** Electron-каркас; IPC с Zod; SQLite с WAL; миграции; `schema_version`;
журнал изменений; `pnpm check`; сборка установщика (черновая).
**Зависимости:** нет.
**DoD:** приложение открывает пустой файл, создаёт схему, повторный запуск не
теряет данные; проверка версии схемы; тест «файл новее приложения отклонён».
**Риски:** нативная сборка `better-sqlite3` под три ОС (ADR-0010).

### E-02 — Профиль владельца и доступ

**Цель:** вход по профилю владельца и аудит действий; модель готова к членам семьи.
**Требования:** FR-14, INV-16, QS-05. **ADR:** 0006.
**Результат:** создание профиля `owner`, вход, смена пароля, аудит входа и
изменений; таблицы `profile`/`setting` готовы к ролям, но управление другими
профилями не входит в v1.
**Зависимости:** E-01.
**DoD:** нельзя удалить последнего `owner`; пароли — только Argon2id; тест входа;
модель профилей не требует миграции при добавлении `member`.

### E-03 — Справочники

**Цель:** внести всё, к чему потом привязываются начисления и платежи.
**Требования:** FR-01…FR-04, FR-19; INV-04; QS-01. **ADR:** 0002.
**Результат:** объекты (квартира/дом/машиноместо/участок), поставщики, лицевые счета
(со ссылкой на ЛК и памяткой), услуги, тарифы с датой действия; архивирование без
удаления.
**Зависимости:** E-01, E-02.
**DoD:** пересечение тарифов отклоняется; закрытие счёта с долгом запрещено;
списки работают на 10× объёме.

### E-04 — Начисления за период

**Цель:** зафиксировать начисления за период — вручную или из подтверждённой
квитанции.
**Требования:** FR-05, FR-18; INV-01, INV-02, INV-11, INV-13. **ADR:** 0002, 0004.
**Результат:** ручной ввод, ввод по шаблону, начисления из распознанной квитанции
(`source = recognition`), сторно. Импорт CSV — после первой версии (R-06) и в
первую веху не входит.
**Зависимости:** E-03.
**DoD:** дубль начисления отклоняется; сторно однократно; начисление из
распознавания связано с вложением и квитанцией.

### E-05 — Квитанции

**Цель:** собрать квитанцию из начислений, зафиксировать и защитить от правок.
**Требования:** FR-06; INV-03, INV-05, INV-06; QS-06. **ADR:** 0003, 0007.
**Результат:** черновик, строки со ссылкой на начисления, фиксация, срок оплаты,
аннулирование с причиной, перевыпуск после `void`, связь «документ — сторно».
**Зависимости:** E-04.
**DoD:** сумма = сумма строк; `issued` не редактируется; аннулирование только без
активных распределений; перевыпуск за тот же период работает; каждое изменение в аудите.

### E-06 — Платежи, распределение, баланс

**Цель:** внести платёж и увидеть долг/переплату.
**Требования:** FR-07, FR-08; INV-07…INV-10, INV-13; QS-02, QS-04. **ADR:** 0003.
**Результат:** платёж с ключом сразу с распределением по выбранным квитанциям,
FIFO/ручное разнесение аванса, отмена распределения, баланс лицевого счёта.
**Зависимости:** E-05.
**DoD:** 0 переплат сверх суммы; баланс сходится; повтор платежа возвращает
существующий; платёж без квитанции невозможен (INV-22); конкурентный тест.
Отметка «оплачено» из сценария «квитанция → оплата» работает через этот эпик.

### E-07 — Счётчики и показания

**Цель:** вести счётчики, показания, поверку и передачу.
**Требования:** FR-09, FR-10; INV-14, INV-15; QS-06.
**Результат:** карточка счётчика, история поверок, показания по периодам,
подтверждение убывания, замена счётчика с начальным показанием, отметка о передаче.
**Зависимости:** E-03.
**DoD:** дубль периода отклоняется; убывание без подтверждения отклоняется, с
подтверждением — аудит; вне срока поверки — `VERIFICATION_EXPIRED`; замена создаёт
новый счётчик; отметка не переписывает показание.

### E-08 — Напоминания

**Цель:** не забывать оплатить, передать показания и пройти поверку.
**Требования:** FR-11; QS-06.
**Результат:** простые настраиваемые правила (за сколько дней до срока оплаты,
окно передачи показаний, приближение поверки) с разумными значениями по
умолчанию; список, выполнение и откладывание. Сложный конструктор правил не
делается (R-07).
**Зависимости:** E-05, E-07.
**DoD:** напоминания создаются идемпотентно; закрытие снимает напоминание;
просроченные видны; нет дублей при повторном открытии.

### E-09 — Отчёты и графики

**Цель:** увидеть расходы по периодам, услугам и объектам.
**Требования:** FR-13; QS-01.
**Результат:** отчёты «расходы за период», «динамика по услугам», «долг по
объектам», графики, экспорт отчёта.
**Зависимости:** E-06.
**DoD:** отчёт сходится с балансом; открытие отчёта ≤ 1 с на 10× объёме; данные
не блокируют ввод.

### E-10 — Вложения

**Цель:** хранить сканы и фото квитанций рядом с документами.
**Требования:** FR-12; INV-19; QS-07. **ADR:** 0008.
**Результат:** прикрепление, просмотр, удаление с подтверждением, проверка
целостности по `sha256` (без дедупликации); изображение сжимается при добавлении,
хранится только сжатая копия (R-01).
**Зависимости:** E-05.
**DoD:** файл попадает в тот же файл данных; битая ссылка обнаруживается; бэкап
включает вложения.

### E-11 — Экспорт, бэкап, миграции

**Цель:** данные можно перенести и не потерять.
**Требования:** FR-16; C-09; INV-20; QS-07. **ADR:** 0008, 0009.
**Результат:** две автокопии состояния (текущая и предыдущая) при запуске/закрытии
с проверкой целостности, ручная копия, восстановление, экспорт CSV/XLSX/JSON,
миграции с копией перед применением (R-02).
**Зависимости:** E-01, E-06.
**DoD:** репетиция восстановления ≤ 1 ч; файл новее приложения отклоняется;
экспорт открывается без приложения; обе автокопии восстанавливаются.

### E-12 — Установщики и обновления

**Цель:** установка без администратора и обновления без боли.
**Требования:** C-08; QS-10. **ADR:** 0009, 0010.
**Результат:** CI GitHub Actions на macOS/Windows/Linux; NSIS/DMG/AppImage/deb;
подпись Windows и нотаризация macOS к релизу 1.0 (до этого — тестовые сборки без
подписи, R-04); `electron-updater`, канал stable/beta, инструкция для пользователя.
**Зависимости:** E-01.
**DoD:** чистая установка на трёх ОС без прав администратора; обновление поверх
старой версии сохраняет данные; релизная сборка подписана; тестовая сборка
помечена как неподписанная.

### E-14 — Распознавание квитанций

**Цель:** вносить квитанции со сканов и фото без ручного перебивания.
**Требования:** FR-18; C-11; INV-21; QS-11. **ADR:** 0012.
**Результат:** загрузка файла → OCR в воркере → шаблоны поставщиков → кандидаты
с уверенностью, включая несколько строк услуг → экран подтверждения → создание
начислений (source = `recognition`)/квитанции; исправления сохраняются в аудите
и шаблон не меняют (INV-23). Шаблоны берутся из модуля настройки (E-15); для
известных поставщиков могут поставляться стартовые шаблоны по образцам (R-10).
**Зависимости:** E-04, E-05, E-10. Входит в веху M2 (OQ-01).
**DoD:** точность полей ≥ 90 % на эталонном наборе из 20 квитанций (фото, скан,
PDF); страница ≤ 15 с на 4 ядрах; 0 документов без подтверждения; сеть не
используется; низкая уверенность подсвечена; правка попадает в аудит, но не меняет
шаблон (INV-23); применяется шаблон выбранного поставщика.
**Риски:** качество фото и рукописный текст (R-09); поддержка шаблонов
поставщиков (R-10).

### E-15 — Модуль настройки шаблонов квитанций

**Цель:** пользователь сам добавляет новый формат квитанции, не дожидаясь
обновления приложения.
**Требования:** FR-20; INV-23; QS-12. **ADR:** 0012.
**Результат:** список шаблонов по поставщикам; создание шаблона по скану с
разметкой областей полей и таблицы услуг мышью; предпросмотр распознавания на
образце; сохранение новой версии без перезаписи старых; применение шаблона по
поставщику при распознавании.
**Зависимости:** E-14 (пайплайн и кандидаты), E-10 (вложения), E-03 (поставщики).
Входит в веху M2.
**DoD:** пользователь без разработчика создаёт шаблон по образцу ≤ 15 мин (QS-12);
обязательные поля распознаются на образце; предпросмотр не создаёт документов;
правка поля не меняет шаблон (INV-23); повторно загруженная квитанция этого
формата распознаётся по сохранённому шаблону; сеть не используется.
**Риски:** качество разметки и сложные таблицы услуг (R-10, R-09); смена формата
поставщиком требует повторной настройки (R-10).

### E-13 — Синхронизация (зона развития)

**Цель:** данные доступны на нескольких устройствах.
**Требования:** FR-17; ADR-0011.
**Результат:** сервер-ретранслятор журнала, шифрование, курсоры, разрешение
конфликтов справочников, статус синхронизации в UI.
**Зависимости:** E-01…E-11, E-14.
**DoD:** два устройства сходятся; повторная доставка не создаёт дублей; конфликт
справочника разрешается детерминированно и виден пользователю; данные на сервере
зашифрованы.
**Примечание:** включается отдельным решением пользователя; в критерии приёмки
первой версии не входит.

## 5. Зависимости эпиков

```
E-01 → E-02 → E-03 → E-04 → E-05 → E-06
                    ↘ E-07 → E-08
                              E-06 → E-09
E-05 → E-10 → E-14 → E-15
E-01 → E-11
E-06 → E-11
E-01 → E-12
E-01…E-11, E-14, E-15 → E-13
```

Критический путь: E-01 → E-03 → E-04 → E-05 → E-10 → E-14 → E-15. Задержка на
любом из них сдвигает M2 — первый сценарий «квитанция → распознавание → оплата»
и настройку нового формата пользователем. E-06 может идти параллельно E-10;
E-07…E-09 и E-11/E-12 — после своих зависимостей.

## 6. Предлагаемый порядок (не решение)

| Приоритет | Вехи | Почему |
|---|---|---|
| P1 | M0, M1, M2 | Первый полезный контур: справочники, квитанция с фото/скана, распознавание, оплата |
| P2 | M3 | Счётчики, напоминания и отчёты — повседневная ценность после основного сценария |
| P3 | M4 | Переносимость и установщики нужны до первого «боевого» использования |
| P4 | M5 | Синхронизация — после подтверждения спроса на несколько устройств |

Порядок зафиксирован решением OQ-01 (2026-11-04); зависимости §5 обязательны.
Распознавание квитанций и модуль настройки шаблонов (E-14, E-15) — часть M2, а не
поздняя надстройка. Решение по шаблонам — R-10 в [risks.md](risks.md).

## 7. Как это превращается в задачи

Для каждого эпика:

1. Выписать вертикальные срезы «пользовательский сценарий + данные + тест».
2. Разбить на задачи до 3 дней; каждая — один модуль и одна проверка.
3. Завести задачи на доске, привязать к проекту и отметить зависимости.
4. Приёмка задачи — критерии эпика + зелёные проверки; приёмка эпика — DoD §4.
5. Артефакты (`docs/design/**`, ADR) обновляются в той же задаче, если меняется
   решение или модель.
