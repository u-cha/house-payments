# AGENTS.md — правила работы в этом репозитории

Один репозиторий = DSH-воркспейс `house-payments`: проектная документация и код
приложения живут вместе и версионируются вместе. Читайте этот файл перед любым
изменением; правила ниже не рекомендации, а границы.

## 1. Что где лежит

| Путь | Что это | Кто меняет |
|---|---|---|
| `docs/design/` | Проектные артефакты: бриф, ADR, домен, архитектура, UX, roadmap, трассировка. Источник истины по решениям. | дизайн/архитектура; правки — любая задача, которая меняет решение |
| `archive/` | Прежние проработки (SaaS-версия). Не действуют, не исправляются «под текущее». | только при явной задаче об архиве |
| `apps/desktop/` | Код приложения (Electron: main/preload/renderer, модули из `core-modules.md`). Создаётся с E-01. | только задачи на код |
| `apps/*/`, `packages/*/` | Будущие пакеты pnpm-воркспейса. | задачи на код |
| `scripts/`, `tests/` | Проверки артефактов и рендер диаграмм. | задачи на инструменты/проверки |
| `release/` | Артефакт локальной сборки (`house-payments-mac-arm64-latest.dmg`). **В git не входит**, перезаписывается каждой сборкой (ADR-0018, ADR-0019). | никто: создаётся `pnpm dist:mac` |
| `.github/workflows/` | CI-проверки GitHub Actions (job `check`). | задачи на CI/инфраструктуру |
| `.dsh/skills/` | Симлинки на вендоренные скиллы. | не редактировать руками: `pnpm bootstrap` |
| `skills.lock.json` | Закреплённые версии вендоренных скиллов. | только вместе с проверкой, что скилл грузится |
| `third_party/` | Клоны чужих репозиториев. **В git не входит.** | никто: только `pnpm bootstrap`; руками не править |
| `.dsh-worktrees/` | Рабочие деревья изоляции задач DSH. **В git не входит.** | никто |

Правило границ: **код — только в `apps/`/`packages/`, проектные решения — только в
`docs/`**. Нельзя «по-быстрому» положить код в `docs/` или описание решения в
`apps/`.

## 2. Команды

```bash
pnpm install            # зависимости инструментов документации
pnpm bootstrap          # восстановить third_party/ и .dsh/skills/ после свежего клона
pnpm check              # validate + тесты; обязательное условие любого изменения
pnpm sync:main          # подлить свежий origin/main перед пушем (см. §3.8)
pnpm ci:status          # статус последнего прогона CI текущей ветки (--wait, --json)
pnpm dist:mac           # пересобрать артефакт в release/ и напечатать путь (ADR-0019)
pnpm validate           # только проверки артефактов
pnpm diagrams           # отрендерить .mmd/.dbml в .svg/.png (результат не коммитится)
```

Новый клон: `git clone`, затем `pnpm install`, затем `pnpm bootstrap` — иначе
скиллы проекта будут битыми симлинками. `pnpm bootstrap` также включает локальный
`pre-push`-хук (`.githooks/pre-push`), который не пускает пуш ветки без свежего
`origin/main`.

## 3. Git: правила, которые нельзя нарушать

1. **`main` защищён.** Прямые коммиты в `main` не делаются; работа идёт в ветке,
   результат попадает в `main` только через pull request.
2. Имя ветки: `<тип>/<id-задачи>-<краткий-слаг>`, где тип — `feat`, `fix`, `docs`,
   `chore`, `refactor`, `test`; `<id-задачи>` — id карточки доски (`t-…`) или
   номер issue. Пример: `docs/t-mw279jn2-repo-policy`.
3. Коммит — Conventional Commits: `feat: …`, `fix: …`, `docs: …`, `chore: …`,
   `refactor: …`, `test: …`. Заголовок до 72 символов, тело объясняет **почему**,
   а не что. В теле — строка `Task: <id задачи>`.
4. Атомарность: один логический смысл на коммит; сгенерированные файлы не
   коммитятся.
5. Запрещено: `git push --force` в `main`; переписывание истории `main`;
   `git clean -xdf` в корне (сотрёт `third_party/`, `node_modules/` и кэш);
   коммит `node_modules/`, `third_party/`, `.dsh-worktrees/`, `.env*`, секретов,
   `*.svg`/`*.png` под `docs/` (это производные).
6. PR: заголовок по Conventional Commits, описание — что/зачем/как проверено/
   остаточные риски и принятые по ним решения (ссылки на строки
   `docs/design/risks.md` §8); зелёный `pnpm check` и зелёный job CI `check`;
   squash-merge, ветка удаляется. Merge в `main` подтверждает владелец репозитория.
7. CI: проверки запускаются на PR в `main` (ADR-0016); после пуша в PR-ветку
   дождаться результата `pnpm ci:status --wait`; упавший прогон чинится до merge
   (`gh run view <id> --log-failed`), после исправления — новый пуш. Ветку без PR
   проверяют вручную: `gh workflow run ci.yml --ref <ветка>`. Merge с красным CI
   запрещён.
8. **Свежий `main` перед каждым пушем.** Перед `git push` в ветку (в том числе
   перед первым пушем новой ветки):

   ```bash
   pnpm sync:main    # git fetch origin + git merge origin/main, без rebase
   pnpm check        # после слияния проверки обязательны
   ```

   - Конфликт разрешается вручную и только если понятны обе стороны и смысл
     изменения сохраняется. После разрешения — `pnpm check` и коммит слияния.
   - **Смысловой конфликт** (обе стороны меняют одно решение, логику, инвариант)
     или непонимание, чья версия верна, — **остановиться и спросить
     пользователя**: показать файлы, обе стороны и предложение по разрешению.
     Не выбирать сторону «наугад» и не «чинить» конфликт удалением чужой правки.
   - Запрещено: `--ours`/`--theirs`/`-X ours`/`-X theirs`, отключение или
     ослабление тестов ради зелёного `pnpm check`, пуш без свежего `origin/main`.
   - Хук `.githooks/pre-push` (ставится `pnpm bootstrap`) блокирует такой пуш;
     обход `git push --no-verify` — только с явного разрешения пользователя.
   - Решение и границы — ADR-0017.

## 4. Документация и решения

1. Решение, которое меняет архитектуру, домен или процесс, оформляется ADR в
   `docs/design/architecture/adr/` по правилам журнала. Принятый ADR не
   переписывается: новое решение — новый ADR со ссылкой «Заменяет: ADR-NNNN».
2. Изменение решения в одном PR обновляет **все** затронутые артефакты: бриф,
   трассировку, roadmap, инварианты, README-навигацию. `pnpm check` это проверяет
   частично, остальное — ответственность автора.
3. Диаграммы — только из текстовых источников (`.mmd`, `.dbml`). Руками
   отредактированный `.svg` считается ошибкой.
4. Пользовательская документация (установка, руководство) появится в `docs/user/`
   в E-12 и версионируется тем же тегом, что и код.

## 5. Что считается завершённой работой

- Задача выполнена, `pnpm check` зелёный, job CI `check` зелёный, изменения
  закоммичены в ветку и описаны в PR.
- Ветка содержит свежий `origin/main` (`pnpm sync:main` перед пушем); конфликты
  слияния разрешены осознанно или вынесены пользователю.
- Затронутые артефакты (`docs/design/**`, ADR, трассировка) обновлены в том же
  изменении.
- **Итерация с кодом заканчивается пересборкой.** Если задача меняет код
  приложения (`apps/**`, `packages/**`, конфигурацию сборки), перед сдачей
  выполняется `pnpm dist:mac`: артефакт лежит в известном месте
  `release/house-payments-mac-arm64-latest.dmg` (ADR-0019). Задачи без изменений
  кода пересборки не требуют.
- Отчёт по задаче доски содержит: что изменено, как проверено, остаточные риски
  и решения по ним (или явное «остаточных рисков нет») со ссылками на строки
  `docs/design/risks.md` §8, **и ссылку на пересобранный артефакт** —
  markdown-ссылку на `release/house-payments-mac-arm64-latest.dmg`, а не только
  имя файла. «Собрано» без ссылки завершением итерации не считается.
- Секретов, абсолютных путей этой машины и артефактов сборки в коммите нет.

## 6. Остаточные риски и решения пользователя

Остаточный риск — то, с чем пользователь будет жить после изменения: ручной шаг,
отложенная работа, внешняя зависимость, необратимый выбор, известное
ограничение. Техническая деталь, не меняющая поведение пользователя и не
требующая выбора, риском не считается.

Любая сессия или задача, которая меняет репозиторий, до перевода карточки в
`in_review` (в интерактивной сессии — до финального ответа) обязана:

1. Перечислить остаточные риски простым языком: что случится с пользователем,
   при каких условиях и чем это грозит. Если рисков нет — явно написать
   «остаточных рисков нет» и почему.
2. По каждому риску, где есть выбор, задать пользователю один вопрос с 2–3
   вариантами и рекомендацией: `ask_user_question` в интерактивной сессии; в
   исполнении доски — `waitingForHuman=true` с причиной, карточка остаётся
   `in_progress` и не переводится в `in_review` до решения.
3. Записать решение в `docs/design/risks.md` §8 «Риски итераций и решения» и в
   комментарий карточки разделом «Решения по остаточным рискам». «Отложить» —
   тоже решение, с триггером пересмотра; если отложенная работа нужна — отдельная
   карточка.
4. Не считать риск принятым без записи решения. Молчаливое принятие запрещено.

Пользователь — источник истины. Агент не решает за пользователя риск, если есть
выбор; решение «отложить» допустимо только явно. `done` ставит только
пользователь, и для карточки с рисками это означает, что решения приняты.
Создаваемые агентом карточки получают DoD-пункт «Остаточные риски вынесены на
решение пользователя». Проверка журнала — `pnpm check` (`validate-risks`).

## 7. Карточки задач на доске

Исполняющий агент получает только заголовок и `prompt` карточки; `description`
ему не передаётся. Поэтому:

1. `prompt` — самодостаточное ТЗ: контекст, что сделать, файлы и пути,
   ограничения, зависимости, критерии приёмки, команды проверки, правила
   репозитория и риски. Всё, что нужно для работы, должно быть в нём.
2. `description` — краткое описание для человека на доске; рассчитывать на него
   как на инструкцию нельзя.
3. Перед созданием карточки проверяй: если убрать `description`, задача всё ещё
   выполнима по `prompt`?
4. DoD-пункт про остаточные риски и ссылка на артефакт сборки — в `prompt` и
   чек-листе, не только в `description`.
